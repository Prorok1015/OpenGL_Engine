# Модель угроз: процесс-декодер моделей

**Issue:** #1043 (Windows-песочница — #1054, macOS — #1097). Предыстория: #647 (отдельный процесс), #925, #987.

## Что защищаем

- **Файлы пользователя**: всё, что может прочитать редактор с правами пользователя (домашняя папка, ключи, токены, другие проекты).
- **Проект**: файлы `res://`, `user://`, настройки редактора (`edt://`), git-репозиторий; то, что импорт копирует в проект, потом грузится внутри редактора.
- **Сам редактор**: его память, время и стабильность.

## Атакующий

Автор файла модели (`.gltf/.glb/.obj/.fbx` и `.bin/.mtl`/текстуры рядом). Модель может прийти из интернета, от агента или из чужого проекта. Считаем, что модель может эксплуатировать ошибку в парсере (Assimp) и выполнить произвольный код в процессе, который её разбирает.

## Границы

1. **Процесс** (#647, сделано): модель разбирает `snk_model_decoder` в своей временной папке (0700), с лимитом памяти (`RLIMIT_AS` / Job) и временем (kill по дедлайну), без core dump, без наследования окружения. Падение, зависание или съеденная память стоят только неудавшегося импорта. Ответ ребёнка редактор проверяет (`accept_scan_answer`, `accept_import_answer`) до того, как что-либо сохранить.
2. **Брокер файлов** (#1043, PR 1): ребёнок не открывает ни одного файла, кроме своей папки запуска. Редактор сам находит, читает и хэширует каждый побочный файл по правилу `model_file_access` (папка модели или content root, без скрытых имён, без выхода через `..` и ссылки, только `.bin`/`.mtl`/картинки, лимиты по числу и байтам) и передаёт байты в бандле запроса. Скан (`broker_scan`) — до 3 раундов с общим бюджетом и одним дедлайном на весь скан, включая чтения редактора (после дедлайна новый раунд не запускается и файл не читается); повторный запрос того же имени в следующем раунде пропускается (не ошибка). В ответе — до 256 имён, у одного файла — не больше 8 имён, байты каждого файла идут одним блобом, сколько бы имён на него ни указывало. Импорт получает ровно показанный человеку список, перечитанный и сверенный по идентичности и SHA-256.
3. **Песочница ОС** (#1043 PR 2 — Linux; #1054 — Windows; macOS — #1097, ещё нет): ребёнок сам отнимает у себя файловую систему, сеть и лишние системные вызовы на уровне ядра, до того как прочитать запрос. Подробно — ниже, «Песочница Linux».

## Песочница Linux (#1043, PR 2)

`tools/model_decoder/decoder_sandbox.cpp`, `decoder_sandbox::apply`, сразу после `harden_process` (no_new_privs, без core dump, PDEATHSIG) и до чтения бандла запроса:

1. Закрываются все дескрипторы, кроме 0, 1, 2 (`close_range`, иначе цикл до `RLIMIT_NOFILE`).
2. `RLIMIT_FSIZE` = самый большой ответ, который редактор прочитает (`--max-output-bytes`, `largest_bundle_bytes` от `answer_limits`): ни один файл ребёнка не больше; превышение — SIGXFSZ.
3. **Landlock** (ABI берётся у ядра): обрабатываются все права ФС, которые знает ABI (ABI 1 — чтение, запись, каталоги, создание/удаление, спецфайлы, ссылки, исполнение; ABI 2 — REFER; ABI 3 — TRUNCATE; ABI 5 — IOCTL_DEV). Одно правило: папка запуска (cwd) — всё, кроме EXECUTE. Значит, вне папки запуска нельзя открыть, создать, удалить, переименовать, обрезать (с ABI 3) ни одного файла, а исполнить нельзя ничего, в том числе в своей папке. ABI ≥ 4: TCP bind/connect обрабатываются без правил — никакого TCP. ABI ≥ 6: scoped — абстрактные unix-сокеты и сигналы только внутри своего домена. `/proc` после этого тоже закрыт (часовой пояс читается до песочницы).
4. **seccomp-bpf, список разрешённого**; всё прочее — `EPERM`. Чужая архитектура (`AUDIT_ARCH` не x86_64/aarch64) и x32-вызовы — kill процесса. Разрешено то, что нужно пути декодирования: чтение/запись, `openat`, stat-семейство, `getdents64`, `mkdir/unlink/rename` (*at и старые x86_64), `readlink` (libstdc++ `fs::canonical` → glibc `realpath` вызывает его на каждой части пути), память, futex, сигналы себе, время, `getrandom`, epoll/eventfd/timerfd (boost::asio), `clone3` → `ENOSYS` (glibc откатывается на `clone`, а тот отказан: ни процессов, ни потоков, #1105), `tgkill`/`tkill` только себе (`abort`). Закрыто: сокеты, `connect`/`bind`, `execve(at)`, fork/vfork/новый процесс, `ptrace`, `process_vm_*`, `bpf`, `io_uring_*`, `ioctl`, `truncate`, chmod/chown, `utimensat`, xattr, `kill`, SysV/POSIX IPC, keyctl, `pidfd_*`, `perf_event_open`, `userfaultfd`, `unshare`/`setns`/`mount`, `open_by_handle_at`, `personality`, `prctl` (после установки).
   `fcntl` — только команды над своими дескрипторами и блокировками (`F_DUPFD[_CLOEXEC]`, `F_GETFD/SETFD`, `F_GETFL`, `F_SETFL` без `O_ASYNC`, `F_[OFD_]GETLK/SETLK/SETLKW`): `F_SETOWN`/`F_SETSIG`/`O_ASYNC`/`F_NOTIFY`/аренды заставили бы ядро слать сигнал другому процессу (редактору). Фильтр ставится с `SECCOMP_FILTER_FLAG_TSYNC`.
5. Окружение ребёнка — `TMPDIR=<папка запуска>`.
6. Перед Landlock ребёнок проверяет, что у него один поток (`/proc/self/status`): `landlock_restrict_self` ограничивает только вызвавший поток. Второй поток (или нечитаемый `/proc`) — сбой настройки, код 4 (кроме `off`; в сборках с санитайзерами проверки нет — у TSan свой поток).
7. Сразу после настройки, **до чтения запроса**, ребёнок пишет первой строкой stderr `snk-sandbox-status: fs=landlock|none syscalls=seccomp|none[ why=...]`. Редактор берёт состояние изоляции только из первой строки (`sandbox_status_reader`); всё, что ребёнок пишет после разбора, может исходить от модели и не учитывается. В ответе (`manifest`) поля `sandbox` больше нет.

**Что остаётся открытым.** Landlock не ограничивает stat и readlink: ребёнок может узнать, существует ли путь вне своей папки, его размер, время и цель ссылки (не содержимое). Чтение того, что ребёнку передали (байты модели и побочных файлов), и запись в свою папку — по определению. Время и память — лимиты из #647. Ответ по-прежнему проверяет редактор.

**Исполняемая память.** `mmap` и `mprotect` разрешены без проверки аргументов, `PROT_EXEC` тоже: код, внедрённый через ошибку парсера, может создать и выполнить новый машинный код в своём процессе. Принято: он остаётся под той же песочницей — без exec, сети, сигналов редактору, файлов вне папки запуска. Фильтр мог бы проверять аргумент `prot` у `mmap`/`mprotect`. Сейчас он этого не делает. Пути декодирования `PROT_EXEC` после настройки не нужен, но glibc может подгрузить модуль через `dlopen` (iconv, nss), поэтому такой запрет надо сначала проверить на всех путях.

**Исчерпание процессов** (#1105, закрыто). Потоки входят в лимит процессов пользователя: модель, плодящая потоки до срока декодера (#647), исчерпала бы его, и `fork` перестал бы работать у всех процессов пользователя, в том числе у редактора. Поэтому фильтр отказывает `clone` целиком, не только новым процессам. Декодеру потоки не нужны: до песочницы он проверяет, что поток один (п. 6), а после неё ни один путь поток не создаёт — с #1077 в декодере нет системы ресурсов и `ds::task_system`, в assimp потоков нет, логгер синхронный. Если декодеру понадобятся потоки, это отдельное решение: ограниченный пул до песочницы и пересмотр проверки п. 6. Без фильтра (`best_effort` на ядре без seccomp, процессор без фильтра, сборка с санитайзером) потоки, как и `fork`, не ограничены. `RLIMIT_NPROC` не годится: он считает все процессы пользователя.

**Проверено тестами** (`tests/edt_decode_runner_tests.cpp`, #1082). Изнутри ребёнка отказаны: открытие и запись вне папки запуска, `truncate` (Landlock с ABI 3 или фильтр) и `chmod` (только фильтр) файла вне папки, TCP, `execve`, `io_uring_setup`, `ptrace`, `fork`, `clone` для `posix_spawn` (CLONE_VM|CLONE_VFORK) и для потока (`pthread_create`, #1105), сигналы редактору. У каждой пробы есть контрольный запуск, который должен пройти, иначе тест падает: тот же вызов под `--sandbox off` (для записи — запись в свою папку). Так видно, что проба работает и отказывает именно песочница. Исключение одно: `io_uring`, которому система отказывает и без песочницы (sysctl, профиль контейнера), — тогда сообщение вместо проверки.

**Режимы** (`--sandbox off|best_effort|required`, решение владельца). `off` — только закрытие унаследованных дескрипторов, no_new_privs и `RLIMIT_FSIZE`, без Landlock и seccomp. Политику проверяет сам ребёнок до чтения запроса — его отчёту после компрометации верить нельзя:
- механизма **нет** (Landlock: ENOSYS/EOPNOTSUPP/EPERM от проверки ABI или ABI < 1; seccomp: `PR_GET_SECCOMP` → EINVAL; не Linux): `required` — выход с кодом 4 и одной строкой причины в stderr, редактор проваливает импорт/загрузку с текстом «the model decoder cannot run in its sandbox: <причина>»; `best_effort` — работа без него, строка состояния говорит `fs=none`/`syscalls=none` с причиной, редактор пишет один WARN за запуск (без Landlock — «может читать и писать любые файлы пользователя»: seccomp файлы не защищает);
- механизм **есть, но настройка не удалась** (любой вызов landlock_*/seccomp после успешной проверки ABI, no_new_privs, RLIMIT_FSIZE): код 4 в `best_effort` и `required` (no_new_privs и RLIMIT_FSIZE — и в `off`), ребёнок никогда не продолжает. Вне `required` это дефект, а не отсутствие изоляции: редактор добавляет к ошибке, что изоляцию можно выключить в `import/decoder_sandbox` (решение лида).

Режим задаёт одна настройка, которую меняет только человек: cfg `import/decoder_sandbox` — `on` (по умолчанию, = `best_effort`), `off`, `required` (для CI и тестов); иное значение — `on` с WARN. Она действует на любой импорт: человека, модели уровня (`res://`) и агента; `import_source::sandbox` может только повысить режим, импорт агента его не трогает. Решение владельца: импорт никогда не отказывает из-за отсутствия изоляции — при `on` без Landlock/seccomp (старое ядро, политика, Windows/macOS до #1054) декодер работает без неё с WARN в лог; видимое предупреждение — #1076: одна строка уровня warning в Problems (источник `decoder`, худший статус за запуск, при `off` — сразу при старте), пометка в обоих вопросах агенту и поле `decoder_sandbox` в результате его job (не скрывается). Агент настройку не меняет: она читается один раз при старте из cfg-файла или `--set`, ни одна доступная агенту команда не пишет cfg, ни один доступный ему путь записи не ведёт к cfg-файлу, а `vcs.checkout`/`vcs.pull` агента, меняющие файл конфигурации редактора (`--config`, иначе `config/editor.cfg` рядом с exe), отклоняются так же, как для файла политики агента. Статус уходит в Problems до проверки ответа: упавший, остановленный по времени или вернувший мусор запуск тоже учитывается; ребёнок, не написавший первой строкой статус, считается работающим без изоляции. Граница не держится, если агент сам запускает процесс редактора (`--mcp-stdio`) с `--set import/decoder_sandbox off`: такой агент и так запускает что угодно от имени пользователя (в том числе разбор модели без всякого декодера); это принято (решение владельца), а поле `decoder_sandbox` в ответе всё равно говорит об отсутствии изоляции. При `off` изоляции нет, риск на человеке. Код 4 — только `required` без механизма или сбой настройки имеющегося механизма (см. выше).

**Сборки с санитайзерами** (тестовые, не поставляются): seccomp не ставится (рантайм санитайзера делает вызовы, которых нет в списке) — `syscalls=none`, и `required` там выполняется одним Landlock. Проверки «один поток» тоже нет — у TSan свой поток. Это допустимо, пока такие сборки не выпускаются. Landlock ставится; проверка утечек LSan выполняется до него (она читает `/proc`) и на выходе больше не запускается.

## Песочница Windows (#1054, #1099)
Редактор запускает ребёнка (`platform::process_options::confinement`):
1. **AppContainer** `snk.model_decoder` без capabilities. Нет сети, нет профиля пользователя, нет файлов, на которые у контейнеров нет ACE.
   - Профиль создаётся до первого запуска (`platform::app_container`, `CreateAppContainerProfile`; уже есть — SID по имени, `DeriveAppContainerSidFromAppContainerName`). Объект с SID создаётся один раз за сессию и хранится в `process_decoder`. Профиль остаётся в реестре и `%LOCALAPPDATA%\Packages\snk.model_decoder` и после удаления редактора; эта папка доступна контейнеру на запись и переживает запуски.
   - Не удалось создать профиль — изоляции нет, причина та же, что ниже в «Запасном пути»: при `on` редактор запускает ребёнка без контейнера и сам ставит статус, при `required` — отказ. Неудачный старт процесса больше не трактуется как «нет профиля».
   - SID контейнера получает ACE. Папка запуска: чтение и запись (наследуется всем, что в ней) плюс отдельный `FILE_TRAVERSE` только для папок — на файлах этот бит означает исполнение. Папка копии декодера: чтение и исполнение. ACE на копию добавляется, только если в ACL её ещё нет, и не снимается никогда.
   - На папку запуска ставится метка low integrity (`S:(ML;OICI;NW;;;LW)`): AppContainer работает на low и иначе не пишет. Метка и ACE ставятся по имени и не снимаются. Поэтому в `read_write` передаётся только папка, созданная для одного запуска и удаляемая после него, никогда не путь, выбранный человеком.
   - Других изменений в ACL машины нет: папка запуска и копия принадлежат редактору.
2. **Политики при создании процесса.** Дочерние процессы запрещены (`CHILD_PROCESS_RESTRICTED`; на CI `CreateProcess` из контейнера получил `ERROR_CHILD_PROCESS_BLOCKED`). Mitigations:
   - нет dynamic code;
   - нет точек расширения;
   - образы не грузятся с удалённых путей (предпочтения System32 нет: свой рантайм C/C++ рядом с программой должен выигрывать у старого в System32);
   - строгая проверка дескрипторов;
   - шрифты не грузятся.

   Сам декодер первым делом вызывает `SetDefaultDllDirectories(System32 | папка программы)`: папка запуска в поиске DLL не участвует.
3. **Job:**
   - один процесс;
   - `KILL_ON_JOB_CLOSE`;
   - лимит памяти;
   - без буфера обмена, рабочего стола, чужих дескрипторов окон, глобальных атомов, системных параметров, выхода из сеанса, настроек экрана.
4. **Без консоли** (`DETACHED_PROCESS`): процесс AppContainer, получивший консоль, не стартует (`STATUS_DLL_INIT_FAILED`). stdio — каналы редактора.
5. **Окружение.** `TEMP`/`TMP` указывают в папку запуска. `PATH`, `SystemRoot`, `LOCALAPPDATA`, `APPDATA` и `USERPROFILE` редактора передаются ребёнку; последние три нужны: без них контейнер не стартует (`ERROR_ENVVAR_NOT_FOUND`). Сами эти папки контейнеру не открыты.

**Копия декодера.** Сначала ребёнок запускается из папки редактора. Установленная сборка в `Program Files` читаема контейнерами (ACE `ALL APPLICATION PACKAGES`), копия ей не нужна; CI проверяет это на распакованном пакете, которому та же ACE выдана вручную (`check_windows_package.sh`, шаг 6).
- Если контейнер не стартует или DLL не грузятся (код выхода загрузчика до строки статуса), редактор один раз за сессию копирует декодер.
- Копируются: `snk_model_decoder.exe`, DLL из `snk_model_decoder.deps` (его пишет CMake; после #1077 декодер не грузит DLL проекта) и рантайм C/C++ рядом с ним.
- Место: `%LOCALAPPDATA%\snk\decoder\<имя>\<SHA-256 набора>\`. Подменённый файл копии пересоздаётся. Копии других сборок удаляются (`fs::remove_all`; папку копий пишет только редактор).
- Если запуск из сохранённой копии не удался (её мог удалить другой редактор), копия делается заново один раз.
- Неподписанный exe, запущенный из `AppData`, может задеть антивирус или политику (AppLocker/WDAC/ASR). Тогда работает запасной путь ниже. Подпись релизов — отдельное решение владельца.

**Проверка в ребёнке**, до чтения запроса. Требуется:
- токен AppContainer;
- пустой список capabilities;
- процесс в Job;
- запрет dynamic code и дочерних процессов.

Контейнер есть, но не такой — код 4 при любом режиме, кроме `off`: это дефект.

Не в контейнере:
- `required` — код 4;
- `best_effort` — `fs=none`.

Строка статуса: `fs=appcontainer syscalls=policy`. Разбор строгий (#1099): другой порядок полей, лишний пробел или неизвестное значение — «не сообщил», то есть худший случай. Конец строки (`\n` или `\r\n`) отрезает чтение каналов до разбора.

**Ответ и папка запуска.** Ребёнок может удалить всё в своей папке и сделать саму папку junction (без контейнера — точно; в контейнере на CI Windows отказала, но тест на этом не настаивает). Поэтому редактор:
- читает ответ ниже папки запуска: резолвит только её родителя, а саму папку и файл открывает без перехода по ссылкам (`read_bundle`, `bundle_folder::written_by_peer`; до #1099 `canonical()` проходил такую junction);
- удаляет папку запуска без перехода по ссылкам (`core::res::remove_scratch_dir` → `platform::beneath::remove_tree_beneath`, #1316): каждая папка открывается от вышестоящей, ссылка внутри удаляется сама, ссылка на месте самой папки — отказ, READONLY снимается у самой записи, пути длиннее MAX_PATH удаляются. Дерево глубже 256 папок не удаляется (отказ в лог).

**Запасной путь (решение владельца).** Контейнер нельзя поднять ни на месте, ни из копии: нет профиля, политика машины, ACL, нет копии.
- При `on` редактор запускает ребёнка без контейнера. Статус «без изоляции» с причиной ставит сам редактор, а не берёт со слов ребёнка. Дальше — Problems, пометка агенту, поле `decoder_sandbox` (#1076).
- При `required` — отказ с той же причиной.

**Проверено тестами** (`tests/edt_decode_runner_tests.cpp`, `tests/plt_beneath_tree_tests.cpp`). В контейнере отказаны: открытие файла вне папки, hardlink на него в папку запуска, TCP к слушающему порту, запуск `cmd.exe`. У каждой пробы есть контрольный запуск той же копии без контейнера (`--sandbox off`), который должен пройти. Отдельно проверяются:
- отчёт `fs=appcontainer syscalls=policy`;
- отказ без имени контейнера;
- одна запись ACE на копии после нескольких запусков;
- папка запуска, ставшая junction: ответ через неё не читается, цель не удаляется (без контейнера junction обязана получиться);
- удаление ссылки с READONLY и дерева глубже MAX_PATH.

На CI пакета (`windows-package`) упакованный декодер запускается на месте, в контейнере, под `required`: на папку распаковки выдаётся `ALL APPLICATION PACKAGES: RX`, как у `Program Files`, редактор грузит уровень с моделью, копия не должна появиться.

**Что остаётся открытым:**
- чтение мест с ACE `ALL APPLICATION PACKAGES` (`Program Files`, `Windows`);
- папка профиля `%LOCALAPPDATA%\Packages\snk.model_decoder`: контейнер пишет в неё, и она переживает запуски — канал между разборами разных моделей;
- поверхность ядра win32k: декодер больше не грузит DLL проекта (#1077), но lockdown (`PROCESS_MITIGATION_SYSTEM_CALL_DISABLE_POLICY`) пока не включён;
- `RLIMIT_FSIZE` на Windows нет: размер ответа ограничивает только чтение редактором.

## Что брокер ловит

- Честный, но враждебный файл модели, который ссылается на `../../.ssh/id_rsa`, абсолютный путь, скрытую папку или ссылку наружу: редактор отказывает по правилу, байты в ребёнка не попадают. Имя сначала проверяется лексически, до любого обращения к ФС: UNC (`//host`, `\\host`), `\\?\`, `\\.\`, потоки (`x.mtl:stream`) и любое `:`, кроме двоеточия диска, — отказ; абсолютный путь допускается только у побочного файла и только лексически внутри папки модели / content root.
- FIFO или устройство вместо файла: `resolve` только делает stat, открывает файл `read_beneath` (без блокировки и ссылок), так что скан на нём не зависает.
- Подмену файла между сканом и импортом: импорт перечитывает файл и сверяет id и SHA-256.
- Файл, которого не было в списке: на импорте ребёнок его не получает — для него такого файла нет, с диска ничего не читается (`.obj` без своего `.mtl` импортируется с материалом по умолчанию, как раньше). Ребёнок не может отличить «запрещён» от «нет на диске», и байтов это ему не добавляет. Так же редактор отвечает на имя побочного файла, которое запрещает именно правило (`refusal_kind::rule`, с WARN); превышение лимита или файл, которому нельзя доверять, валят скан: парсер сам пробует запасные имена, например `<модель>.mtl` у OBJ; запрещённая текстура по-прежнему валит скан, как и любое имя у модели, которая не файл на диске (#925).
- Чтение по пути, где папка или файл подменены на ссылку после проверки: редактор читает через `platform::beneath::read_beneath` (без следования ссылкам).

## Что брокер НЕ ловит

- **Скомпрометированный парсер без песочницы ОС**: если модель выполнила код в ребёнке, а песочницы нет (Windows, где контейнер не поднять, macOS до #1097, Linux без Landlock/seccomp в режиме `best_effort`), у этого кода права пользователя — он может сам открыть любой файл и сходить в сеть. Брокер убирает только *легальный* путь чтения; от эксплойта защищает песочница ОС (Linux и Windows — см. выше).
- **Утечку разрешённых файлов**: ребёнок получает байты каждого файла, прошедшего правило, и может унести их в выходной бандл. Картинки проверяются по сигнатуре, но у `.bin`/`.mtl` сигнатуры нет — их содержимое может оказаться в ресурсах импорта. Правило ограничивает, *какие* файлы читаются (папка модели), а не что с ними делает парсер.
- **Ресурсы (CPU/память) внутри лимитов**: модель может потратить весь дедлайн и всю память, отведённые декодеру.
- **Содержимое ответа сверх проверок**: `accept_import_answer` проверяет имена, типы, ссылки и размеры ресурсов, но не «правильность» геометрии или текстур.
- **Двоичный файл геометрии `<stem>.geom.bin`** (EPIC-79, #1068 PR3b): принимается только под этим именем, один, только вместе с geom desc, у которого есть диапазоны, и не в `all_tags`. До записи в `memory://` редактор декодирует пару так же, как загрузчик: размер не больше `desc_binary::max_file_bytes` и лимитов ответа, затем `res::desc_binary::parse` (заголовок, закрытый словарь раскладок, диапазоны внутри файла и без перекрытий, SHA-256 каждого диапазона считает редактор), затем проверки данных загрузчика (`check_geometry_data`: индексы в пределах вершин, конечные position/uv, шаг, целые треугольники). Хранится не ответ ребёнка, а пара, заново закодированная писателем редактора из проверенных данных: смещения, хэши и поля заголовка ребёнка не сохраняются. Треугольники массивами и линии/точки с `.bin` — отказ. Не ловится: правдоподобность самой формы модели (как и раньше).

## Остаточный риск и следующие шаги

- Linux: stat/readlink вне папки запуска остаются возможны (см. «Что остаётся открытым»); отметка в панели Problems и в вопросе агенту о работе без песочницы — следующий шаг.
- #1097: песочница для macOS.
- #1077: декодер без `snk_engine.dll` (меньше кода в процессе, lockdown win32k).
- Сообщения с именами из ребёнка проходят `text_escape::escaped_text` (≤ 256 байт) — подделать строку лога или вопроса человеку нельзя.
- Ссылка (symlink, junction) внутри папки модели не читается: тип проверяется без следования ссылкам, а `read_beneath` открывает каждый компонент пути без них. Такой файл валит скан как «не обычный файл», даже если указывает внутрь папки.
