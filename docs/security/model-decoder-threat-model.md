# Модель угроз: процесс-декодер моделей

**Issue:** #1043 (Windows-песочница — #1054). Предыстория: #647 (отдельный процесс), #925, #987.

## Что защищаем

- **Файлы пользователя**: всё, что может прочитать редактор с правами пользователя (домашняя папка, ключи, токены, другие проекты).
- **Проект**: файлы `res://`, `user://`, настройки редактора (`edt://`), git-репозиторий; то, что импорт копирует в проект, потом грузится внутри редактора.
- **Сам редактор**: его память, время и стабильность.

## Атакующий

Автор файла модели (`.gltf/.glb/.obj/.fbx` и `.bin/.mtl`/текстуры рядом). Модель может прийти из интернета, от агента или из чужого проекта. Считаем, что модель может эксплуатировать ошибку в парсере (Assimp) и выполнить произвольный код в процессе, который её разбирает.

## Границы

1. **Процесс** (#647, сделано): модель разбирает `snk_model_decoder` в своей временной папке (0700), с лимитом памяти (`RLIMIT_AS` / Job) и временем (kill по дедлайну), без core dump, без наследования окружения. Падение, зависание или съеденная память стоят только неудавшегося импорта. Ответ ребёнка редактор проверяет (`accept_scan_answer`, `accept_import_answer`) до того, как что-либо сохранить.
2. **Брокер файлов** (#1043, PR 1): ребёнок не открывает ни одного файла, кроме своей папки запуска. Редактор сам находит, читает и хэширует каждый побочный файл по правилу `model_file_access` (папка модели или content root, без скрытых имён, без выхода через `..` и ссылки, только `.bin`/`.mtl`/картинки, лимиты по числу и байтам) и передаёт байты в бандле запроса. Скан (`broker_scan`) — до 3 раундов с общим бюджетом и одним дедлайном на весь скан, включая чтения редактора (после дедлайна новый раунд не запускается и файл не читается); повторный запрос того же имени в следующем раунде пропускается (не ошибка). В ответе — до 256 имён, у одного файла — не больше 8 имён, байты каждого файла идут одним блобом, сколько бы имён на него ни указывало. Импорт получает ровно показанный человеку список, перечитанный и сверенный по идентичности и SHA-256.
3. **Песочница ОС** (#1043 PR 2 — Linux, сделано; #1054 — Windows, ещё нет; macOS — нет): ребёнок сам отнимает у себя файловую систему, сеть и лишние системные вызовы на уровне ядра, до того как прочитать запрос. Подробно — ниже, «Песочница Linux».

## Песочница Linux (#1043, PR 2)

`tools/model_decoder/decoder_sandbox.cpp`, `decoder_sandbox::apply`, сразу после `harden_process` (no_new_privs, без core dump, PDEATHSIG) и до чтения бандла запроса:

1. Закрываются все дескрипторы, кроме 0, 1, 2 (`close_range`, иначе цикл до `RLIMIT_NOFILE`).
2. `RLIMIT_FSIZE` = самый большой ответ, который редактор прочитает (`--max-output-bytes`, `largest_bundle_bytes` от `answer_limits`): ни один файл ребёнка не больше; превышение — SIGXFSZ.
3. **Landlock** (ABI берётся у ядра): обрабатываются все права ФС, которые знает ABI (ABI 1 — чтение, запись, каталоги, создание/удаление, спецфайлы, ссылки, исполнение; ABI 2 — REFER; ABI 3 — TRUNCATE; ABI 5 — IOCTL_DEV). Одно правило: папка запуска (cwd) — всё, кроме EXECUTE. Значит, вне папки запуска нельзя открыть, создать, удалить, переименовать, обрезать (с ABI 3) ни одного файла, а исполнить нельзя ничего, в том числе в своей папке. ABI ≥ 4: TCP bind/connect обрабатываются без правил — никакого TCP. ABI ≥ 6: scoped — абстрактные unix-сокеты и сигналы только внутри своего домена. `/proc` после этого тоже закрыт (часовой пояс читается до песочницы).
4. **seccomp-bpf, список разрешённого**; всё прочее — `EPERM`. Чужая архитектура (`AUDIT_ARCH` не x86_64/aarch64) и x32-вызовы — kill процесса. Разрешено то, что нужно пути декодирования: чтение/запись, `openat`, stat-семейство, `getdents64`, `mkdir/unlink/rename` (*at и старые x86_64), `readlink` (libstdc++ `fs::canonical` → glibc `realpath` вызывает его на каждой части пути), память, futex, сигналы себе, время, `getrandom`, epoll/eventfd/timerfd (boost::asio io-потоки системы ресурсов), `clone` только с флагами потока (CLONE_VM|FS|FILES|SIGHAND|THREAD, без namespace-флагов, ptrace, vfork), `clone3` → `ENOSYS` (glibc откатывается на `clone`), `tgkill`/`tkill` только себе (`abort`). Закрыто: сокеты, `connect`/`bind`, `execve(at)`, fork/vfork/новый процесс, `ptrace`, `process_vm_*`, `bpf`, `io_uring_*`, `ioctl`, `truncate`, chmod/chown, `utimensat`, xattr, `kill`, SysV/POSIX IPC, keyctl, `pidfd_*`, `perf_event_open`, `userfaultfd`, `unshare`/`setns`/`mount`, `open_by_handle_at`, `personality`, `prctl` (после установки).
   `fcntl` — только команды над своими дескрипторами и блокировками (`F_DUPFD[_CLOEXEC]`, `F_GETFD/SETFD`, `F_GETFL`, `F_SETFL` без `O_ASYNC`, `F_[OFD_]GETLK/SETLK/SETLKW`): `F_SETOWN`/`F_SETSIG`/`O_ASYNC`/`F_NOTIFY`/аренды заставили бы ядро слать сигнал другому процессу (редактору). Фильтр ставится с `SECCOMP_FILTER_FLAG_TSYNC`.
5. Окружение ребёнка — `TMPDIR=<папка запуска>`.
6. Перед Landlock ребёнок проверяет, что у него один поток (`/proc/self/status`): `landlock_restrict_self` ограничивает только вызвавший поток. Второй поток (или нечитаемый `/proc`) — сбой настройки, код 4 (кроме `off`; в сборках с санитайзерами проверки нет — у TSan свой поток).
7. Сразу после настройки, **до чтения запроса**, ребёнок пишет первой строкой stderr `snk-sandbox-status: fs=landlock|none syscalls=seccomp|none[ why=...]`. Редактор берёт состояние изоляции только из первой строки (`sandbox_status_reader`); всё, что ребёнок пишет после разбора, может исходить от модели и не учитывается. В ответе (`manifest`) поля `sandbox` больше нет.

**Что остаётся открытым.** Landlock не ограничивает stat и readlink: ребёнок может узнать, существует ли путь вне своей папки, его размер, время и цель ссылки (не содержимое). Чтение того, что ребёнку передали (байты модели и побочных файлов), и запись в свою папку — по определению. Время и память — лимиты из #647. Ответ по-прежнему проверяет редактор.

**Исполняемая память.** `mmap` и `mprotect` разрешены без проверки аргументов, `PROT_EXEC` тоже: код, внедрённый через ошибку парсера, может создать и выполнить новый машинный код в своём процессе. Принято: он остаётся под той же песочницей — без exec, сети, сигналов редактору, файлов вне папки запуска. Фильтр мог бы проверять аргумент `prot` у `mmap`/`mprotect`. Сейчас он этого не делает. Пути декодирования `PROT_EXEC` после настройки не нужен, но glibc может подгрузить модуль через `dlopen` (iconv, nss), поэтому такой запрет надо сначала проверить на всех путях.

**Исчерпание процессов.** `clone` разрешён для потоков без счёта, а потоки входят в лимит процессов пользователя: модель может плодить потоки до срока декодера (#647), и тогда `fork` перестаёт работать у всех процессов пользователя, в том числе у редактора. Сейчас это ограничено только сроком и лимитом памяти (стек каждого потока). `RLIMIT_NPROC` не годится — он считает все процессы пользователя. Варианты — #1105.

**Проверено тестами** (`tests/edt_decode_runner_tests.cpp`, #1082). Изнутри ребёнка отказаны: открытие и запись вне папки запуска, `truncate` (Landlock с ABI 3 или фильтр) и `chmod` (только фильтр) файла вне папки, TCP, `execve`, `io_uring_setup`, `ptrace`, `fork`, сигналы редактору. У каждой пробы есть контрольный запуск, который должен пройти, иначе тест падает: тот же вызов под `--sandbox off` (для записи — запись в свою папку). Так видно, что проба работает и отказывает именно песочница. Исключение одно: `io_uring`, которому система отказывает и без песочницы (sysctl, профиль контейнера), — тогда сообщение вместо проверки.

**Режимы** (`--sandbox off|best_effort|required`, решение владельца). `off` — только закрытие унаследованных дескрипторов, no_new_privs и `RLIMIT_FSIZE`, без Landlock и seccomp. Политику проверяет сам ребёнок до чтения запроса — его отчёту после компрометации верить нельзя:
- механизма **нет** (Landlock: ENOSYS/EOPNOTSUPP/EPERM от проверки ABI или ABI < 1; seccomp: `PR_GET_SECCOMP` → EINVAL; не Linux): `required` — выход с кодом 4 и одной строкой причины в stderr, редактор проваливает импорт/загрузку с текстом «the model decoder cannot run in its sandbox: <причина>»; `best_effort` — работа без него, строка состояния говорит `fs=none`/`syscalls=none` с причиной, редактор пишет один WARN за запуск (без Landlock — «может читать и писать любые файлы пользователя»: seccomp файлы не защищает);
- механизм **есть, но настройка не удалась** (любой вызов landlock_*/seccomp после успешной проверки ABI, no_new_privs, RLIMIT_FSIZE): код 4 в `best_effort` и `required` (no_new_privs и RLIMIT_FSIZE — и в `off`), ребёнок никогда не продолжает. Вне `required` это дефект, а не отсутствие изоляции: редактор добавляет к ошибке, что изоляцию можно выключить в `import/decoder_sandbox` (решение лида).

Режим задаёт одна настройка, которую меняет только человек: cfg `import/decoder_sandbox` — `on` (по умолчанию, = `best_effort`), `off`, `required` (для CI и тестов); иное значение — `on` с WARN. Она действует на любой импорт: человека, модели уровня (`res://`) и агента; `import_source::sandbox` может только повысить режим, импорт агента его не трогает. Решение владельца: импорт никогда не отказывает из-за отсутствия изоляции — при `on` без Landlock/seccomp (старое ядро, политика, Windows/macOS до #1054) декодер работает без неё с WARN в лог; видимое предупреждение — #1076: одна строка уровня warning в Problems (источник `decoder`, худший статус за запуск, при `off` — сразу при старте), пометка в обоих вопросах агенту и поле `decoder_sandbox` в результате его job (не скрывается). Агент настройку не меняет: она читается один раз при старте из cfg-файла или `--set`, ни одна доступная агенту команда не пишет cfg, ни один доступный ему путь записи не ведёт к cfg-файлу, а `vcs.checkout`/`vcs.pull` агента, меняющие файл конфигурации редактора (`--config`, иначе `config/editor.cfg` рядом с exe), отклоняются так же, как для файла политики агента. Статус уходит в Problems до проверки ответа: упавший, остановленный по времени или вернувший мусор запуск тоже учитывается; ребёнок, не написавший первой строкой статус, считается работающим без изоляции. Граница не держится, если агент сам запускает процесс редактора (`--mcp-stdio`) с `--set import/decoder_sandbox off`: такой агент и так запускает что угодно от имени пользователя (в том числе разбор модели без всякого декодера); это принято (решение владельца), а поле `decoder_sandbox` в ответе всё равно говорит об отсутствии изоляции. При `off` изоляции нет, риск на человеке. Код 4 — только `required` без механизма или сбой настройки имеющегося механизма (см. выше).

**Сборки с санитайзерами** (тестовые, не поставляются): seccomp не ставится (рантайм санитайзера делает вызовы, которых нет в списке) — `syscalls=none`, и `required` там выполняется одним Landlock. Проверки «один поток» тоже нет — у TSan свой поток. Это допустимо, пока такие сборки не выпускаются. Landlock ставится; проверка утечек LSan выполняется до него (она читает `/proc`) и на выходе больше не запускается.

## Что брокер ловит

- Честный, но враждебный файл модели, который ссылается на `../../.ssh/id_rsa`, абсолютный путь, скрытую папку или ссылку наружу: редактор отказывает по правилу, байты в ребёнка не попадают. Имя сначала проверяется лексически, до любого обращения к ФС: UNC (`//host`, `\\host`), `\\?\`, `\\.\`, потоки (`x.mtl:stream`) и любое `:`, кроме двоеточия диска, — отказ; абсолютный путь допускается только у побочного файла и только лексически внутри папки модели / content root.
- FIFO или устройство вместо файла: `resolve` только делает stat, открывает файл `read_beneath` (без блокировки и ссылок), так что скан на нём не зависает.
- Подмену файла между сканом и импортом: импорт перечитывает файл и сверяет id и SHA-256.
- Файл, которого не было в списке: на импорте ребёнок его не получает — для него такого файла нет, с диска ничего не читается (`.obj` без своего `.mtl` импортируется с материалом по умолчанию, как раньше). Ребёнок не может отличить «запрещён» от «нет на диске», и байтов это ему не добавляет. Так же редактор отвечает на имя побочного файла, которое запрещает именно правило (`refusal_kind::rule`, с WARN); превышение лимита или файл, которому нельзя доверять, валят скан: парсер сам пробует запасные имена, например `<модель>.mtl` у OBJ; запрещённая текстура по-прежнему валит скан, как и любое имя у модели, которая не файл на диске (#925).
- Чтение по пути, где папка или файл подменены на ссылку после проверки: редактор читает через `platform::beneath::read_beneath` (без следования ссылкам).

## Что брокер НЕ ловит

- **Скомпрометированный парсер без песочницы ОС**: если модель выполнила код в ребёнке, а песочницы нет (Windows до #1054, macOS, Linux без Landlock/seccomp в режиме `best_effort`), у этого кода права пользователя — он может сам открыть любой файл и сходить в сеть. Брокер убирает только *легальный* путь чтения; от эксплойта защищает песочница ОС (Linux — см. выше).
- **Утечку разрешённых файлов**: ребёнок получает байты каждого файла, прошедшего правило, и может унести их в выходной бандл. Картинки проверяются по сигнатуре, но у `.bin`/`.mtl` сигнатуры нет — их содержимое может оказаться в ресурсах импорта. Правило ограничивает, *какие* файлы читаются (папка модели), а не что с ними делает парсер.
- **Ресурсы (CPU/память) внутри лимитов**: модель может потратить весь дедлайн и всю память, отведённые декодеру.
- **Содержимое ответа сверх проверок**: `accept_import_answer` проверяет имена, типы, ссылки и размеры ресурсов, но не «правильность» геометрии или текстур.

## Остаточный риск и следующие шаги

- Linux: stat/readlink вне папки запуска остаются возможны (см. «Что остаётся открытым»); отметка в панели Problems и в вопросе агенту о работе без песочницы — следующий шаг.
- #1054: AppContainer / restricted token для Windows.
- Сообщения с именами из ребёнка проходят `text_escape::escaped_text` (≤ 256 байт) — подделать строку лога или вопроса человеку нельзя.
- Ссылка (symlink, junction) внутри папки модели не читается: тип проверяется без следования ссылкам, а `read_beneath` открывает каждый компонент пути без них. Такой файл валит скан как «не обычный файл», даже если указывает внутрь папки.
