# Архитектурное ревью движка перед работами по ТЗ «Химера»

**Статус:** решения приняты владельцем (§9); выполняется Фаза 0, этап A
**Ревизия кода:** `aibranch` @ `80d4e86` (после EPIC-49)
**Связанные документы:** [CHIMERA_ROADMAP.md](CHIMERA_ROADMAP.md) — разрывы с ТЗ и вехи

> **Ревизия 2.** Владелец ответил на вопросы §8 — решения зафиксированы в **§9** и имеют приоритет над рекомендациями §3.4, §3.5 и §4 там, где они расходятся: GLFW остаётся, SDL_GPU не используется, шейдеры остаются на GLSL с правилами переносимости, явные фазы ECS — по схеме §9.4.

Цель документа — до начала работ по ТЗ оценить каждое принятое архитектурное решение, найти легаси и решить, что переделать сейчас, пока это дёшево. Ориентир — исходный замысел: **мультиплатформенный движок без привязки к ОС и графическому API**.

Легенда вердиктов: **оставить** · **доработать** (эволюционно, без смены идеи) · **переделать** (идея неверна или блокирует цели). Стоимость: S ≈ дни, M ≈ 1–3 недели, L ≈ месяц и больше; «сейчас → потом» показывает, как растёт цена при откладывании.

## 1. Итог в одном абзаце

Каркас правильный, и его стоит сохранить: слои common → core → engine → editor, desc как источник правды, модули с `depends_on`, конвейер ресурсов resolver → adapter → cache, data-driven рендер extract → packet → pass, реестр стадий кадра. Проблемы сидят уровнем ниже, в нескольких решениях, которые **противоречат мультиплатформенности и будущей модели «игра как модуль»**:
1. Интерфейс графического драйвера повторяет OpenGL, хотя GL-заголовки за него не выходят.
2. Шейдеры — GLSL, который компилируется во время работы.
3. Окно срослось с GL-контекстом.
4. Синглтоны и счётчик type-id ломаются на границе DLL.
5. Идентичность построена на именах и путях.
6. Планировщик ECS держится на неявном выводе зависимостей; в нём два бага корректности.
7. У desc нет схемы и версий.

Часть этого переделывается за дни (ассерты, ключи сервисов, ID узлов, баги планировщика), часть — за недели (RHI, `world_context`, схема desc). Всё это дешевле сделать **до** того, как появятся игровой код и контент Химеры.

## 3. Оценка по подсистемам

### 3.1 Сборка и слои

**Хорошо.** EPIC-49 сделал главное:
- слои зафиксированы в CMake;
- зонтичные таргеты стали `PRIVATE`, наружу торчат только `core_api` / `engine_api`;
- тяжёлые заголовки изолированы;
- нарушения слоёв window→gui и scene→gui устранены.

На это можно опираться.

**Плохо:**
- **Нет подготовки к shared library.** Нет `POSITION_INDEPENDENT_CODE`, `CXX_VISIBILITY_PRESET hidden`, `generate_export_header`, `install(EXPORT)`. `BUILD_SHARED_LIBS` принудительно выключен (`cmake/ThirdParty.cmake:12`). Чем больше кода написано без `SNK_API`, тем дороже переход.
- **Плоские заголовки без префикса** (`#include "res_system.h"`). При установке SDK они столкнутся с заголовками пользователя.
- **Абсолютные пути вшиты при компиляции.** `RESOURCE_PATH` (PUBLIC, `core/core/resource/CMakeLists.txt:12`) и `PROJECT_SOURCE_PATH` (`drv_opengl`) несовместимы с установленным редактором.
- **Остаточные нарушения слоёв.** `resource_system` (core) линкует `snk::image` (engine) и assimp. `window` линкует `drv_opengl` (см. 3.4).
- **Каждая поддиректория вызывает `project()`** (~24 раза). Third-party подключается через `add_subdirectory` в разных компонентах, поэтому невозможно `find_package`-потребление и переключение на системные зависимости.

**Рекомендация (M):**
- Глобально включить PIC и hidden visibility.
- Добавить заголовок `snk_export.h` с `SNK_API`; пока сборка статическая, макрос пустой.
- Опция `SNK_ENGINE_SHARED`: один `snk_engine` SHARED, внутри которого core+engine. Все stateful-синглтоны и аллокаторы живут только в нём.
- Перенести заголовки в `include/snk/<component>/` — это и есть отложенный «физический public/ split» из US-49-1.
- Убрать абсолютные дефайны.
- Собрать всё third-party в `ThirdParty.cmake` с переключателем `SNK_USE_SYSTEM_DEPS` (find_package / vcpkg).
- Пиннить Boost через SHA256.

### 3.2 Приложение: модули, сервисы, синглтоны, цикл кадра

**Модули — доработать.** Топосорт по `depends_on` корректный (`app_module_loader.hpp:97-158`). Недостатки:
- у модуля нет состояния, нельзя загрузить или выгрузить один модуль (а это нужно для DLL игры);
- фазы возвращают `void`, поэтому нет отказа и отката (BL-004);
- enum `MODULE_PRIORITY` избыточен рядом с зависимостями;
- инверсия: `engine_module` инициализирует loop service, который регистрирует редактор (`engine_module.cpp:23`), так что без редактора движок не поднимается.

Рекомендация:
- `load(module)` / `unload(name)` с состоянием;
- фазы возвращают результат, при отказе откат в обратном порядке;
- `loop.init()` перенести в `application::run`;
- C-точка входа `snk_module_api_version()` / `snk_create_module()`;
- убрать `MODULE_PRIORITY`.

**Service locator — доработать, критично для DLL:**
- **Ключ типа ломается на границе модулей.** `ds_type_id.hpp:13-33` выдаёт id из function-static счётчика: каждый бинарник нумерует типы в своём порядке, и DLL игры получит чужой слот.
- `require()` в release разыменовывает nullptr (`ds_store.hpp:129-133`).
- Хранилище — `unordered_map`, поэтому порядок разрушения сервисов случайный.
- Политики хранения и parent-scoping почти не используются.
- `frame_context` использует `app_data_storage` как покадровый blackboard: heap + `any` + хеш-узел на каждый кадр.

Рекомендация (S, ~2 заголовка):
- стабильный ключ (`entt::type_hash<T>` или явный `service_id`);
- проверка в release;
- разрушение в порядке, обратном регистрации;
- убрать policy-шаблон;
- parent-scoping дать реальную работу (дочернее хранилище Play-сессии);
- `frame_context` — типизированные поля вместо storage.

**Синглтоны — переделать:**
- Найдено 12 видов глобального состояния. Среди них `res::get_system`, `rnd::get_system`, `gui::get_system`, `gs::get_system`, `cfg::instance`, глобальный `skin_manager`, `gMaxTexture2DSize`, `g_gpu_profiler`, реестр spdlog, thread-local frame allocator, счётчик type-id.
- Живых вызовов `get_system()` около 18, из них 11 в `scn_model_importer_adapter.cpp`.
- При статической линковке в несколько DLL каждая получит свои копии.
- Сам `CLAUDE.md` предписывает `res::get_system()`, и паттерн расползается.

Рекомендация:
- удалить мёртвые (`gs`, `skin_manager`, `gMaxTexture2DSize`);
- `resource_system&` внедрять в ассемблер и адаптеры;
- оставшееся (config, spdlog, frame allocator, profiler) — строго в одном shared-бинарнике;
- исправить правило в `CLAUDE.md`.

**`game_system` — удалить.** Класс ничего не делает. Регистрации несимметричны: 17 desc-типов регистрируются, а снимаются 10; из 14 спавнеров снимаются 13. Для DLL игры, которые выгружаются, это недопустимо. Рекомендация:
- `scn::register_scene_types(...)` возвращает RAII `registration_scope`, который снимает регистрации автоматически;
- EPIC-29 переформулировать: US-29-2 (массовый ренейм в `_service`) убрать как шум и добавить требования DLL.

**Цикл кадра — доработать.**
- Концепция реестра стадий правильная.
- Ключи порядка — магические числа (10/20/25/28/…), стадии каждый кадр ищут сервисы через `require<>`.
- `gs_loop_service` нигде не создаётся, путь без редактора мёртв; `frame_allocator_reset` вызывает только редактор (BL-005).

Рекомендация:
- именованные фазы (`begin, input, update, post_update, extract, render, ui, present`) плюс sub-order;
- реестр как сервис, куда модули добавляют стадии;
- сброс аллокатора в стадии `begin`;
- один класс `loop_service`;
- исполняемый `player`, чтобы этот путь компилировался и запускался постоянно.

### 3.3 Инфраструктура: ассерты, ошибки, логи, память

**Ассерты — переделать, критично.**
- `engine_assert.h` завязан на `_DEBUG`, а это макрос MSVC-рантайма; CMake его не задаёт.
- Значит, **на Linux/GCC/Clang ассерты выключены всегда, даже в Debug** — шире, чем описано в BL-002. Мультиплатформенная разработка сейчас идёт без страховки.
- Release-вариант принимает ровно 2 аргумента, debug — variadic, поэтому код с лишними аргументами собирается только в одной конфигурации.
- Условие в release не вычисляется, побочные эффекты пропадают.

Рекомендация (S):
- гейт по `NDEBUG` или опции `SNK_ASSERTS`;
- `ENGINE_VERIFY` всегда вычисляет условие, логирует и деградирует (BL-002).

**Политика ошибок (нужно зафиксировать):**
- исключения допустимы при старте и в I/O; ловятся на границе модуля и в `main` (BL-004);
- на покадровом пути исключений нет;
- контракт выражается через VERIFY плюс `bool` / `optional` / свой `result<T>` (в C++20 нет `std::expected`).

**Логгер — оставить.** Мелочь: макросы делают `std::format` до проверки уровня.

**Профайлер — доработать.**
- `eng_profiler.cpp` собирается в `core` условно, `unit_tests` подключает его вручную.
- Режим `TRACY` объявлен, но не подключён.

**Аллокаторы — доработать.**
- **Баг:** при переполнении 2 MB `linear_resource` уходит в upstream (`mem_linear_allocator.cpp:50-53`), но `deallocate` — no-op, а `reset()` только обнуляет offset. Overflow-память **утекает навсегда**.
- pool и stack используются только в тестах.

Рекомендация:
- цепочка блоков или учёт upstream-блоков с освобождением в `reset`;
- лог high-water mark;
- неиспользуемые ресурсы пометить или удалить.

### 3.4 Платформа и окно

**Решение:** GLFW используется напрямую. `wnd::window` и `wnd::context` отдают наружу `GLFWwindow*`, в том числе через неявное преобразование (`wnd_window.h:35-41`). GL-контекст создаётся и принадлежит `window_system`: GL-hints в `wnd_window_system.cpp:124-133`, таргет window линкует `drv_opengl` и glad, а рендер получает драйвер от окна.

**Вердикт: переделать (малый объём, ~600 строк).** Это прямое противоречие независимости от графического API: окно не должно знать про GL.

Есть и другие пробелы:
- нет событий ввода текста, геймпада, touch, повтора клавиш;
- DPI читается один раз и только для шрифта ImGui;
- resize берёт window size вместо framebuffer size (на Retina и Wayland это неверно);
- `core_thread_utils.hpp` содержит ветки только Win32/Linux;
- в `Editor/main.cpp` ветка `WinMain` без `_WIN32`-гарда;
- `layout_settings.ini` пишется в CWD.

**Рекомендация.** Принять решение **GLFW vs SDL3** сейчас, пока слой маленький:
- `platform::window` отдаёт native handle, framebuffer size, content scale и события;
- создание контекста и swapchain переезжает в драйвер: `create_swapchain(native_window)`.

~~Моя рекомендация — SDL3.~~ **Пересмотрено (§9.2):** GLFW остаётся. Проблема не в библиотеке, а в том, что она торчит наружу и окно владеет GL-контекстом.

### 3.5 Графический API и рендер

**Хорошо:**
- GL-заголовки действительно не выходят за `drv_opengl`, window и GUI-бэкенд.
- Схема extract → packet → pass правильная.
- `frame_context`-инъекция и POD-материалы (EPIC-49) — шаг в нужную сторону.

**Плохо: сама абстракция повторяет OpenGL.** Vulkan, D3D12 или Metal не смогут её реализовать:
- стек FBO `push/pop_frame_buffer` + `set_render_target`; GL-реализация создаёт и удаляет FBO на каждый пасс и кадр (`rnd_gl_driver.cpp:266-287`); нет render pass begin/end и load/store;
- texture units (`bind(position)`), `set_activate_texture`;
- uniform по имени с `glGetUniformLocation` на каждый вызов;
- VAO bind/unbind; инстансинг включается неявно, если есть атрибут MAT4;
- binding points UBO/SSBO зашиты при создании (слоты 0/1/2) и должны совпадать с `layout(binding=)` в GLSL;
- топологии FAN / LOOP / ADJ; `TEXTURE_USAGE` — одно значение вместо флагов (RT, который потом сэмплится, работает только потому, что GL игнорирует usage);
- нет PSO, descriptor/bind-group, command list, swapchain/present;
- ресурсы — сырые `texture_interface*` в пакетах; resize удаляет RT, и в пакетах того же кадра остаются висячие указатели;
- соглашения GL зашиты везде: клип-глубина −1..1, origin снизу слева (картинки флипаются глобально при загрузке, UV — в редакторе);
- **macOS невозможна в принципе**: бэкенд требует GL 4.5 + DSA, а macOS останавливается на 4.1.

**Шейдеры:**
- сырой GLSL разных версий (330 / 420 / 460), свободные non-block uniforms (Vulkan-GLSL их отвергает);
- текстовый `#include`;
- варианты через вставку `#define`; хеш варианта XOR-ит только значения, без имён;
- компиляция ленивая и синхронная прямо в кадре; число направленных источников света вшито в вариант, поэтому каждый новый счёт даёт фриз;
- пути в SPIR-V / MSL / HLSL нет.

**Пакеты не самодостаточны.**
- `draw_call_t` несёт тяжёлый `shader_config` (строки, map'ы), сырые указатели на GPU-объекты и на память ECS (`bone_matrices`).
- Extract вызывает `require_texture` и может создавать GPU-объекты.
- Материал перекомпилируется на каждый draw, камеру и кадр (это то, что измеряет EPIC-45).
- `configure_pass` всё ещё ходит в `rnd::get_system()`.

**Нет пути на экран без ImGui.** Отсутствует present-пасс, поэтому standalone-плеер ничего не покажет. Нет ортографической камеры, спрайтов и 2D, которые нужны карточной игре.

**Вердикт: RHI переделать эволюционно (M сейчас, L потом — каждый новый 2D/UI/post-пасс добавит GL-стиль).** По шагам:
1. `begin_render_pass(desc{attachments, load/store, clear})` / `end`; GL-реализация кеширует FBO по набору attachments. Текстурам — usage-**флаги**.
2. Неизменяемый `pipeline_desc` (шейдеры + vertex layout + состояние) → handle пайплайна.
3. Привязка ресурсов через bind-group с явными set/slot; per-draw данные — через UBO / push-constant блок.
4. Типизированные handle (`texture_handle{u32}`) вместо сырых указателей.
5. Шейдеры: правило «только блоки» сразу. Затем исходник на **Slang** (или HLSL) с компиляцией при импорте в SPIR-V / GLSL / MSL. Кеш вариантов по стабильному ключу, прекомпиляция известных перестановок, число источников света — uniform.
6. Пакеты — только POD: id материала-инстанса, id геометрии, трансформ, sort key, offset костей в кадровом буфере. Материал компилируется при изменении, а не каждый кадр (EPIC-45).
7. Небольшой декларативный frame graph: пассы объявляют чтение и запись RT, RT ресайзятся централизованно, финальный `present`. Плюс 2D-пасс со спрайтами и ортокамерой.

**Стратегия бэкендов — решено (§9.1, §9.3): только свои бэкенды, SDL_GPU не используется.** Исходный текст: После шагов 1–4 интерфейс совпадает с современными API. Дальше два пути:
- **(a)** GL 4.5 остаётся первым бэкендом, вторым идёт **SDL_GPU**: Vulkan / Metal / D3D12 одним бэкендом, шейдеры через SDL_shadercross или Slang;
- **(b)** свои Vulkan- и Metal-бэкенды.

Для маленькой команды рекомендую (a). Обёртки уровня bgfx или Diligent тоже совместимы с этим RHI, но тянут свои модели ресурсов.

**ImGui-бэкенд — доработать.**
- Сейчас GLFW + GL3 слиты в один класс, а `get_imgui_texture_from_texture` кастует к `gl::texture`.
- Разделить на платформенную и рендерную половины, выбираемые RHI; `ImTextureID` брать из RHI-handle.
- ImGui оставить только для редактора; игровой UI строить на 2D / text-пассе.

### 3.6 ECS и рантайм сцены

**EnTT как хранилище — оставить.**

**Планирование через `entt::organizer` — переделать, критично.** Порядок выводится из типов аргументов. Детерминизм — жёсткое требование (RUN03), а подход уже дал:
- **двойной запуск**: `run_graph_recursive` обходит граф DFS без visited-set, узел с N предшественниками исполняется N раз и может запуститься раньше второго предшественника;
- мёртвый fixed-граф: `m_fixed_organizer` никогда не заполняется, `fixed_time` / `update_alpha` пишутся, но не читаются;
- случайную сериализацию: `const T&` регистрируется как запись, потому что `salted_type<const T,W>` не const.

Систем сейчас около 9, тестов на планирование нет — идеальный момент для замены. Рекомендация (S):
- явные фазы (`input, pre_update, fixed, update, post_update, transform, late`);
- в каждой фазе упорядоченный список в порядке desc плюс опциональные `after:`, отсортированные Kahn один раз;
- юнит-тесты: «ромб», reload одного мира, загрузка двух уровней подряд.

**Много миров в одном level + «соление» — переделать.**
- Соление существует только ради одного общего organizer.
- Межмировой `bind_res<ID,…>` в продакшене не используется, кроме `level_res<const delta_time>`.
- Цена: compile-time лимит 5 миров; XOR-соль на 32-битных хешах (`LEVEL_ID` даёт `0xFFFF0000`, коллизии возможны); `std::function` на каждый вызов системы.
- Нарушена изоляция: превью префаба делит organizer, hot reload и ввод со сценой.

Рекомендация (M): **`world_context`** = один `entt::registry` + свои фазы + время (dt, fixed accumulator) + источник ввода + command buffer + флаг hot reload. Системы получают контекст, а не id. Соль, `registration_dispatcher` и `runtime_context_provider` исчезают. Сцена редактора, превью префаба, превью ассета, Play и плеер — отдельные контексты; `level_manager` превращается в `context_manager`.

**`invoker` — доработать.**
- Внедрение view и ресурсов удобное, его оставить.
- Вывод зависимостей из типов убрать вместе с фазами.
- Отсутствующий ресурс сейчас молча default-конструируется (`ecs_invoker.hpp:100`): запрос `const delta_time&` вернёт мировой 0. Должно быть ASSERT / VERIFY с opt-in `optional<T>`.
- Резолвер аргументов строить один раз при регистрации.

**Level / level_manager — переделать эволюционно.** Найдены баги:
- `level::clear()` не чистит `m_organizer`: второй загруженный уровень наследует системы первого;
- конструктор кладёт в ctx лямбду с захватом `this`, а `level` объявлен movable и имеет `swap` — после move указатель висит;
- `create_system` возвращает `shared_ptr`, который выбрасывается; stateful-системы in-place живут по висячему указателю (пока затронут только тестовый exe).

Миры хранятся в `unordered_map`, поэтому порядок обхода — порядок хеша.

**Полная пересборка на каждую правку — доработать.**
- Desc как источник правды оставить: он идеален для сохранения, Apply/Revert и Undo.
- Инфраструктура patch (`desc_patcher_fn`) есть, но все 14 спавнеров передают null.
- Нужно: стабильный id узла → карта `node_id → entity` в контексте → команда меняет desc и патчит только затронутую сущность. Полная пересборка остаётся fallback для структурных изменений.

**Hot reload — доработать.**
- Подключать per-context: включён в редакторе, выключен в Play и плеере.
- Тикать из стадии кадра, а не из `level::sync_point`.
- Пропускать через тот же patch-путь.

**Command buffers.** `entity_changer` / `entity_spawner` в продакшене никто не пишет, порядок применения недетерминирован (`unordered_map`). Нужен один простой упорядоченный буфер на контекст, применяемый в конце фазы.

### 3.7 Desc-модель и префабы

**Desc как данные + `__parent` — идея верная, реализация — переделать эволюционно (критично).**
- **Каждый тип вручную пишет три функции.** `copy_to` — это `static_cast`, поэтому чужой тип даёт UB. Enum'ы конвертируются вручную синхронизированными таблицами строк.
- **Нет метаданных полей.** `desc_hints.hpp` не используется. Из-за этого невозможны генерический инспектор, пометки «наследуется / переопределено», минимальный diff при сохранении и cooking.
- **Наследование `__parent` грубое.** Это `copy_to` целого объекта плюс deserialize поверх, без маски переопределений.
- **Inline sub-desc пишутся на диск** как `memory://overrides/…`, с `std::hash` в имени. Этот хеш нестабилен между платформами и STL.
- **Нет `__version`.** Неизвестный `__type` даёт разыменование null.

Рекомендация (M сейчас; каждый новый desc-тип — около 16 сейчас плюс всё будущее Химеры — удорожает переход):
- `DESC_FIELDS(type, FIELD(name, hints…))` → `type_schema`; поверх неё генерические serialize / deserialize / copy / diff / inspector и enum ↔ string;
- миграция существующих desc по одному, виртуальные методы остаются fallback;
- `__version` на тип и реестр миграций в адаптере;
- `__parent` как объявленная зависимость с маской полей.

**Модель префаба — переделать модель данных (критично).**
- **Идентичность — имя узла.** Одинаковые имена соседей схлопываются, переименование выглядит как удаление + добавление. Импортированные модели уже содержат повторяющиеся имена (`ROOT`, `Armature`, `geometry_0`).
- **Трансформ «переопределён», если ≠ 0 / 1**, поэтому вернуть позицию в начало координат через override нельзя.
- **Merge поверхностный.** Компоненты лежат в `unordered_map`, порядок спавна недетерминирован.
- **Hot reload не удаляет** исчезнувшие компоненты.
- **~120 строк дублируются** между assemble и hot reload.
- **`component_tracker`** хранит вторую копию overrides — второй источник правды.

Рекомендация (M сейчас, L — как только карты и сцены Химеры сохранятся с name-based overrides, потому что эти данные придётся мигрировать):
- persistent `node_id` в desc;
- overrides — список `{target_node_id, component, json_pointer, value}` с явным присутствием;
- Apply = перенос в префаб, Revert = удаление записи;
- одна процедура `reconcile(base, overrides, live_map)` вместо двух копий.

**JSON — оставить** как авторский формат. Позже добавить cooked-формат (CBOR / MessagePack / бинарный по схеме) и pak с индексом по GUID; у бинарных блобов должен быть заголовок `{magic, version}`.

### 3.8 Ресурсы, IO, конфиг

**`res::tag` — доработать сейчас, идентичность переделать.**
- `operator==` сравнивает только хеши (`res_tag.h:62`): коллизия молча вернёт чужой ресурс.
- Парсер хрупкий (`find_first_of("://")` ищет любой из символов), путь не нормализуется.
- Путь как идентичность ломает ссылки при переименовании.

Рекомендация:
- сравнение строк и нормализация (S);
- затем `res::asset_id` (GUID) + реестр guid ↔ tag + `res::ref<T>` с сериализацией `{guid, path}`;
- ключ кеша `{id, type}` (EPIC-28).

**Конвейер и VFS — оставить и доработать.** Плохо:
- регистрируется ровно один корень на протокол;
- `memory://` — это папка на диске;
- `resolve_tag` откатывается на путь от CWD;
- `m_resolvers[proto]` создаёт null для неизвестного протокола и разыменовывает его;
- magic-detection объявлено, но пусто;
- ~10 обходов VFS через `get_resources_path()` в редакторе.

Рекомендация:
- mount table из конфига проекта (engine → game → user, read-only / writable);
- RAM-only `memory://`;
- ошибка вместо CWD-fallback;
- удалить `get_resources_path()`, добавить `resolver::to_native_path`.

**Потоки — переделать поэтапно.**
- `then()` вызывается на IO- или worker-потоке под мьютексом; гонки BL-006 подтверждены.
- `wait()` — spin + ASSERT при ошибке, поэтому `require_sync` на отсутствующем файле падает.
- Вложенный `require_sync` внутри адаптеров на единственном worker'е несёт риск дедлока (анализ, не воспроизведено).
- Гонки в кеше: lookup и insert под разными замками; `erase` под shared_lock; `signal_changed`, алиасы и `exists` без замков.
- stb-flip — глобальная настройка.

Рекомендация:
- `core::task_system` (N воркеров, main-thread очередь, прогресс и отмена);
- загрузка поверх него, колбэки по умолчанию на главном потоке;
- `condition_variable` вместо spin; `require_sync` возвращает ошибку;
- адаптеры **объявляют зависимости** вместо вложенных синхронных загрузок — это же даёт граф зависимостей для hot reload и cooking.

**Кеш — доработать.**
- Нет бюджета и eviction.
- `pin_resource` автоматически сериализует на диск: для `.png` пишет **JPEG-байты** в контентные корни.
- File watcher раз в 500 мс полностью сканирует все корни.
- Инвалидация не транзитивна.

Рекомендация:
- `register_runtime(tag, obj)` без записи;
- `size_bytes()` + LRU-уровень с бюджетом;
- обратные зависимости;
- позже — нативные watchers.

**`store()` — доработать.**
- Временное имя через `replace_extension(".tmp")` даёт коллизию: `a.desc` и `a.json` → `a.tmp`.
- Нет проверки записи и flush.
- Ошибка — ASSERT на IO-потоке, а `store()` возвращает true до записи.
- Адаптер импорта моделей пишет файлы во время загрузки — побочный эффект, недопустимый для cooking.

Рекомендация:
- результат через task;
- уникальное tmp-имя, flush, rename (`ReplaceFileW` на Windows);
- явный writable-корень;
- записи импорта перенести в задачу редактора.

**Конфиг — доработать (S).**
- `-c` привязан и к `help`, и к `config`.
- Неизвестные ключи и дубликаты молча игнорируются.
- `std::cout` в help.
- Нет записи пользовательских настроек и проектного конфига.

## 4. Мультиплатформенность и независимость от API: честная оценка

| Ось | Сейчас | Что мешает | Целевое решение |
|---|---|---|---|
| ОС | Фактически только Windows (MSVC) | Ассерты мертвы на GCC/Clang; `WinMain`-ветка без гарда; `core_thread_utils` без Apple; CWD-пути (логи, ini); `system("pause")` в `image_test` | CI на MSVC + Clang/Linux (BL-003); платформенный слой; все пути через VFS / платформенные каталоги |
| Окно и ввод | GLFW напрямую | `GLFWwindow*` в API, окно владеет GL-контекстом, нет текста/IME/геймпада/DPI-событий | `platform::window` поверх GLFW (решение §9.2) |
| Графический API | Только OpenGL 4.5 | GL-образный RHI, GLSL в рантайме, GL-соглашения (глубина, origin), сырые указатели | RHI с render pass / pipeline / bind group / handle; GLSL с правилами переносимости (§9.4); новые API — только собственными бэкендами (§9.1) |
| macOS | Невозможна | GL 4.5 + DSA (macOS ≤ 4.1) | Вне текущих целей; при необходимости — собственный Metal-бэкенд после редизайна RHI |
| Модульность (DLL игры) | Невозможна | Счётчик type-id, синглтоны в статических либах, нет export / PIC / visibility, несимметричные регистрации | Стабильные ключи, `snk_engine` SHARED, RAII-регистрации, C-точка входа |

Вывод: независимость от API **заложена на уровне заголовков, но не на уровне модели**. Чем больше пассов и шейдеров будет написано под текущий интерфейс (а игровой UI и 2D добавят их), тем дороже редизайн. Поэтому шаги 1–4 из 3.5 стоит сделать до UI-работ по ТЗ.

## 9. Принятые решения (ответы владельца, ревизия 2)

**Статус: приняты владельцем (2026-10-17).** Рекомендации §2–§7 действуют с поправками этого раздела. План расчистки §7 утверждён; выполнение начато с этапа A.

### 9.1 Платформа и графический API
**Решение:** целевая платформа сейчас — Windows + OpenGL. Требование к архитектуре: **добавление нового графического API = написание нового бэкенда**, без правок рендера, пассов, редактора и игрового кода.

Следствия:
- Шаги RHI 1–4 из §3.5 обязательны: render pass descriptors, `pipeline_desc`, bind groups, typed handles, usage-флаги. Без них новый бэкенд не написать, не трогая пассы.
- Критерий готовности RHI: ни один файл вне `drv_*` не знает о GL-понятиях. Это касается texture units, uniform по имени, FBO, VAO, GL-соглашений глубины и origin. Соглашения нормализуются в бэкенде: глубина 0..1 в движке, origin сверху слева, GL-бэкенд конвертирует.
- Проверка без второго бэкенда: **null/validation-бэкенд**. Он реализует интерфейс без GPU, проверяет корректность вызовов (порядок begin/end, совместимость pipeline и attachments, привязки) и запускается в юнит-тестах. Это дешёвое доказательство API-независимости.

### 9.2 Оконная библиотека: GLFW остаётся
Реальные плюсы SDL3 для текущих целей оказались малы. Всё нужное уже есть в GLFW 3.3+:
- `glfwSetCharCallback` — ввод текста в Unicode, достаточно для кириллицы;
- `glfwSetWindowContentScaleCallback` + framebuffer size — DPI;
- `glfwGetGamepadState` — геймпады;
- `GLFW_NO_API` + `glfwGetWin32Window` / `glfwCreateWindowSurface` — окно под Vulkan / D3D / Metal.

Чего у GLFW действительно нет: композиции IME (CJK), мобильных платформ, аудио. Ничего из этого ТЗ не требует.

**Что делаем:**
- `platform::window` — интерфейс без GLFW-типов: native handle, framebuffer size, content scale, события, включая `char` и `content_scale_changed`.
- GLFW становится его единственной реализацией.
- Создание GL-контекста и swap переезжают в `drv_opengl` (`create_swapchain(native_window)`).
- Таргет window перестаёт линковать `drv_opengl` и glad.

### 9.3 SDL_GPU не используется
SDL_GPU — GPU-API в составе SDL3: тонкая абстракция над Vulkan, D3D12 и Metal в современной модели (render pass, pipeline, bind). По решению владельца движок не завязывается на чужой GPU-слой. SDL_GPU, WebGPU и Metal можно использовать только как **референс дизайна** своего RHI: их минимальные модели почти совпадают с шагами 1–4.

### 9.4 Шейдеры: GLSL с правилами переносимости
**Решение:** исходный язык остаётся GLSL. Slang не вводится сейчас; пересмотреть, когда появится не-GL бэкенд.

Сам язык важен меньше, чем **модель привязок**. Её задаёт RHI, а шейдеры ей следуют. Правила для всех шейдеров, начиная с первого переписанного:
1. Одна версия — `#version 450 core` (или 460). Единый заголовок `snk_common.glsl` подключается препроцессором движка.
2. **Никаких свободных uniform.** Только блоки (`uniform`/`buffer` blocks) и сэмплеры с явной привязкой через макрос `SNK_BINDING(set, slot)`. Для GL он разворачивается в `layout(binding = set*16+slot)`, для Vulkan — в `layout(set=, binding=)`. Наборы: 0 — кадр, 1 — пасс, 2 — материал, 3 — объект.
3. Типы и функции, которые расходятся между языками, — только через макросы общего заголовка: `float2/float3/float4x4`, `lerp`/`mix`, `saturate`, `mul(m, v)`.
4. Варианты задаются явным списком ключей в описании шейдера, а не произвольными `#define` из кода. Ключ варианта — стабильный хеш имён и значений. Счётчики вроде числа источников света — uniform, а не вариант.
5. Шейдеры не зависят от GL-соглашений: глубина 0..1, origin сверху слева; компенсация — в бэкенде.
6. `#include` — через нормальный препроцессор с guard'ами и путями VFS.

**Где кончаются возможности макросов** (поэтому одних макросов для D3D / Metal не хватит):
- в HLSL и MSL текстура и сэмплер — разные объекты, в GLSL — один combined sampler;
- точка входа: GLSL использует глобальные `in`/`out`, HLSL и MSL — функцию со структурами;
- модели привязок (`binding` / `register` / argument buffers) и раскладки матриц.

Для этих API понадобится трансляция. Путь без смены языка: glslang (GLSL → SPIR-V) + SPIRV-Cross (SPIR-V → HLSL / MSL) как **инструменты сборки ассетов**, не рантайм-зависимости. Альтернатива на тот момент — Slang.

**Что даёт glslang уже сейчас** (опционально, как offline-валидация на этапе импорта и CI):
- раннее обнаружение ошибок без запуска;
- рефлексия привязок через SPIRV-Reflect; она может заполнить схему параметров материала для инспектора;
- готовый SPIR-V на будущее; GL 4.6 умеет потреблять SPIR-V через `ARB_gl_spirv`.

### 9.5 Явные фазы ECS: кто задаёт и как работает
Два уровня, которые не надо путать:
- **Стадии кадра** (`frame_stage_registry`): poll → update → extract → render → gui → present. Движковый уровень, без изменений.
- **Фазы ECS**: исполняются внутри стадии `update` для каждого `world_context`.

**Кто что задаёт:**

| Что | Кто | Где |
|---|---|---|
| Набор фаз | Движок | Фиксированный список: `input → pre_update → fixed_update → update → post_update → transform → late_update`. Игра может добавить свою **именованную** фазу с якорем «до/после встроенной», но не менять встроенные |
| Фаза системы и ограничения порядка | Автор системы, в коде | При регистрации: `register_system("scn::transform_system", fn, {.phase = phase::transform, .after = {...}, .before = {...}, .run_in_edit = true})`. Фаза — свойство смысла системы (распространение трансформов всегда в `transform`), а не уровня |
| Какие системы включены в мире | Данные | `world_desc.systems` — список имён (как сейчас). Desc решает **какие**, код — **где** |
| Порядок внутри фазы | Планировщик | Топологическая сортировка по `after`/`before`. Ничья разрешается стабильно, по порядку в `world_desc.systems`, поэтому существующие уровни, где порядок задан списком, ведут себя ожидаемо |

**Как исполняется:**
1. При загрузке мира или изменении списка систем планировщик **один раз** строит план: `vector<phase_plan{vector<system_node>}>`.
2. При построении плана:
   - цикл в `after`/`before` даёт ошибку с именами систем;
   - неизвестное имя в desc даёт диагностику, а не падение;
   - в Debug дополнительно проверяется конфликт доступа: типы аргументов, которые сейчас выводит `invoker`, используются **для валидации, а не для порядка**. Например: «A и B пишут `transform_component` в фазе `update` без ограничения порядка».
3. Каждый кадр: для каждой фазы по порядку; `fixed_update` крутится N раз по аккумулятору времени контекста; после каждой фазы применяется command buffer контекста.
4. Режимы контекста:
   - **Edit** — только системы с `run_in_edit` (трансформы, матрицы камер), геймплей не тикает;
   - **Play** — все;
   - **Pause** — ничего, кроме `run_in_edit`;
   - **Step** — один `fixed_update` + один проход остальных фаз.
5. План — плоская структура, поэтому позже внутри фазы можно параллелить системы с непересекающимся доступом. Сейчас всё однопоточно.

**Пример для текущего `editor_level.desc`:** список `inp::update_input_state, scn::animation_controller_update, scn::animation_system_node, scn::depth_system, scn::transform_system, scn::animation_system_matrix, scn::update_camera_matrix_system` раскладывается так:

| Фаза | Системы |
|---|---|
| `input` | `inp::update_input_state` |
| `update` | `scn::animation_controller_update` → `scn::animation_system_node` |
| `transform` | `scn::depth_system` → `scn::transform_system` |
| `post_update`… `late_update` | `scn::animation_system_matrix` (`.after = transform_system`) → `scn::update_camera_matrix_system` |

Порядок больше не зависит от того, какие типы аргументов у систем.

### 9.7 Легаси с пометкой «проверить»
- `.idx/` — удалить.
- Неиспользуемые шейдеры и черновые уровни **не удалять вслепую**: владелец использовал их как шаблоны. Порядок такой:
  1. Для каждого файла составить карточку: какую задачу он решал (например, `scene_inst.*` — инстансинг, `normal.*` — визуализация нормалей через geometry shader).
  2. Проверить, решается ли эта задача текущим конвейером.
  3. Найти внешние ссылки: документация, эпики, конфиги, локальные заметки владельца.
  4. Решить: удалить; перенести в `templates/` с пометкой «референс»; или превратить в фичу нового конвейера (например, debug-пасс нормалей).
- Удаление — только после подтверждения таблицы владельцем.
