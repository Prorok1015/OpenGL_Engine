## 1. Цель стадии и критерии выхода

**Цель.** Закрыть веху M1 (игровой модуль, расширения редактора, Shipping-хост) и довести AI-2 (#540): агент через MCP собирает игру без ручной правки файлов. Плюс два решения владельца, перенесённые в эту стадию: hot reload с сохранением живого Play (#541, вариант C, Р1) и первый срез шины игровых событий с базовыми действиями (#542, Р8).

**Что владелец сможет сделать и увидеть в конце стадии:**
1. **Агент собирает игру.** Через MCP: импорт моделей, подключение системы из `game.dll` к миру, запись desc уровня, сохранение и открытие сцены, чтение runtime-сущностей в Play. Человек только подтверждает опасные действия (AC эпика #540, кроме шейдеров — см. вопрос В4).
2. **Редактор.** Систему из `game.dll` можно подключить к миру в UI, с undo (#549). Ошибки загрузки desc и проверка проекта перед Play видны в панели Problems, оттуда можно перейти к объекту (#24).
3. **Hot reload в Play.** Правка функции системы → сборка → Play продолжается: сущности и счёт на месте. Несовместимая правка даёт явное предупреждение или откат на старую DLL (#541).
4. **API для игрового кода:** `spawn_prefab`/`despawn` (#551), `play_animation` с событием конца клипа (#563), переходы меню → уровень → результат (#564), действия `MoveLeft`/`Restart` с клавишами из настроек проекта, события на шине мира, их видно через MCP (#542).
5. **Shipping-хост.** Один `.exe` без кода редактора, движок и игра собраны статически. Он запускает стартовую сцену проекта, ресурсы пока читает из папки (пак — стадия 7, #46). CI запускает его headless (#23).
6. **Расширение редактора.** Модуль `game_editor` добавляет панель и рендерер инспектора без правки редактора, реестры документированы (#22).
7. **Веха M1 закрыта:** #21, #22, #23, #160, #219, #220.

- **S541-0. Дизайн и ADR.**
  - Разобраны пять вопросов из решения владельца: runtime-сущности без `node_id`, ссылки между сущностями, компоненты без схемы и GPU-ресурсы, удалённая система или тип, откат.

  - Каждый компонент со схемой проходит круг «registry → desc → registry» без потерь (тест).
  - Runtime-сущности без пути получают id, локальные для снимка. Ссылки между сущностями переназначаются.
  - Компоненты без схемы перечисляются в отчёте.
  - Этот же сериализатор использует #552.

- **S541-2. Hot reload в Play.**
  - На тестовом модуле правка функции системы не сбрасывает сущности и счёт.
  - Время, seed и пауза сохраняются.
  - После reload нет ссылок на код старой DLL (тест + ASan).
- **S541-3. Несовместимые изменения и откат.**
  - Удалённый тип компонента или система даёт явное предупреждение и отчёт, а не тихое переиспользование.
  - Если восстановление не удалось, возвращается старая DLL и Play продолжается.
  - Компоненты без схемы и поля систем дают предупреждение в логе и уведомление.

## 4. Риски и вопросы владельцу

### Вопросы, где нужно решение владельца

**В1. Объём стадии.** По Р1 и Р8 в стадию добавлены реализация #541, срез #542 и #563. План §4 их ещё не учитывает: там стадия 2 = 34–64 PR на 3–6 дней. Сейчас ~55–75 PR.
- **Рекомендация:** одна стадия с воротами. Если ADR #541 не утверждён к концу волны 1, реализация #541 (S541-2/3) уходит в начало стадии 3, а остальное идёт как есть.
- **Почему:** M1 и AI-2 от #541 не зависят, а #541 — самый длинный путь.

**В2. Шина #542 или почта набора.** Почта набора уже есть: `ecs_channel.hpp`, `WORLD_MESSAGING.md` §3, утверждена 2026-10-19. Она одна на набор миров и доставляет с лагом ровно в кадр. Владелец в #542 просит «свою шину у каждого мира» с доставкой в фазе кадра.
- **Рекомендация:** новая шина на мир, доставка в том же кадре в фиксированной точке. Типы конвертов те же, что у почты. Межмировые сообщения остаются на почте набора.
- **Почему:** «монета собрана → звук» не должна ждать кадр, а утверждённая семантика почты не меняется.

**В3. Как поставлять расширения редактора (#22).** Отдельный модуль `game_editor` (DLL только для редактора) плюс API редактора отдельной библиотекой в SDK. Это второй модуль в проекте, а решение 2026-10-28 в #220 гласит: «один игровой модуль на проект (M1)».
- **Рекомендация:** разрешить ровно одну пару `game` + `game_editor`.
- **Почему:** иначе код редактора попадёт в Shipping-`.exe`. К тому же `editor_system` сейчас STATIC внутри `editor.exe`, и модулю не с чем линковаться.

**В4. #554 (шейдеры через MCP).**
- **Рекомендация:** перенести в стадию 5 к #36. Критерий AI-2 («агент собирает DemoProject2») считать без записи шейдеров: в демо шейдеры — строки C++ в модуле (#554).
- **Почему:** это прямо следует из Р10, и тогда стадия 2 не тянет за собой редактор шейдеров.

**В5. #220.**
- **Рекомендация:** закрыть. Последний AC (компонент по схеме без C++-типа) вынести в новую story после этапа А, рядом с #230.
- **Почему:** он нужен только wasm, остальные AC выполнены (#395–#402, #405, #406 закрыты).

**В6. Хвосты стадии 1.** TEAM-LEAD считает стадию 1 закрытой (#543–#546), но её пункты «затем» из плана §3 ещё открыты: #553, #556–#561, #470, #404.
- **Рекомендация:** #553, #556, #557, #558 взять в стадию 2 (они в тех же файлах, что AI-2 и Shipping). Остальные брать как наполнитель, иначе в стадию 3.
- **Почему:** иначе они так и будут висеть без стадии.

**В7. Где проверять AC «демо-змейка переведена»** (#551; то же в #563, #564, #542). DemoProject2 в репозитории нет.
- **Рекомендация:** проверять AC на тестовом модуле в `tests/`. Демо владелец повторяет вручную на приёмке стадии.
- **Почему:** CI проверяет только код из репозитория.
