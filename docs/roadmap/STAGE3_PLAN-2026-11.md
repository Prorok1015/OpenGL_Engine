## 1. Цель стадии

**Простыми словами.** Данные проекта перестают ломаться и становятся удобными для правки:
1. **Ассеты получают постоянный ID** (#27). Переименовали или перенесли файл — ссылки на него не ломаются. Видно, кто ссылается на ассет.
2. **Старые проекты обновляются одной командой** (#28). Перед обновлением показывается план, делается бэкап, после — отчёт; сбой откатывает всё.
3. **Настройки игры правятся в редакторе** (#26). Конфиг игры из `game.dll` открывается как документ, правится инспектором (списки, словари, optional), ссылки выбираются пикером нужного типа. После Ctrl+S Play видит новое значение без пересборки (F33, Р30).
4. **Мажор module API 4.0 (Р27).** Ссылки `{guid, path}`, кэш ресурсов без inline-кода в модуле, а также все отложенные ломающие правки ABI (окно 4.0, #758). После стадии модули снова живут по обычным правилам ABI.

**Что владелец сможет сделать в конце стадии:**
- переименовать, перенести или удалить ассет в браузере или через MCP (`asset.rename/move/delete`) с отчётом; при удалении увидеть, кто на ассет ссылается («Используется в», `asset.usages`);
- открыть проект старой версии и обновить его через «Мигрировать…», `Project → Migrate Project…`, `--migrate` или MCP `project.migrate`, а при неудаче откатиться;
- двойным щелчком открыть конфиг игры, поменять поле, сбросить его к унаследованному, переставить строки списка и сохранить.

- `CHIMERA_PLAN-2026-11.md` §4 давал стадии 3 **25–50 PR и 3–5 активных дней** (#27 10–20, #28 5–10, #26 10–20, оценка грубая).

  - мажор 4.0 и окно (+8–12 PR, в плане их не было);

- По допущению плана три сессии дают 12–20 merged PR за активный день. Реально 5–7 мержей на сессию в день (STAGE2_PLAN §5).

- Узкое место — последовательная цепочка PR-6: 21–23 PR при 5–7 мержах в день дают ~3,5–4,5 дня. Плюс ожидание #756 для #776 и выравнивание очереди окна.

- приёмка: ~0,5 дня;
