# API расширения редактора: реестры и снятие регистраций

**Issue:** #590 (эпик #22; #587–#589) · для автора проекта: модуль `game_editor` · заголовки: `Editor/code/editor_system/include/snk/editor/`

Модуль `game_editor` — это отдельная библиотека проекта (`kind: "editor"` в `project.snkproj`), которую редактор грузит после `game`. Она добавляет в редактор панели, команды, рендереры инспектора и виды ассетов, не меняя сам редактор. В игровой `.exe` (Shipping) она не попадает. Рабочий пример — `Editor/data/templates/projects/empty/code/src/game_editor.cpp`, образец для тестов — `tests/editor_api_dll`.

## Как устроен модуль

```cpp
#include <snk/editor/edt_editor_extension.h>

class my_editor_module final : public edt::editor_extension
{
public:
	std::string_view name() const override { return "game_editor"; }  // как в манифесте
	void register_editor(edt::editor_module_context& context) override { /* регистрации */ }
	void shutdown_editor() override { /* своё состояние */ }
};

SNK_DECLARE_EDITOR_MODULE(my_editor_module)
```

`SNK_DECLARE_EDITOR_MODULE` экспортирует функции модуля и `snk_editor_api_version`. Редактор сравнивает её с `SNK_EDITOR_API_VERSION` до создания модуля: major должен совпасть, minor модуля — не быть больше minor редактора. Версия сейчас 1.2 (1.1 добавила превью ассетов; 1.2 — счётчик исполняемых колбэков модуля: панели, действия, инспекторы, asset kinds и обработчики событий, зарегистрированные через `editor_module_context`, считаются, пока работают, и `module_unload_refusal` отказывает выгрузке из них). CMake: `snk::engine snk::engine_api snk::editor_api` из SDK; библиотека `snk::editor_api` есть только при общем движке.

## Реестры

Всё, что модуль кладёт в редактор, идёт через `editor_module_context`; руками реестры редактора модуль не трогает.

| Реестр | Вызов | Что регистрируется | Ключ |
|---|---|---|---|
| Панели | `add_panel(panel_desc)` | наследник `edt::panel_base`, место в раскладке, пункт меню View | `id` (равен `panel_base::get_id()`) |
| Меню | `add_menu(name)` | верхнее меню | имя |
| Действия | `add_action(action_desc)` или `add_action(cmd::command_desc, action_ui)` | команда (видна агентам и скриптам по своим правам) и её пункт меню и сочетание клавиш | `id` команды |
| Рендереры инспектора | `add_inspector(type, renderer)` | рисует поля компонента по `__type` desc | `type` |
| Виды ассетов | `add_asset_kind(asset_kind_desc)` | действия «открыть» и «бросить в сцену» по суффиксу пути | `id`; побеждает самый длинный подходящий суффикс |
| Превью ассетов (API 1.1) | `add_asset_preview(asset_preview_desc)` | документ предпросмотра по суффиксу | `id` |
| События | `subscribe(signal, handler)` | подписка на сигнал `editor_events` | — |
| Задачи | `start_job(...)`, `tasks()` | фоновая работа, привязанная к жизни модуля | — |
| Проблемы | `set_problems(source, items)` | записи списка проблем | `source` |

Правила, общие для всех реестров:
- Неверная регистрация (пустой или занятый id, панель, чьи `id`/`title` не равны собственным, действие без подписи или с неразобранным сочетанием, пустой обработчик) — ошибка в логе: возвращённая регистрация не активна, модуль продолжает грузиться. Занятое сочетание клавиш не ошибка: выигрывает более раннее действие, в лог идёт предупреждение.
- Рендерер на тип, у которого он уже есть, в том числе встроенный, отвергается. Тип desc проекта (в примере `game_note`) — безопасный выбор.
- Тип без рендерера рисуется общим JSON-редактором; рендерер возвращает `true`, если поменял данные.
- Все реестры и панели работают на главном потоке.
- `dialog_service` модулю не выдаётся (его обратные вызовы пережили бы модуль).

## Снятие регистраций

Всё, что модуль зарегистрировал, держит `registration_scope`. При выгрузке:

1. `stop_tasks()`: новые задачи отклоняются, запущенные получают stop-токен и ожидаются, продолжения на главном потоке, поставленные раньше, выполняются сейчас (со статусом «отменено»). Задача модуля обязана смотреть на stop-токен.
2. `shutdown_editor()` модуля: здесь освобождается собственное состояние. Редактор вызывает его до снятия регистраций и всегда перед уничтожением модуля. Если оно бросило исключение, шаг 3 всё равно выполняется: область очищается и снимается с учёта до возврата, чтобы редактор не держал указатель в выгружаемый код.
3. Подписки, потом регистрации, потом очистки (`set_problems` и подобное), каждая группа в обратном порядке регистрации. После этого редактор такой же, как до загрузки, а повторная загрузка не конфликтует со старыми записями.

Что требуется от модуля:
- Регистрации и подписки делать только через `editor_module_context` (`subscribe`, а не сигнал `events()` напрямую). Соединение, сделанное руками, нужно снять в `shutdown_editor`.
- Не обращаться к `edt::` из статических инициализаторов DLL.
- Не вызывать выгрузку из своих же обратных вызовов: редактор отказывает в выгрузке, пока выполняется продолжение задачи модуля (`editor_context::module_unload_refusal`).

## Чего пока нет

- `services()` (реестры самого движка) и сырые сигналы `events()` не отслеживаются областью: пробелы контекста — #663.
- Отдельной перезагрузки `game_editor` нет (#664). Он выгружается и грузится заново вместе с `game`: перезагрузка `game` снимает и снова регистрирует модули редактора, и они берут свежую копию библиотеки. Если пересобран только `game_editor`, живая сборка редактора смотрит лишь на модули `runtime`, и новая версия подхватывается после перезапуска редактора.
- Редактор не держит файл библиотеки: он грузит **копию** из `.cache/modules/<pid>-<n>/` (как `game.dll`, #435), поэтому «Build > Build Game» на Windows перезаписывает `build/bin/game_editor.dll` и `.pdb`, пока редактор запущен.
