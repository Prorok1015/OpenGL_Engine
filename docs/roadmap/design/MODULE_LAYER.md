# Дизайн: слой модуля («дочерний контекст»)

**Issue:** #220 (S3 эпика #217; основа для #21 EPIC-52, #222 hot reload, #230 wasm) · **Основа:** спайк #218 ([SPIKE-218-entt-dll.md](SPIKE-218-entt-dll.md)), [DISTRIBUTION.md](DISTRIBUTION.md) §2 · **Статус:** модель — решение владельца 2026-10-27; план PR — ред. 2 в #220, одобрен 2026-10-27

## 1. Модель

Игровой модуль (`game.dll`, позже wasm-модуль) получает **слой** — дочерний контекст поверх контекста движка.
- **Чтение сквозное:** сначала слой, затем база. **Запись — только в слой.** Модуль не может изменить базу.
- В слое живёт всё, что создаёт модуль: системы и игровые фазы, имена компонентов, типы desc, спавнеры и миграции, ресурсы в кэше, meta-регистрации EnTT, сервисы модуля.
- **Игровые миры принадлежат слою.** База = движок + редактор, всё игровое — в слое.
- **Выгрузка = уничтожение слоя целиком.** Состояние программы возвращается к исходному, повторная загрузка безопасна.
- **Hot reload (#222):** уровни сохраняются в desc → слой уничтожается → DLL перезагружается → создаётся новый слой → уровни загружаются.
- **Игровой слой есть всегда**, даже без модуля: при открытии проекта создаётся пустой слой (решение владельца 2026-10-27). У редактора один путь: игровые миры всегда в активном слое.

**Инвариант:** в базе нет ничего, что ссылается на код модуля. Его дают два свойства:
1. База не может создать тип модуля: её `desc_system` и ассемблер этого типа не знают.
2. База не держит миров с компонентами модуля: такие миры принадлежат слою.

Спайк показал, что именно держит код модуля после выгрузки (SPIKE-218 §3.2–3.5): пулы EnTT, meta-узлы, записи систем и планов, фабрики desc, спавнеры, экземпляры desc в кэше, имена сервисов. Все они оказываются в слое.

## 2. Состав слоя

| Часть | Сейчас | В слое |
|---|---|---|
| Хранилище сервисов | `ds::app_data_storage` уже умеет родителя: чтение по цепочке (`ds_store.hpp:138-147`), запись локальная; в production не используется | дочернее хранилище (`parent` = корень). Слоёные сервисы лежат в нём и **затеняют** базовые: `require<desc::desc_system>()` из модуля возвращает дочерний |
| `ecs::system_factory` / `system_registry` / `phase_table` | плоские | `find` по цепочке; `ordered()` сливает игровые фазы базы и слоя; планы миров слоя строятся по реестру слоя |
| `ecs::component_registry` (новый) | нет | стабильное имя → `type_hash` |
| `desc::desc_system` | плоский: фабрики, миграции, схемы, имена компонентов | все четыре по цепочке; экземпляр desc указывает на `desc_system`, который его создал (`desc_base::m_system`) |
| `scn::ecs_assembler` | плоские спавнеры | спавнеры по цепочке; ассемблер слоя держит `desc_system` слоя |
| кэш `res::resource_system` | один кэш (`cache_key{tag,type}`, слабый + pinned); слои путей `res://` (#390, mount table) — только файловая система | **слой кэша** поверх общего `resource_system`: свой кэш и pinned, свой desc-адаптер на `desc_system` слоя. Резолверы, mount table, IO-потоки и watchers общие (решение владельца 2026-10-27) |
| meta EnTT | `ecs::meta_context()` движка (#220 PR-1) | свой `entt::meta_ctx` слоя, §3 |
| миры | `scn::context_manager` (один на процесс), сеты `level`, `preview:<tag>` | сеты создаются для слоя и собираются его сервисами; уничтожаются вместе со слоем |

**Правило коллизий:** имя, занятое в базе (система, фаза, desc-тип, компонент), слой зарегистрировать не может. Это ошибка регистрации с логом, а не ASSERT. Затенение допускается только для сервисов слоя в хранилище: слоёный `desc_system` слоя затеняет базовый.

## 3. EnTT meta

EnTT не знает «родительского» контекста. Рассмотрены два варианта; оба — штатный API, спайк уже проверил `resolve(ctx, id)` и `meta_reset` между бинарниками.
- **(A, принято) Свой `entt::meta_ctx` у слоя, поиск «слой → база».**
  - Locator модуля (`entt::locator<entt::meta_ctx>` в его бинарнике) подключается к контексту слоя.
  - Движок ищет тип по id через мир: `world_context` знает свой слой. Сейчас это одно место — `apply_commands` (`scn_world_context.cpp:115`), helper `ecs::find_meta(layer_ctx, base_ctx, id)`.
  - Уничтожение слоя уничтожает контекст, учёт id не нужен. Модуль физически не может дописать функцию или данные к meta-узлу типа базы.
- (B, отклонено) Один контекст и `meta_reset` записанных id при уничтожении слоя. Модуль может дописать meta к типу движка, а откатить это нельзя — нарушает «база неизменяема».

## 4. Миры и редактор

- `scn::scene_layer` — набор сервисов слоя: `desc_system`, `ecs_assembler`, `system_factory`, слой ресурсов, `meta_ctx`.
- `context_manager` остаётся одним на процесс: render extractor и редактор обходят все сеты, как сейчас. Но:
  - каждый сет создаётся **для слоя** и собирается его сервисами (сейчас `load_level` берёт `m_assembler`/`m_system_factory`, `scn_context_manager.cpp:144`);
  - при уничтожении слоя вызывается `destroy_sets_of(layer)`.
- **Редактор:**
  - `editor_services` вместо полей `sfactory`/`assembler` даёт `active_layer()`;
  - `level_set()` возвращает сет `level` активного слоя;
  - превью префаба (`preview:<tag>`) создаётся в активном слое — префаб может содержать компоненты модуля.
- Документы редактора хранят desc и пути `node_id`, а не сущности, поэтому пересоздание слоя для них прозрачно. Сырые указатели на registry и компоненты при пересборке не хранятся — это уже правило (`Editor/CLAUDE.md`).

## 5. Данные базы со ссылками на код модуля

- **Сервисы модуля** (`app_data_storage::entry::name` и deleter лежат в бинарнике, который регистрировал) попадают только в хранилище слоя и уничтожаются вместе с ним.
- **Реестры базы**, которые модуль может достать через `require` и которые не слоятся: `cmd::command_registry`, `frame_stage_registry`, `channel_registry` и подписки на события, `task_system`, лог-синки, render passes.
  - Регистрация из модуля — только через RAII-хэндл, который хранит слой и снимает при уничтожении.
  - Задачи `task_system` с кодом модуля слой дожидается или отменяет до уничтожения.
  - Проверка в тесте: счётчики базовых реестров до загрузки и после выгрузки совпадают.
- Полностью read-only базу (`require<const T>`) не вводим: нужен новый API хранилища, а выигрыш поверх затенения и RAII-хэндлов мал.

## 6. Жизненный цикл

1. Загрузка: `module_source::load()` → `check_module_entry` (включая флаги EnTT, PR-7) → создание слоя → `create_module` → `register_services(хранилище слоя)` → `initialize_services`.
2. Работа: миры слоя, редактор через `active_layer()`.
3. Выгрузка:
   1. `shutdown_services(хранилище слоя)`;
   2. уничтожение слоя в обратном порядке создания: сеты и миры → слой кэша (ждёт загрузки слоя) → ассемблер → `desc_system` → реестр систем → meta-контекст → сервисы модуля;
   3. `destroy_module`;
   4. `module_source::unload()`.
4. Модули базы (core, engine, editor) работают как сейчас — в корневом хранилище. Для их систем остаётся `ecs::system_scope` (#220 PR-2).

## 8. Риски

- **Слой кэша и потоки.** Загрузка, начатая через слой, может завершиться после начала его уничтожения. Уничтожение ждёт или отменяет загрузки слоя. Проверка — TSan.
- **Затенение сервисов.** Код базы, который получил базовый `desc_system` по ссылке (адаптеры, редактор), не увидит типы слоя. Всё, что работает с игровыми данными, берёт сервисы из слоя (`active_layer()`, сет мира). Ревью PR-5 проверяет каждое место, перечисленное в карте ссылок.
- **Объём PR-5:** в редакторе много мест, где берутся `sfactory`/`assembler`/`level_set()`. Делается одним PR, поведение сохраняется, smoke-скриншоты не меняются.
