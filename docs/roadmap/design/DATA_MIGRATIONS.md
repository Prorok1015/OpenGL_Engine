# Миграции данных: гайд для авторов модулей

Как менять формат своих данных так, чтобы проекты со старыми файлами открывались и переносились на новую версию модуля. Дизайн — [EPIC-58](../../epics/desc-driven/EPIC-58.md), формат схем — [DESC_SCHEMA.md](DESC_SCHEMA.md), слой модуля — [MODULE_LAYER.md](MODULE_LAYER.md). Issue: #769.

## 1. Версия типа

- У каждого типизированного объекта (`__type`) есть версия. Она пишется в `__version`; если ключа нет, версия равна 1.
- Текущая версия типа — 1 плюс число зарегистрированных шагов миграции (`desc_system::current_version`). Шаг `from = N` переводит объект из версии N в N+1. Шаги идут с 1 без пропусков.
- Сохранение всегда пишет текущую версию (`stamp_header`). Ключи `__type`, `__version`, `__guid` идут первыми.
- Схема типа (`type_schema::version`) обязана совпадать с версией, к которой ведут шаги. Иначе `register_schema` отказывает в любой сборке.
- Когда версия поднимается:
  - переименовали, убрали или изменили смысл поля — это новый шаг;
  - добавили поле со значением по умолчанию — шаг не нужен, если отсутствие ключа читается как значение по умолчанию;
  - перевели тип на схему без изменения байтов файла — версия **не** поднимается (проверка: `desc_resave --check`).
- Шаг не удаляется и не правится после выпуска: в проектах уже есть файлы, которые прошли его.
- Шаги на C++ и декларативные шаги (§3) для одного типа не смешиваются: регистрация второго вида отклоняется.

## 2. Шаги на C++

Регистрируются на desc system слоя модуля, вместе с типом, и снимаются вместе со слоем:

```cpp
layer.descs().register_migration(type, 1, "renames old to new",
	[](boost::json::object& obj, desc::migration_context& context) {
		desc::migrations::rename(obj, "/old", "/new");
		if (!obj.contains("new")) context.warn("no 'old' field");
	});
```

- **Сводка** (третий аргумент) попадает в план `--migrate --dry-run` и в отчёт миграции. Шаги без сводки (`register_migration(type, from, fn)`) тоже работают, но в плане о них ничего не сказано.
- **`migration_context`** знает тип, версию «откуда» и файл (пусто для объекта из памяти). `warn()` пишет в лог и в раздел «Warnings» отчёта: так шаг сообщает о потерянных данных или о допущении.
- Шаг видит только JSON своего объекта. Он не трогает проект: не переписывает ссылки на другие файлы и не создаёт файлы (EPIC-58 §3.2).
  - Единственное исключение — `context.id_of(path)` (#1200): asset id файла по пути, больше ничего. Ответ выбирает только «перевести или отказать», от него не зависит, что шаг пишет; без хука ответ «нет». Отказ — исключение из шага с понятным текстом: загрузка не удаётся, ошибка видна в Problems.
  - То, что шаг типа отклоняет, переводит шаг проекта фазы pre (EPIC-58 §3.3) до миграции файлов: так `engine.material_shaders` (#1200) пишет `.shader.desc` для стадий материала, которых нет в движке. Скан проекта прогоняет шаг типа на копии и отмечает такие файлы, план не запускает на них шаг типа заранее. Материал, который не перевести и шагу проекта (родитель не читается, нет вершинной или фрагментной стадии), скан помечает `invalid`: `--force` оставляет его, остальной проект мигрирует. `--migrate` отдаёт `resource_system` индекс ассетов проекта на время плана и применения, так что `context.id_of` шага типа и скан отвечают по одному индексу.
- Вложенные типизированные объекты мигрируют сами, по своим шагам. Шаг родителя выполняется раньше, чем обходятся его дети.
- **Хелперы** `desc::migrations::rename / remove / set_default` (`snk/desc/desc_migrations.h`) работают с JSON-указателями от корня объекта:
  - `rename(from, to)`: нечего переносить — ничего не делает; цель занята — исключение (значение не перезаписывается). Исключение — цель, в которой лежит сам источник (`/a/b` → `/a`, подъём на уровень вверх): значение встаёт на место объекта, если в нём нет ничего, кроме пути к источнику; иначе исключение называет ключ, который бы потерялся. Подъём зависит от данных: лишний ключ в `/a` тем же шагом не убрать (`remove` внутри цели подъёма — отказ разбора), его убирает шаг версией раньше. Обратное — цель внутри источника (`/hp` → `/hp/value`): значение целиком, в том числе скаляр или массив, уходит на уровень вниз. Опускание не узнаёт файл, который уже вручную приведён к новому виду без подъёма версии: такой файл будет обёрнут ещё раз. Меняйте формат только шагом. Любое исключение оставляет объект нетронутым (#1228);
  - `remove(pointer)`: ключа нет — ничего не делает;
  - `set_default(pointer, value)`: заполняет только отсутствующий ключ, `null` тоже считается значением.
  - Указатель идёт только по ключам объектов. Заголовочные ключи (`__type`, `__version`, `__guid`) на любой глубине, индексы массивов (`0`, `-`), пустые части и экранирования, кроме `~0`/`~1`, — ошибка. Массив на пути — ошибка шага.

## 3. Декларативные шаги runtime-схемы

Компонент без C++-типа (схема в JSON, #606) объявляет шаги массивом `"migrations"` и передаёт его вместе со схемой:

```cpp
const boost::json::object doc = boost::json::parse(schema_json).as_object();
data.require<gs::module_context>().register_component(desc::parse_type_schema(doc), doc.at("migrations").as_array());
```

```json
"migrations": [
	{ "from": 1, "rename": { "/hp": "/health" } },
	{ "from": 2, "remove": ["/legacy"], "set_default": { "/armor": 0 } }
]
```

- Ключ поля (`key`) и алиас (`read_aliases`) — JSON-указатель с ведущей «/»; иначе регистрация отказывает (#1228). Указатели шагов ссылаются на них.
- Внутри шага сначала выполняются `rename`, затем `remove`, затем `set_default`. Правила указателей — как у хелперов из §2.
- Ключ, повторённый внутри объекта `rename` или `set_default`, движок не видит: массив приходит уже разобранным, и JSON-парсер оставляет последнее значение. Проверяйте исходник схемы. Повтор указателя в `remove` — отказ.
- Отказ регистрации (`register_component` вернёт `false`, причина в логе), если:
  - шаги не идут с `from` = 1 без пропусков или не ведут к `version` схемы;
  - внутри шага есть цепочка (цель одного `rename` — источник другого), два `rename` в один ключ, один указатель дважды в `remove` или указатели, вложенные один в другой (`/a` и `/a/b`); источник и цель одного `rename` (`/a/b` → `/a` или `/hp` → `/hp/value`) — не такая пара;
  - у типа уже есть шаги на C++;
  - цель `rename` или указатель `set_default` после поздних шагов (их `rename` переносят указатель, `remove` снимает проверку) не ведёт к полю схемы, к которой ведут шаги, или значение `set_default` не подходит полю (#1228). Схем промежуточных версий нет, поэтому проверяется только место, куда значение попадёт в конце. Временный ключ, который поздний шаг переносит в поле, разбирает (переносит то, что под ним) или удаляет, тем же шагом или позже, допустим. Если ключ разобран, но не удалён и сам не поле, регистрация проходит с предупреждением (один раз на процесс): что ещё под ним лежит, при чтении отбросится. Явный `remove` этого ключа говорит, что так и задумано, и предупреждение снимает (#1270). Путь ниже поля допустим только у поля с ключами (структура, словарь, custom): у числа или списка ключей нет. Причину отказа заранее даёт `desc_system::migrations_problem(schema, migrations)`.
- Без компонента: `desc_system::register_schema(schema, migrations)` или `scn::register_schema_component(..., migrations)`.
- Проверить массив заранее: `desc::schema_migrations_problem(migrations, version)` возвращает текст ошибки или пустую строку.

## 4. `unknown_type`

- Миграция проекта (`--migrate`) знает тип только тогда, когда у него есть **схема или зарегистрированный desc** в загруженном модуле. Тип, у которого есть одни шаги, тоже `unknown_type`: регистрируйте схему (или desc) вместе с шагами.
- Файл неизвестного типа остаётся как есть. Миграция завершается как partial (код 4), файл и тип попадают в отчёт.
- Модули проекта загружаются, только если им доверяют: в headless-режиме это флаг `--trust-project`. Модуль, который не собран или не загрузился, делает миграцию отказом (код 2), а не partial: иначе все его типы были бы `unknown_type`.

## 5. Как проверить

- **План без записи:**
  `editor --headless --project <dir> --trust-project --migrate --dry-run [--report <файл вне проекта>]`
  - код 0 — мигрировать нечего, 1 — миграция нужна, 2 — отказ (невалидный файл без `--force`, проект новее движка, незавершённая миграция, модуль не загружен).
- **Миграция:** `--migrate [--report <файл>] [--force]`.
  - Коды: 0 — готово, 4 — часть файлов оставлена как есть (`unknown_type`, новее движка, невалидные с `--force`), 5 — сбой и откат, 6 — откат не завершён.
  - Журнал, бэкап и `report.md` лежат в `.snk/migrations/<id>/`.
- **Откат:** `--migrate-rollback <id>`.
- **Очистка старых бэкапов:** `--migrate-prune --keep N [--dry-run]` (#767).
- **Тест модуля:**
  - фикстура проекта со старыми версиями файлов своего типа;
  - `prj::migration::run_migrate` поверх неё: с загруженным модулем — готово, без модуля — partial;
  - пример — `tests/module_dll/app_module_dll_tests.cpp` (#764).

## 6. Данные игрока и данные из памяти (EPIC-58 §7.2)

- **Файлы игрока** (привязки ввода, снимки мира) не переписываются миграцией проекта. При чтении они поднимаются в памяти через `desc_system::upgrade_in_memory`. Файл новее движка не читается и не перезаписывается (#766).
- **Версия записи** формата, который пишет движок, обязана совпадать с версией, к которой ведут его шаги. Это проверяется на старте.
- **Встроенный desc** (поле-ссылка с объектом `__type` вместо тега) записывается из памяти с текущей `__version` (#1236). Объект без `__version` читается как версия 1. Модуль, собранный до #1236, пишет встроенные desc без версии: пересоберите его. Движок перекрывает старые модули только там, где сам сериализует загруженный desc и сразу читает обратно: при сборке компонента экземпляра префаба (`compose_component_json`, `assemble_and_apply` с overrides) и в `copy_to`. В остальных местах объект без версии читается как v1.
- **Записи переопределений экземпляров** (`set` в `overrides`) хранят версию типа компонента и мигрируют его шагами при раскрытии экземпляра и при загрузке документа в редакторе (#1255, EPIC-58 §7.4). Ограничение: запись без версии (файл до prefab v5, ни разу не сохранённый редактором) игра без редактора применяет как написана; `--migrate` версию записи не ставит.
