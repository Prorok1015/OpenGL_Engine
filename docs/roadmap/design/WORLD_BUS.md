# Дизайн: шина событий мира и игровые действия

**Issue:** #602 (S542-0) · эпик #542 · **Статус:** предложен, ждёт утверждения владельцем · Основа: решение владельца Р8 (комментарий в #542), В2 из `STAGE2_PLAN-2026-11.md` (шина на мир, доставка в том же кадре в фиксированной точке, конверты почты, межмировое — на почте набора), `WORLD_MESSAGING.md` (почта набора, утверждена 2026-10-19), `HOT_RELOAD_PLAY.md` (#598) · Код — #603 (шина), #604 (действия), #605 (MCP), только после утверждения.

## 1. Что есть сейчас

- **Почта набора** (`ecs_channel.hpp`, `scn::set_channel`, `WORLD_MESSAGING.md` §3).
  - Одна на набор миров. Конверт `ecs::envelope<T>{from, to, seq, payload}`. Система пишет в `ecs::outbox<T>&`, читает `const ecs::inbox<T>&`.
  - Обмен идёт один раз в начале кадра набора (`context_set::begin_frame_channel`), лаг ровно в кадр. В Edit/Pause почта заморожена, Step даёт один обмен.
  - Типы регистрирует модуль: `layer.channels().add<T>()`. В production пользователей пока нет.
- **`ecs::event<T>`** (`ecs_event.hpp`) — список `entt::entity` без данных, только внутри мира. На нём работают `transform_updated`/`hierarchy_updated`. Подписок нет.
- **Подписок на события нет вообще.** В движке и редакторе нет `entt::dispatcher` и `sigh`.
- **Ввод.**
  - `inp::input_state` — только уровни (`keyboard[]`, `mouse[]`, без фронтов нажатия).
  - `gs::route_input` в стадии `update` кладёт его в ctx каждого контекста. Контекст без фокуса или вне привязки получает нейтральное состояние.
  - В редакторе ввод в Play идёт только из окна Game (`bind_game_window_input`).
  - Действий и раскладок нет. Нет и преобразования имени клавиши в код.
- **Порядок кадра мира** (`context_set::update_context`): фазы `input`, `pre_update`, `fixed_update` (×N шагов), `update`, `post_update`, `transform`, `late_update`. После каждой фазы и каждого фиксированного шага выполняется `apply_commands`.

## 2. Решение в одном абзаце

У каждого мира своя **шина**: ctx-ресурс в его registry.

- **Точка доставки одна, фиксированная:** сразу после встроенной фазы `update` и её `apply_commands`, до игровых фаз, привязанных после `update`, и до `post_update`.
- **Что происходит в ней:**
  1. события, накопленные с прошлой доставки, упорядочиваются детерминированно;
  2. вызываются подписки;
  3. события становятся видны системам-читателям до следующей доставки.
- Конверты — те же `ecs::envelope<T>`.
- **Межмировое остаётся на почте набора.** Чтобы событие ушло в другой мир, подписчик или система отправляет его в `outbox`.
- **Действия** — слой поверх шины.
  - Раскладка живёт в `res/input/actions.desc`, ссылка на неё — из `project.snkproj`.
  - Состояние действий мира (pressed/held/released) считается в фазе `input` из уже маршрутизированного `input_state`.
  - Фронты публикуются на шину событием `inp::action_event`.

## 3. Шина мира (#603)

### 3.1. API

```cpp
// Регистрация типа — как у почты, в слое (модуль) или в базе (движок).
layer.events().add<coin_collected>();                 // T копируемый; схема desc — по желанию (§3.6)

// Система: писать и читать — обычные параметры-ресурсы ctx.
void pickup_system(entt::view<...> v, ecs::event_writer<coin_collected>& out) { out.emit({ .coins = 1 }); }
void hud_system(const ecs::event_reader<coin_collected>& in) { for (const auto& e : in.events()) { ... e.payload ... } }

// Подписка из game.dll — через module_context, RAII (держатель уходит в layer.keep).
ctx.subscribe<coin_collected>([](ecs::bus_context& bus, const ecs::envelope<coin_collected>& e) { ... });

// Вне фаз (редактор, тесты): в очередь, доставка в ближайшей точке мира.
context_manager::emit<T>(set, context, payload);
```

- **Имена.** `event_writer`/`event_reader` не пересекаются с `outbox`/`inbox`. Поэтому один и тот же `T` может быть и событием мира, и письмом набора. Существующий `ecs::event<T>` (сущности для transform) не меняется; переименовать его — отдельная задача, не в этом срезе.
- **Поля конверта.**
  - `from` — имя системы-отправителя. Для подписчика это `"subscriber:<тип>"`, для внешнего поста — пустая строка. Используется для отладки и MCP.
  - `to` пуст: шина рассылает событие всем в своём мире.
  - `seq` — порядковый номер в доставке (§3.3).
- **Записать без регистрации** — ASSERT, как у `outbox::send`.

### 3.2. Точка доставки

```
input → pre_update → fixed_update ×N → update → [apply_commands] → ДОСТАВКА → игровые фазы after(update) → post_update → transform → late_update
```

Почему после `update`:

- «Монета собрана → звук и UI» укладывается в один кадр. Подбор, урон и конец клипа (#563: `scn::animation_controller_update` работает в `update`) происходят до точки, а реакция на них — в подписке или в системах после точки.
- События всех фиксированных шагов кадра (столкновения) приходят одной пачкой и в порядке шагов.
- Одна точка за кадр — это и есть «честный Step»: один кадр Step = одна доставка.

**Окно читателя.** `event_reader<T>::events()` возвращает события последней доставки и держит их до следующей. Поэтому каждая система **видит каждое событие ровно один раз**: системы до точки увидят его в следующем кадре, системы после точки — в этом. Исключение — `fixed_update`: он выполняется несколько раз за кадр и увидит одно и то же событие на каждом шаге. Правило для него то же, что у почты: перенести событие в компонент.

**События, отправленные после точки** (`post_update`…`late_update`), доставляются в точке следующего кадра. Это лаг в кадр только для поздних отправителей; он документирован в API, и в отладочной сборке пишется предупреждение один раз на тип.

### 3.3. Порядок и детерминизм

Ключ порядка в доставке: (фаза, номер фиксированного шага, порядок системы в плане мира, порядок вызова `emit` внутри системы). Номер `seq` присваивается по этому ключу.

- Каждая система пишет в свой локальный буфер. Поэтому порядок не зависит от того, параллельно ли выполняются системы фазы.
- Внешние посты идут **первыми**, как у почты. За ними — события подписчиков прошлой доставки (§3.4).
- Подписчики одного типа вызываются в порядке подписки. Типы между собой — в порядке регистрации. Внутри типа события идут по `seq`.
- Перебора `unordered_map`, wall-clock и `random_device` нет (`WORLD_MESSAGING.md` §5).
- Тест: два прогона дают побайтно равные доставки, независимо от числа потоков фазы.

### 3.4. Подписки

- Подписки вызываются **в точке доставки**, на главном потоке, вне фаз.
- Подписчик получает `ecs::bus_context`:
  - `entt::registry&` мира;
  - `ecs::command_buffer` — структурные правки применяются сразу после всех подписчиков тем же `apply_commands`;
  - писатели событий;
  - `outbox` почты набора.
- Событие, отправленное подписчиком, уходит в **следующую** доставку. Повторного входа в шину нет, поэтому пинг-понг внутри одной точки невозможен. Его ловит лимит (§3.5).
- Подписка задаётся на тип и не привязана к конкретному миру: колбэк вызывается для каждого мира, где этот тип доставлен, и `bus_context` говорит, какой это мир. Фильтр по миру — `subscribe<T>(world_name, fn)`.
- **Снятие подписки.**
  - `module_context::subscribe` возвращает RAII-держатель и сразу отдаёт его в `m_layer.keep(...)`. Подписка снимается при уничтожении слоя, то есть при выгрузке и при любом reload, и раньше FreeLibrary.
  - Движок (или редактор) подписывается через `ecs::bus_registry::subscribe` и сам держит RAII-держатель.
  - Тест: выгрузка → ни одной подписки модуля; reload → подписки нового модуля, старых нет.

### 3.5. Режимы, лимит, жизнь шины

| Режим набора | Доставка | Писатели |
|---|---|---|
| Play | каждый кадр | пишут |
| Step | одна на кадр Step | пишут |
| Pause, Edit | **нет**; окно читателей очищается, чтобы событие не было видно дважды | системы `run_in_edit` пишут в очередь, она копится до лимита и уходит при Play/Step |

- **Лимит** — 1024 события на тип за доставку, как у почты. Лишнее отбрасывается с `egLOG_WARN("scene", …)`. Значение меняется через `bus.set_event_limit`.
- **Жизнь шины.** Шина живёт и умирает с миром. Каждый Play начинается с пустой шины.
- **Hot reload (#598).** События, ждущие доставки, и окно читателей отбрасываются, в отчёте пишется их число. Это события поздних отправителей (§3.2) и одна доставка. Переносить их не стоит отдельного кода, правило то же, что у почты набора.

### 3.6. Схема и MCP (#605)

- **Регистрация.** `events().add<T>()` принимает необязательную схему desc. С ней событие сериализуется в JSON для MCP, без неё — только тип, `seq`, `from` и кадр.
- **Журнал.** У шины есть журнал последних N доставленных событий: кольцо, по умолчанию выключено. Редактор включает его в мирах Play, N = 256.
- **Команды MCP**, обе только для чтения, `expose_as_tool`:
  - `world.events` — параметры `{world?, type?, last?}`. Возвращает последние события из журнала: тип, кадр, `seq`, `from`, payload.
  - `input.actions` — параметр `{world?}`. Возвращает состояние каждого действия и кадр последнего фронта.
- **Вне Play** — ошибка `"no Play session: world events exist only while Play runs"`.

## 4. Игровые действия (#604)

### 4.1. Данные

`project.snkproj` получает новое поле. Его проверяют так же, как `start_scene`: это res-тег внутри проекта.

```json
{ "input_actions": "res://input/actions.desc" }
```

Сам файл `res/input/actions.desc`:

```json
{
  "__type": "input_actions", "__version": 1,
  "actions": [
    { "name": "MoveLeft", "bindings": [ { "key": "A" }, { "key": "LEFT" } ] },
    { "name": "Restart",  "bindings": [ { "key": "R" } ] },
    { "name": "Fire",     "bindings": [ { "mouse": "LEFT" } ] }
  ]
}
```

- **Имена клавиш** — имена перечислителей `KEYBOARD_BUTTONS` и `MOUSE_BUTTONS`. Эти значения только дописываются (`inp_keyboard_event.hpp`), поэтому имена стабильны. #604 добавляет таблицу `inp::key_from_name`/`key_name` и тест: каждый перечислитель до `COUNT` имеет имя.
- **Проверка при загрузке.** Неизвестное имя клавиши, пустое или повторяющееся имя действия — это предупреждение с путём в JSON, а не отказ. Привязка пропускается, действие остаётся.
- **Нет поля или файла** — действий нет. Запрос неизвестного действия пишет предупреждение один раз на имя и возвращает `false`.
- `input_actions_desc` — обычный desc со схемой. Поэтому его видят инспектор и `asset.query`, и он перезагружается живьём через кэш ресурсов. Шаблон проекта (`Editor/data/templates/projects/empty`) получает файл с примером и поле в манифесте.

### 4.2. Состояние действий

- **Раскладка.** Владелец раскладки — `gs` (там, где `route_input`). Он держит `res_handle<input_actions_desc>` и собранную из него `inp::action_map`: имя → id, id → привязки.
- **В каждом контексте** `route_input` кладёт в ctx `std::shared_ptr<const inp::action_map>` рядом с `input_state`.
- **Система движка** `inp::update_actions` работает в фазе `input`:
  - вход: `input_state` этого контекста, `input_focus` и `action_map`;
  - выход: ctx-ресурс `inp::action_state`, где на каждое действие есть `held` (уровень) и фронты `pressed`/`released` относительно прошлого кадра этого мира.
- **Ввод только из Game View с фокусом.**
  - Маршрутизация уже даёт нейтральное состояние контекстам вне привязки.
  - Кроме того, `update_actions` считает все действия отпущенными, пока `input_focus.active == false`.
  - Потеря фокуса при зажатой клавише даёт один фронт `released`. Действие не «залипает».
- **В Pause** система не работает, состояние замирает. Первый кадр после Pause сравнивает с замороженным. **Step** — один кадр. Edit-набор (`level`) действий не считает: система не помечена `run_in_edit`.
- **API для игры.**

  ```cpp
  void restart_system(const inp::action_state& a) { if (a.pressed(k_restart)) { ... } }   // k_restart: inp::action_id
  inp::action_id k_restart = actions.id("Restart");   // поиск по имени один раз; a.pressed("Restart") тоже есть, медленнее
  ```

- **События.** На каждом фронте `update_actions` пишет `inp::action_event{action_id, name, edge: pressed|released}` в шину своего мира. Тип регистрирует движок. Доставка идёт в точке после `update` того же кадра, так что подписчик на `Restart` срабатывает в кадре нажатия.

### 4.3. Ограничения первого среза

- Фронт виден только если клавиша держалась хотя бы до опроса кадра. Нажатие и отпускание между двумя опросами теряется, потому что `input_state` хранит только уровни. Если это понадобится, `ecs_input_manager` начнёт копить счётчик нажатий за кадр; в этот срез это не входит.
- Нет модификаторов (`Ctrl+R`), осей (`MoveLeft`/`MoveRight` → `-1..1`), геймпада и переназначения в UI. Это «позже» по Р8. Формат `bindings` — массив объектов, поэтому эти поля можно добавить без смены версии.

## 5. Порядок кадра (дополнение к `WORLD_MESSAGING.md` §4)

| Место | Что | Лаг |
|---|---|---|
| стадия `update`: `route_input` | `input_state`, `input_focus`, `action_map` → ctx контекстов | 0 |
| `begin_frame_channel` набора | почта N-1 → inbox N | 1 кадр (почта) |
| фаза `input`: `inp::update_actions` | `action_state`; `action_event` → шина | 0 |
| фазы `input`…`update` | `event_writer` → очередь шины мира | — |
| **точка доставки** (после `update`) | подписчики; окно `event_reader` | 0 для систем после точки и подписчиков, 1 кадр для систем до неё |
| `post_update`…`late_update` | читают окно; поздние `emit` → следующая доставка | 1 кадр для поздних отправителей |

## 7. Риски

- **Две системы сообщений.** Правило выбора записывается в API-доке и в `WORLD_MESSAGING.md`:
  - внутри мира, в этом кадре — шина;
  - между мирами — почта;
  - состояние — blackboard.
- **Поздние отправители получают лаг в кадр.** Есть предупреждение в отладочной сборке. Если понадобится, можно добавить вторую точку (после `late_update`) — для этого шине достаточно номера точки.
- **Подписчик с тяжёлой логикой** выполняется на главном потоке вне фаз и не виден в плане систем. Профилирование и MCP показывают его как `subscriber:<тип>`.
- **Без счётчика нажатий** быстрые нажатия теряются (§4.3).

## 8. Вопросы владельцу

1. Одна точка доставки — сразу после `update` (рекомендация). Или после каждой фазы (сложнее: читателям нужны курсоры)?
2. Подписки — колбэки в точке доставки, события от подписчиков уходят в следующую доставку (рекомендация). Или только системы-читатели, без колбэков?
3. Действия считаются отпущенными без фокуса Game View, один фронт `released` при потере фокуса (рекомендация)?
4. Неизвестная клавиша или дубль в `actions.desc` — предупреждение, загрузка продолжается (рекомендация). Или ошибка загрузки проекта?
