# Дизайн: шина событий мира и игровые действия

**Issue:** #602 (S542-0) · эпик #542 · **Статус:** предложен, ждёт утверждения владельцем · Основа: решение владельца Р8 (комментарий в #542), В2 из `STAGE2_PLAN-2026-11.md` (шина на мир, доставка в том же кадре в фиксированной точке, конверты почты, межмировое — на почте набора), `WORLD_MESSAGING.md` (почта набора, утверждена 2026-10-19), `HOT_RELOAD_PLAY.md` (#598) · Код — #603 (шина), #604 (действия), #605 (MCP), только после утверждения.

## 1. Что есть сейчас

- **Почта набора** (`ecs_channel.hpp`, `scn::set_channel`, `WORLD_MESSAGING.md` §3).
  - Одна на набор миров.
  - Конверт `ecs::envelope<T>{from, to, seq, payload}`:
    - `from` — имя контекста-отправителя, пустое для внешнего поста (`ecs_channel.hpp:135`);
    - `to` — `ecs::address`.
  - Система пишет в `ecs::outbox<T>&` и читает из `const ecs::inbox<T>&`.
  - Обмен один раз в начале кадра набора, лаг ровно в кадр. В Edit/Pause почта заморожена, Step — один обмен.
- **`ecs::event<T>`** (`ecs_event.hpp`) — список `entt::entity` без данных, внутри мира: `transform_updated`/`hierarchy_updated`.
- **Подписки.** В движке подписок нет, зато в редакторе есть готовый образец:
  - `edt::signal` с RAII `connection` (`edt_editor_events.h:66, 96-142`);
  - только главный поток, слоты вызываются в порядке подписки;
  - подписка и отписка изнутри слота безопасны: обход идёт по снимку списка, снятый слот больше не вызывается, добавленный срабатывает со следующего вызова.
- **Системы мира выполняются последовательно на главном потоке** (`scn_world_context.cpp:90-98`). `ecs::runtime_context` не знает, какая система выполняется (`ecs_invoker.hpp:17-39`). Структурные правки идут через `ecs::entity_changer`/`entity_spawner`, `apply_commands` применяет их после каждой фазы.
- **Ввод.**
  - `inp::input_state` хранит только уровни.
  - `gs::route_input` в стадии `update` кладёт его в ctx контекстов; контекст вне привязки получает нейтральное состояние.
  - В редакторе пристыкованная панель Game привязывает ввод **по наведению курсора** (`bind_item_input`, `edt_game_view_panel.cpp:108`; `edt_input_binding.h:55-66`; роутер выбирает цель по курсору, `inp_input_router.cpp:52-64`).
  - `bind_game_window_input` используется только в полноэкранном режиме игры.
  - Если ни одна область захвата не задета, ввод получают все контексты цели (`WORLD_MESSAGING.md` §6).
  - Действий и раскладок нет. Таблицы имён клавиш для `inp::KEYBOARD_BUTTONS` нет. В редакторе есть одноимённая функция `key_from_name` для ImGui (`edt_main_menu.cpp:7`).
- **Порядок кадра мира:** `input`, `pre_update`, `fixed_update` (×N, N может быть 0), `update`, `post_update`, `transform`, `late_update`. После каждой фазы и каждого шага выполняется `apply_commands`.

## 2. Решение в одном абзаце

У каждого мира своя **шина** — ctx-ресурс в его registry.

- **Точка доставки** одна: сразу после встроенной фазы `update` и её `apply_commands`, до игровых фаз `after(update)` и до `post_update`.
- **В точке доставки:**
  1. события, накопленные с прошлой доставки, идут в порядке отправки;
  2. вызываются подписки;
  3. события становятся видны системам-читателям до следующей доставки.
- **Конверты** — те же `ecs::envelope<T>` с той же семантикой полей.
- **Межмировое** остаётся на почте набора.
- **Действия** — слой поверх шины:
  - раскладка лежит в `res/input/actions.desc`, ссылка на неё — из `project.snkproj`;
  - состояние действий считается в фазе `input` у **владельца действий** набора (§4.3);
  - фронты публикуются на шину событием `inp::action_event`.

## 3. Шина мира (#603)

### 3.1. API

```cpp
layer.events().add<coin_collected>();      // регистрация типа: модуль — в слое, движок — в базе; T копируемый, схема по желанию (§3.7)

void pickup_system(entt::view<...> v, ecs::event_writer<coin_collected>& out) { out.emit({ .coins = 1 }); }
void hud_system(const ecs::event_reader<coin_collected>& in) { for (const auto& e : in.events()) { /* e.payload */ } }

auto c = ctx.subscribe<coin_collected>({ .set = "play" }, [](ecs::bus_context& bus, const ecs::envelope<coin_collected>& e) { ... });

context_manager::emit<T>(set, context, payload);   // вне фаз, главный поток (§3.5)
```

- **Имена.** `event_writer`/`event_reader` не пересекаются с `outbox`/`inbox`: один `T` может быть и событием мира, и письмом набора. `ecs::event<T>` не меняется.
- **Поля конверта** — как у почты:
  - `from` — имя контекста-отправителя, то есть самого мира; пустое для внешнего поста;
  - `to` — `ecs::address{<этот мир>}`;
  - `seq` — номер в доставке.
- **Отладка.** Журнал (§3.7) дополнительно записывает фазу и номер фиксированного шага отправки. Имени системы там нет: `runtime_context` его не знает.
- **Запись типа без регистрации** — ASSERT, как у `outbox::send`.

### 3.2. Точка доставки и окно читателя

```
input → pre_update → fixed_update ×N → update → [apply_commands] → ДОСТАВКА → игровые фазы after(update) → post_update → transform → late_update
```

Почему здесь:

- **«Монета → звук и UI» в одном кадре.** Подбор, урон и конец клипа (#563: `animation_controller_update` работает в `update`) происходят до точки, а реакция на них — в подписке или после точки.
- **Фиксированные шаги.** События всех шагов кадра приходят одной пачкой, в порядке шагов.
- **Честный Step.** Одна точка за кадр: кадр Step = одна доставка.

**Окно читателя.** `event_reader<T>::events()` — события последней доставки. Окно **заменяется только следующей доставкой**: ни Pause, ни Step его не очищают.

- В Play и Step каждая система видит каждое событие **ровно один раз**:
  - системы до точки — в следующем кадре, где была доставка;
  - системы после точки — в этом кадре.
- После последнего кадра Play или кадра Step системы до точки увидят окно в первом кадре после Resume или Step.
- В Pause работают только системы `run_in_edit`. Они видят одно и то же окно в каждом кадре паузы. `event_reader::delivery()` — номер доставки, по нему такие системы отбрасывают повтор.
- **`fixed_update`** выполняется N раз за кадр и увидит одно окно N раз (N = 0 — ни разу). Правило то же, что у почты: перенести событие в компонент в `pre_update`.

**Поздние отправители** (`post_update`…`late_update`) попадают в следующую доставку. Для них лаг в кадр; в отладочной сборке пишется предупреждение один раз на тип.

### 3.3. Порядок и детерминизм

- Системы выполняются последовательно на главном потоке, поэтому **порядок добавления в очередь** уже детерминирован: фаза, шаг, порядок системы в плане, порядок `emit`.
- Перед событиями систем в доставке идут:
  1. внешние посты (как у почты);
  2. события подписчиков прошлой доставки (§3.4).
- `seq` — номер в этом порядке.
- Подписчики одного типа вызываются в порядке подписки, типы — в порядке регистрации, события внутри типа — по `seq`.
- Если у мира появятся параллельные системы, этот раздел придётся пересмотреть. Сейчас этого нет.
- Тест: два прогона дают побайтно равные доставки.

### 3.4. Подписки

- **Механизм** — тот же, что у `edt::signal`, но перенесённый в ядро (`ecs::signal`/`ecs::connection`): RAII-подписка, главный поток, обход по снимку списка. `edt::signal` можно потом перевести на него, это не входит в этот срез.
- **Вызов** — в точке доставки, на главном потоке, вне фаз. Подписчик получает `ecs::bus_context`:
  - имя набора и мира;
  - `const entt::registry&` — читать можно, напрямую менять нельзя;
  - `ecs::entity_changer&` и `ecs::entity_spawner&` мира — правки применяются одним `apply_commands` после всех подписчиков этой доставки;
  - писатели событий — отправленное уходит в **следующую** доставку, повторного входа нет;
  - `outbox` почты набора.
- **Подписка и отписка изнутри колбэка** безопасны (снимок): снятая подписка больше не вызывается, новая срабатывает со следующей доставки.
- **Область.** Подписка модуля действует на миры наборов **его слоя** (`level`, `play`, превью), а не на все слои.
  - Фильтр `{set, world}` необязателен, но рекомендуется: двойник Play повторяет имена миров уровня, поэтому фильтр по одному миру без набора неоднозначен.
  - Пустой фильтр означает все миры всех наборов слоя.
- **Снятие.**
  - `module_context::subscribe` отдаёт RAII-держатель в `m_layer.keep(...)`. Подписка снимается при уничтожении слоя: выгрузка модуля и **перезагрузка кода** (hot reload, `HOT_RELOAD_PLAY.md`).
  - **Перезагрузка данных** (desc, ресурсы, уровень) слой не трогает, подписки остаются.
  - Движок и редактор держат свои `connection` сами.
- Тест: выгрузка → ни одной подписки модуля; перезагрузка кода → подписки нового модуля, старых нет; перезагрузка desc → подписки на месте.

### 3.5. Режимы, внешние посты, лимит

| Режим набора | Доставка | `emit` систем и подписчиков | Окно читателя |
|---|---|---|---|
| Play | каждый кадр | в очередь | заменяется каждой доставкой |
| Step | одна на кадр Step | в очередь | заменяется доставкой Step |
| Pause | нет | в очередь до лимита, доставка — при Resume/Step | не меняется (§3.2) |
| Edit | нет | **отбрасывается** без предупреждения | пусто |

- **Edit отбрасывает**, а не копит. Набор `level` в Edit никогда не доставляет, а системы `run_in_edit` в нём отправляют события (например, `animation_controller_update`). Очередь копилась бы до лимита и сыпала предупреждениями.
- **`context_manager::emit`:**
  - только главный поток и только вне `context_set::update` (ASSERT);
  - пост из задачи идёт через `then_main`;
  - пост во время обновления набора обошёл бы порядок и сломал детерминизм.
- **Лимит** — 1024 события на тип за доставку, как у почты. Лишнее отбрасывается с `egLOG_WARN("scene", …)`, значение меняет `bus.set_event_limit`.
- **Жизнь шины.** Шина живёт и умирает с миром; каждый Play начинается с пустой.
- **Hot reload кода** (`HOT_RELOAD_PLAY.md` §4.4): очередь и окно отбрасываются, в отчёт пишется их число.

### 3.6. Где это в кадре

| Место | Что | Лаг |
|---|---|---|
| стадия `update`: `route_input` | `input_state`, `input_focus`, `action_map` → ctx | 0 |
| `begin_frame_channel` набора | почта N-1 → inbox N | 1 кадр (почта) |
| фаза `input`: `inp::update_actions` | `action_state` у владельца, `action_event` → шина | 0 |
| фазы `input`…`update` | `event_writer` → очередь | — |
| **точка доставки** | подписчики, окно `event_reader` | 0 для подписчиков и систем после точки; 1 кадр для систем до неё |
| `post_update`…`late_update` | читают окно; поздние `emit` → следующая доставка | 1 кадр для поздних |

### 3.7. Схема и MCP (#605)

- **Схема.** `events().add<T>(schema?)`. Событие со схемой видно в MCP с payload, без схемы — только тип, `seq`, `from`, фаза и кадр.
- **Журнал** — кольцо последних доставленных событий на мир, по умолчанию выключено. Редактор включает его в мирах Play, N = 256.
- **Команды MCP**, категория агента `read`, обе только для чтения, `expose_as_tool`, на главном потоке:
  - `world.events {world, set?, type?, last?}`: `last` ≤ 256, payload одного события ≤ 4 КБ JSON, больше — обрезается с пометкой `truncated`;
  - `input.actions {world?}`: состояние каждого действия, кадр последнего фронта, имя мира-владельца.
- **Вне Play** — ошибка `"no Play session: world events exist only while Play runs"`.

## 4. Игровые действия (#604)

### 4.1. Данные

`project.snkproj`:

```json
{ "input_actions": "res://input/actions.desc" }
```

Неверный тег (не `res://`, вне проекта) — **ошибка загрузки манифеста**, как у `start_scene` (`prj_manifest.cpp:277-282`).

`res/input/actions.desc`:

```json
{
  "__type": "input_actions", "__version": 1,
  "actions": [
    { "name": "MoveLeft", "bindings": [ { "key": "A" }, { "key": "LEFT" } ] },
    { "name": "Restart",  "bindings": [ { "key": "R" } ] },
    { "name": "Fire",     "bindings": [ { "mouse": "LEFT" } ] }
  ]
}
```

- **Имена клавиш** — канонические имена перечислителей `KEYBOARD_BUTTONS`/`MOUSE_BUTTONS`.
  - Это **физические позиции в раскладке US**: на AZERTY `"A"` — клавиша, где на US стоит A. Так задумано в `inp_keyboard_event.hpp:17-18`.
  - Синонимов в первом срезе нет. Служебные `LAST` и `COUNT` именами не являются.
  - Функции — `inp::key_code_from_name`/`key_code_name`, чтобы не путать их с ImGui-функцией `key_from_name` редактора.
  - Тест: у каждого перечислителя до `COUNT` есть имя, имена не повторяются.
- **Ошибки внутри файла** (неизвестная клавиша, пустое или повторное имя действия) — предупреждение с путём в JSON. Привязка пропускается, загрузка продолжается (вопрос 4).
- **Нет поля** — действий нет. Запрос неизвестного действия даёт предупреждение один раз на имя и возвращает `false`.
- **`input_actions_desc`** — desc со схемой: инспектор, `asset.query`, живая перезагрузка через кэш ресурсов. Шаблон проекта получает файл с примером и поле манифеста.

### 4.2. Состояние действий

- **Раскладка.** `gs` (там же, где `route_input`) держит `res_handle<input_actions_desc>` и `inp::action_map` (имя → id → привязки). `route_input` кладёт `std::shared_ptr<const inp::action_map>` в ctx контекстов.
- **Система движка `inp::update_actions`** (фаза `input`, только у владельца действий, §4.3):
  - вход: `input_state`, признак «ввод привязан» и `action_map`;
  - выход: ctx-ресурс `inp::action_state` с `held`/`pressed`/`released` на действие и `inp::action_event` на шину.
- **«Фокус» — это привязка ввода, а не фокус окна:**
  - пристыкованная панель Game — пока курсор над ней (`bind_item_input`);
  - полноэкранный режим — всё окно (`bind_game_window_input`).
- **Потеря привязки** (курсор ушёл с панели, открыт попап): все действия отпускаются, по каждому зажатому — один фронт `released`.
- **Возврат привязки с уже зажатой клавишей** не даёт `pressed`. Действие «взводится» только после отпускания, поэтому `Fire`/`Restart` не срабатывают заново, когда курсор возвращается на панель с зажатой клавишей.
- **Pause:** система не работает, состояние замирает.
- **Step:**
  - если ввод в кадре Step не привязан (Step с панели инструментов, курсор не над Game view), состояние берётся **замороженным** с паузы, без фронтов;
  - если привязан (горячая клавиша при курсоре над Game view), считается как обычно.
- **Edit** (набор `level`): действия не считаются, система не `run_in_edit`.
- **После hot reload кода** прошлое состояние берётся равным текущему. Ложных `pressed` за зажатые клавиши нет.
- **API:**

  ```cpp
  inp::action_id k_restart = actions.id("Restart");   // один раз; a.pressed("Restart") тоже есть, медленнее
  void restart_system(const inp::action_state& a) { if (a.pressed(k_restart)) { ... } }
  ```

### 4.3. Владелец действий набора

Если ни одна область захвата не задета, ввод получают все контексты цели. Тогда 3D-мир и UI-мир оба выдали бы `action_event{Restart}`. Поэтому **действия считает один мир набора**:

- **рекомендация (вопрос 5):** мир с `world_desc.owns_actions = true`;
- если такого флага нет ни у одного мира — мир с наименьшим id;
- два мира с флагом — ошибка загрузки уровня в лог, побеждает меньший id.

Остальные миры видят `action_state` владельца через почту набора или blackboard, если им нужно. В первом срезе это не автоматизируется.

### 4.4. Действия и `fixed_update`

Фиксированных шагов за кадр бывает 0 (фронт `pressed` потерялся бы) или N (фронт виден N раз — двойной прыжок). Поэтому:

- для фиксированных систем есть отдельный ctx-ресурс `inp::fixed_action_state` (вопрос 6);
- фронт `pressed`/`released` **защёлкивается** до первого фиксированного шага и виден только в нём;
- при 0 шагах он переносится в первый шаг следующего кадра;
- `held` во всех шагах равен уровню кадра.

### 4.5. Известные ограничения

- **Нажатие и отпускание внутри одного кадра** между опросами теряется: `input_state` хранит уровни. Если понадобится, `ecs_input_manager` будет копить счётчик нажатий за кадр.
- **Автоповтор клавиши** не отражается: в `KEY_ACTION` нет `REPEAT`, и действие видит только `held`.
- **Позже, по Р8:** модификаторы (`Ctrl+R`), оси, геймпад, переназначение в UI. `bindings` — массив объектов, поэтому новые поля добавляются без смены версии.

   - Тесты: фронты, потеря и возврат привязки, Pause/Step, 0 и N фиксированных шагов, два мира с вводом, перезагрузка раскладки, hot reload.

## 6. Риски

- **Две системы сообщений.** Правило выбора пишется в API-доке и в `WORLD_MESSAGING.md`:
  - внутри мира, в этом кадре — шина;
  - между мирами — почта;
  - состояние — blackboard.
- **Поздние отправители** получают лаг в кадр, есть предупреждение. Если понадобится, добавится вторая точка (после `late_update`).
- **Подписчик с тяжёлой логикой** выполняется на главном потоке вне плана систем. Профилирование показывает его как `bus:<тип>`.
- **Параллельные системы в будущем** потребуют пересмотреть §3.3.

## 7. Вопросы владельцу

1. Одна точка доставки сразу после `update` (рекомендация) — или после каждой фазы (читателям нужны курсоры)?

3. **Ввод.** Действия отпускаются, когда ввод не привязан (пристыкованная Game — по наведению, полноэкранная — всё окно). Возврат с зажатой клавишей не даёт `pressed`. Step без привязки берёт состояние с паузы (рекомендация).
4. Ошибки внутри `actions.desc` — предупреждение, загрузка продолжается; неверный тег в манифесте — ошибка, как у `start_scene` (рекомендация)?

8. **Окно читателя** заменяется только следующей доставкой и не очищается в Pause/Step (рекомендация). Или очищается при паузе?
