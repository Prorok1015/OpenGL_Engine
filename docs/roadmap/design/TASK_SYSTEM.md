# Дизайн: task_system, дополнение к ADR-10 (эпик #17)

**Issue:** #17 (stories #132–#135) · **Статус:** утверждён владельцем 2026-10-18 (решения в конце) · Основа: `CHIMERA_ROADMAP.md` ADR-10/ADR-11; `STAGE_D_PLAN.md` §1 #17, §5 (волна 1 после PR-5 #109; `job_service` сначала поверх `std::async`); EPIC-28 (#166–#168); `DISTRIBUTION.md` (сборка `game.dll` фоновой задачей, hot reload); `EDITOR_FRAMEWORK.md` (пишется параллельно: `job_service` #139 оборачивает API отсюда); BL-006

## 1. Как устроено сейчас

**Потоки** (кроме главного):
- `async_adapter_worker`: один `std::thread` поверх `asio::io_context` (`res_adapter_worker.cpp:15-33`). Ставится в `core_module.cpp:79`. Интерфейс: `post/start/stop/is_stopped` (`res_adapter_worker_base.hpp`).
- `vfs_resolver`: свой `io_context` и поток на каждый протокол. Их два: `res://` и `memory://` (`res_system.cpp:24-33`, `res_vfs_resolver.cpp:27-43`). Чтение файла постится в этот поток (`:122`), запись тоже (`:144`). Там же `file_watcher` раз в 500 мс опрашивает диск (`res_file_watcher.h:47-55`).
- Редактор создаёт потоки через `std::async`. Импорт: `edt_editor_system.cpp:200-203`, лямбда захватывает `this`. Экспорт: `edt_asset_export_dialog.cpp:158`, прогресс в самодельном `export_progress` с atomic-полями (`edt_asset_exporter.h:13-19`).
- Своего пула нет. `core_thread_utils.hpp:11` даёт только `set_name`, и эта функция не `inline`: второе включение заголовка нарушит ODR.

**Как грузятся ресурсы.** `require<T>` атомарно находит или вставляет блок в кеш (`res_system.h:235-244`), и загрузку запускает только тот, кто блок создал (`:325-327`). Дальше resolve идёт в поток vfs → `raw_data_block->then` → `post_adapter_work(adapter_cb)` → `deserialize` на adapter-потоке (`:287-318`). `require_sync` выполняет adapter_cb на вызывающем потоке после `wait()` (`:310-313`).
- **Где доставляется завершение.** `res_control_block::then/finish` вызывает колбэки на том потоке, который завершил блок, то есть на worker'е (`res_control_block.hpp:58-104`). BL-006 по факту исправлен: `then` берёт lock, `finish` публикует данные под lock. Публичный `res_handle::then` (`res_resource_handle.hpp:47-52`) в продакшене зовётся только из `warmup` (`res_system.h:188`). Все остальные опрашивают `is_ready()` каждый кадр: `texture_manager::require_texture` (`rnd_texture_manager.cpp:6-40`), `poll_level_load` и `poll_pending_desc` в редакторе.
- **Hot reload.** `signal_changed` вызывает watcher'ов прямо на потоке vfs (`res_system.h:92-105`). `hot_reload_manager` сам складывает теги в очередь под mutex и разбирает её в `tick()` на главном потоке (`scn_hot_reload_manager.cpp:53-57, 76-83`). По сути это самодельная main-thread очередь.
- **`require_sync`.** В продакшене 17 вызовов (41 в тестах). Два из них внутри адаптеров, то есть на worker-потоке: `desc_adapter_t.cpp:69` и `scn_worldwrap_adapter.cpp:36`. Остальные 15 на главном потоке: level_manager, hot_reload, prefab assembly, 10 в редакторе.
- **Найденный дедлок.** Дочерний ресурс C грузится асинхронно, и его родитель P тоже уже стоит в очереди асинхронно (блок P в кеше, `is_new=false`). Тогда `require_sync(P)` в адаптере C ждёт в `get_sync()` на единственном worker'е, а `adapter_cb` для P стоит в очереди того же worker'а. Ожидание вечное. Комментарий в `desc_adapter_t.cpp:44-45` признаёт риск, но `thread_local loading_stack` ловит только циклы внутри одного стека.

**GL.** Объекты создаются только на главном потоке: `drv->create_texture` в пассах (`rnd_opaque_pass.cpp:57`, `rnd_z_prepass.cpp:49`) и при опросе готового `texture_desc` (`rnd_texture_manager.cpp:31-36`). Адаптеры GL не трогают, и это правило сохраняется (ADR-11).

**Отмены нет нигде.** Закрытие диалога экспорта блокирует UI до конца экспорта (`edt_asset_export_dialog.cpp:12-13`). Разрушение `async_import_token` ждёт `std::future` до конца импорта.

**Кадр.** Встроенные стадии `begin…present` (`app_frame_stage.h:25-34`). Модули добавляют свои через `add_stage(name, anchor, side)` (`:73`). Editor UI работает в стадии `ui` (`edt_editor_init.cpp:22`).

## 2. Решение

**Где лежит:** `ds::task_system` в `core/core/common/ds/` (путь в #132/#133 поправить; после #109 это `<snk/common/ds/…>`). Это сервис `app_data_storage`. Создаётся в `core_module` до `resource_system`, разрушается после него.

**Пул (#132).** Две полосы на `asio::thread_pool`, как в ADR-10:
- `lane::compute`: `clamp(hw-1, 2, 8)` потоков, для адаптеров и импорта.
- `lane::io`: 2 потока под блокирующие операции: файлы, процессы, позже HTTP.

Приоритетов в v1 нет. Ресурс, нужный «сейчас», ждёт `require_sync` на главном потоке, а пул не блокируется, поэтому приоритеты не нужны. Третий режим `policy::manual` работает без потоков: тест сам вызывает `run_one(lane)` и `drain_main(budget)`. Потоки получают имена `snk-compute-N` и `snk-io-N`.

**Задача и handle (#132).**
```cpp
template<class T> task_handle<T> task_system::run(lane, task_desc, std::function<T(task_context&)>);
struct task_context { std::stop_token stop; void set_progress(float, std::string_view = {}); };
// task_handle<T>: status() {pending,running,ready,error,cancelled}; progress(); progress_text();
//   cancel() → request_stop; error() как значение; get() только после завершения и только на главном;
//   then_main(const ds::lifetime&, fn(task_result<T>&)) — колбэк строго на главном потоке.
task_handle<void> task_system::when_all(span<handle_base>, lane, fn);   // продолжение на пуле, без ожидания
```
- Отмена кооперативная: тело задачи само проверяет `ctx.stop`. Отменённая до старта задача не запускается вообще.
- `task_desc{name, category, visible}`. `task_system::snapshot()` возвращает видимые задачи для панели задач редактора и для игрового UI.
- `wait()` разрешён только на главном потоке. На потоке пула assert `!task_system::on_worker()`.

**Lifetime-токены (#133).** `ds::lifetime` — член объекта-владельца, внутри у него `shared_ptr<state>`. `then_main(lifetime, fn)` хранит `weak` и проверяет его на главном потоке перед вызовом. Владелец умирает тоже только на главном, поэтому проверка без гонки.
- Опция `cancel_on_destroy`: деструктор `lifetime` отменяет привязанные задачи.
- Тело задачи не трогает владельца: в задачу передаются копии входных данных, а владельца трогает только продолжение на главном потоке.
- `module_loader` держит `lifetime` на каждый модуль. Перед выгрузкой `game.dll` при hot reload задачи модуля отменяются, затем `wait_idle(module)`: код задачи живёт в DLL.

**Main-thread очередь.** `post_main(fn, main_class)` с двумя классами:
- `general`: бюджет `tasks/main_budget_ms` (по умолчанию 2 мс), но не меньше одного элемента за кадр, чтобы очередь не стояла.
- `gpu_upload`: не больше N элементов за кадр, это лимит загрузок из ADR-11.

Очередь дренирует стадия `tasks` (`add_stage("tasks", input, after)`). Результаты видны `update` и `ui` в том же кадре. При завершении работы порядок такой: `request_stop` всем задачам → join пула → остаток очереди выбрасывается без вызова колбэков.

**Ресурсы как граф (#134).**
- `adapter_worker_base` заменяется полосой `compute`; `async_adapter_worker` и тестовый `inline_worker` уходят, тесты переходят на `manual`. Потоки vfs пока остаются, перевод на `lane::io` — отдельной задачей позже.
- Адаптер получает метод `collect_dependencies(tag, bytes) → vector<res_dep{tag, type_id}>` (по умолчанию пусто). `deserialize(tag, bytes, const res_deps&)` получает готовые зависимости и сам ничего не ждёт.
- Конвейер: resolve → `collect` (compute) → `require` каждой зависимости асинхронно → `when_all` → `deserialize` (compute). `desc_adapter_t` и `worldwrap_adapter` переходят на `__parent` как зависимость.
- **Циклы.** Граф ожиданий хранится в `res_system` под mutex. Перед добавлением ребра X→Y проверяется, достижим ли X из Y по ещё не готовым узлам. Если да, все блоки цикла завершаются ошибкой `dependency cycle`. Ограничение глубины 32 сохраняется. Так ловятся и циклы между независимыми корнями, которые `thread_local`-стек не видел.
- **Мульти-ресурс.** Публичный `res::when_all(handles…)` поверх того же графа. Редактору и уровню больше не нужна цепочка `require_sync`.
- **Доставка.** `res_handle::then(lifetime, cb)` вызывает колбэк на главном потоке. Внутреннее `res_control_block::then`, которое срабатывает на любом потоке, переименовывается в `on_settled` и остаётся только для конвейера. Колбэки watcher'ов из `signal_changed` идут через `post_main`, и очередь `hot_reload_manager` упрощается.
- **`require_sync`** остаётся только для главного потока; на пуле стоит assert. Он безопасен, потому что адаптеры больше не блокируются, а у конвейера нет шагов на главном потоке.
- **GL только на главном потоке.** Тело задачи не трогает `drv`/GL; в отладочной сборке GL-драйвер проверяет поток в `create_*`. GPU-объекты создают менеджеры рендера, опрашивая готовые handle (как сейчас), с лимитом через `gpu_upload`. Это стыкуется с ADR-11 (handle-индирекция текстур).

**Импорт, экспорт, сборка (#135).**
- Импорт: `import_background` становится задачей `compute` с прогрессом по мешам и текстурам и проверкой `stop` между ними. `finalize_on_main` переезжает в `then_main(editor lifetime)`. При отмене удаляются уже записанные `memory://`-теги (`import_intermediate::all_tags`).
- Экспорт: `export_progress` заменяется на `task_context`. При отмене недописанные файлы удаляются.
- Сборка `game.dll` (DISTRIBUTION S5): задача `io`, процесс `cmake --build` через `boost::process` v2 на asio. Отмена завершает дерево процессов. Строки вывода пачками уходят через `post_main` в панель problems (#24).

**`job_service` редактора (#139).** У `job_service::start(task_desc, fn(task_context&))` сигнатура как у `task_system::run`. Первая версия — адаптер поверх `std::async`: `std::stop_source`, atomic-прогресс, опрос в стадии `ui`. После #132 меняется только backend. `job_service` добавляет поверх отображение: панель, тосты, привязку к документу.

## 3. Пересечение с EPIC-28 (#166–#168)

#134 и US-28-1…3 правят одни и те же структуры в `res_system.h`: `m_cache`, `find_or_insert_cache`, `signal_changed`, `register_alias`. Узел графа зависимостей — это `{tag, type_id}`: `world_desc` зависит от `__parent` как от `desc_base`. Значит, составной ключ нужен до графа. Порядок: #166 → #167 → #168 одним PR **до** #134, то есть вытянуть EPIC-28 из M4 в волну 1. #132/#133 не трогают `resource` и идут параллельно с EPIC-28.

## 4. Шаги (каждый — отдельный PR после PR-5 #109 и #174, CI зелёный включая TSan)

1. **#132:** `task_system` (2 полосы + `manual`), `task_handle`/`task_context`, `when_all`, `post_main` с бюджетами, стадия `tasks`. `core_thread_utils` делается `inline`. Тесты в режиме `manual`: порядок; отмена до и во время выполнения; бюджет на подставных часах; минимум один элемент за кадр; сброс очереди при завершении.
2. **#133:** `ds::lifetime`, `then_main(lifetime)`, `cancel_on_destroy`, привязка к модулю. Тест: колбэк не вызывается после разрушения владельца.
3. **EPIC-28 #166–#168:** составной ключ, `signal_changed` по всем типам, alias до построения ключа.
4. **#134a:** адаптеры на `lane::compute`, `res_handle::then(lifetime)` на главном потоке, watcher'ы через `post_main`, тесты на `manual` вместо `inline_worker`. Реализовано: `resource_system(ds::task_system&)`; деструктор отменяет и ждёт свои задачи; `res_handle::get_sync()` в режиме `manual` сам гоняет очередь вместо блокировки (как `task_handle::wait()`); `signal_changed` сразу вытесняет кеш, а watcher'ов зовёт позже на главном потоке из актуального списка; индекс `тег → type_id` в кеше и в pinned.
5. **#134b:** `collect_dependencies`, граф ожиданий и циклы, миграция `desc_adapter_t` и `worldwrap_adapter`, assert для `require_sync`. Регрессионный тест на описанный дедлок (C и P в очереди, 1 поток), цикл между двумя корнями, `when_all` с ошибкой зависимости. Реализовано: `res_dep` создаётся через `res::make_dep<T>(tag)`, `deserialize(tag, bytes, res_deps)` по умолчанию зовёт старую перегрузку без зависимостей; `require_sync` теперь запускает тот же асинхронный конвейер и ждёт блок на главном потоке; `res_handle::wait()` больше не помогает с очередью на воркере (ждать там нечего, на воркере assert); граф ожиданий в `res_system.cpp` (`wait_graph`), цикл — ошибка `dependency cycle: a -> b -> a` у всех блоков цикла, глубина цепочки ≤ 32 рёбер; `res::when_all(system, handles...)` отдаёт `res_handle<when_all_result>` и ждёт все блоки, чтобы упавшая зависимость не отменяла доставку остальных. `#include` шейдеров в `shader_config::load` остаётся на главном потоке (это не адаптер), поэтому на зависимости не переведён.
5a. **US-17-5 (#263, #232):** обратные рёбра графа `тег зависимости → теги, построенные из него` пишутся в `collect_stage` до запроса зависимостей. `signal_changed(тег)` обходит их в ширину и транзитивно (посещённые не повторяются, цикл не зацикливает), вытесняет кеш всех найденных тегов под одним замком и доставляет watcher'ов одной задачей на главном потоке на сигнал: родители раньше детей (Кан), каждый тег пачки один раз. Ребро заменяется при новой загрузке тега. Рёбра выгруженного тега (запись кеша истекла или вытеснена) удаляются при сигнале и при росте графа (#311): держатель, построенный через него, наследует его зависимости, рёбра к самому тегу остаются. Блок, который грузится во время сигнала, вытесняется и грузится заново; его держатели достраивают его сами. Хвосты #134: ключ кеша берёт тип из адаптера (`desc_base` и конкретный desc делят один блок); `register_alias` и устаревший комментарий в `hot_reload_manager` — см. #302 и правку комментария.
6. **#135:** импорт и экспорт как задачи с отменой и прогрессом через `job_service`, если #139 уже готов, иначе напрямую. `std::async` из редактора убирается.

TSan (`ci-linux-tsan`, `build.yml:169`; `tsan.supp` пуст) прогоняет стресс-тесты на реальных потоках: `then_main` против разрушения владельца, отмена против завершения, конкурентный `require` одного тега с зависимостями. Логику планировщика проверяют только детерминированные тесты в режиме `manual`.

## 5. Риски

- **#134 — самый рискованный шаг.** Он меняет контракт всех адаптеров. Новый метод по умолчанию возвращает пусто, поэтому остальные адаптеры работают без изменений, а переводятся только два с `require_sync`.
- **Блокировка главного потока.** 15 вызовов `require_sync` на главном остаются. Их перевод на `when_all` — отдельная работа редактора, не этот эпик.
- **Откат отмены импорта.** `memory://`-записи асинхронны (`res_vfs_resolver.cpp:144`), удалять их надо после завершения записи.
- **Выгрузка `game.dll` при живых задачах.** Нужен строгий `wait_idle(module)`, иначе задача продолжит выполнять код выгруженной DLL.
- **Обход правила «тело задачи не трогает владельца».** Ревью и `then_main` как единственный публичный путь к владельцу.
- **Конфликт с параллельным #212/ADR-11 по `texture_manager`.** Класс `gpu_upload` вводится здесь, а потребитель появляется в EPIC-65.

## 6. Вопросы владельцу (рекомендации)

1. Пул: `asio::thread_pool` с двумя полосами (compute `clamp(hw-1,2,8)`, io 2), приоритетов в v1 нет, есть режим `manual` для тестов? **Рекомендация: да.**
2. Очередь главного потока: стадия `tasks` после `input`, бюджет 2 мс (cfg) + минимум 1 элемент + класс `gpu_upload` с лимитом N? **Да.**
3. EPIC-28 #166–#168 вытянуть в волну 1 и сделать до #134? **Да.**
4. Правило: у конвейера ресурсов нет шагов на главном потоке, GL создают менеджеры рендера опросом готовых handle, `require_sync` разрешён только на главном потоке (assert на пуле)? **Да.**
5. Распространение hot reload по обратным рёбрам графа (родитель изменился → дети вытесняются): в #134 или отдельной story? **Отдельной story после #134b.**
6. Отмена импорта удаляет уже записанные `memory://`-теги, без «транзакции до finalize»? **Да, по `all_tags`.**
