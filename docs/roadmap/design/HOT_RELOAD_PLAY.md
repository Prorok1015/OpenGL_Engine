# ADR: hot reload игрового модуля во время Play (вариант C)

**Issue:** #598 (S541-0) · эпик #541 · **Статус:** предложен, ждёт утверждения владельцем · Отменяет: решение 3 владельца от 2026-10-18 в `DISTRIBUTION.md` («Hot reload во время Play: Stop → reload → Start») и порядок #222 для Play · Основа: `DISTRIBUTION.md` §4–§5, `MODULE_LAYER.md`, `WORLD_MESSAGING.md` §1, `SPIKE-218-entt-dll.md`, `STAGE2_PLAN-2026-11.md` §2.6 · Код по ADR — #599 (сериализатор), #600 (reload в Play), #601 (несовместимые изменения и откат); писать его можно только после утверждения ADR.

## 1. Решение

Во время Play пересборка `game.dll` не останавливает игру:

1. снять **снимок живых миров** набора `"play"` в desc (данные, без указателей на код);
2. уничтожить слой старого модуля и выгрузить старую DLL (как сейчас);
3. загрузить новую DLL и создать её слой (как сейчас);
4. **восстановить** набор `"play"` из снимка в слое нового модуля;
5. Play продолжается с того же кадра, в той же паузе, с тем же временем и seed.

Правила владельца (#541) остаются без изменений:

- **поля систем не сохраняются**: системы создаются заново;
- **компоненты без схемы не переживают reload**: они перечисляются в отчёте, в лог пишется предупреждение.

Состояние игры живёт в компонентах и ресурсах со схемой. Всё остальное — производные данные или состояние кода, и после reload оно строится заново.

## 2. Как устроено сейчас

- **Вход.** `project_module_host::reload(module, m_swap_gate.hooks())` (`edt_editor_system.cpp:532`). Её вызывает `game_reloader` через `next_frame`, то есть **между кадрами, на главном потоке**. Шаги (`core_project_modules.cpp:480-560`):
  1. `prepare` — новая копия загружается рядом со старой и проверяется;
  2. `before_swap`;
  3. `unload` старой;
  4. `load` новой;
  5. если загрузка не удалась — откат на `previous()`;
  6. `after_swap`.
- **Где навязан Stop → reload → Start.** `edt::module_swap_gate::before_swap` первым вызывает Play-хук. `play_session::before_module_swap` делает `stop(stopped_for_reload)` (`edt_play_session.cpp:224-230`), а `after_module_swap` делает `start(module_reloaded)` и при необходимости `pause()` (:232-242). Причина в комментарии гейта: `destroy_layer` забирает набор `"play"` вместе со слоем (`scn_context_manager.cpp:75-86`).
- **Что сохраняется сейчас.** Только редактируемый документ: `detach_from_game_layer` строит JSON уровня из `world_descs` (`edt_level_controller.cpp:162-186`). Play после reload собирается заново из копий desc документа, поэтому время, счёт и runtime-сущности теряются.
- **Чего нет.** Пути registry → desc нет (`WORLD_MESSAGING.md` §1: «Сериализация живой сущности отсутствует»). Его добавляет #599.

## 3. Последовательность (вариант C)

Шаги 1–4 из `DISTRIBUTION.md` §4 (сборка, копия в `.cache/modules`, `prepare`, отказ при неудачной проверке) не меняются. Меняются шаги 5–7:

| Шаг | Кто | Что |
|---|---|---|
| 5a | `module_swap_gate::before_swap` → `play_session::before_module_swap` | Проверить, что reload можно делать сейчас (§4). Снять снимок набора `"play"` (§5), сохранить его диагностическую копию на диск. Запомнить состояние редактора, привязанное к сущностям: выделение и камеру Play — по `snap_id`. Набор `"play"` уничтожить явно, **до** уничтожения слоя. |
| 5b | `follow_game_layer_change(before)` | Как сейчас: уровень документа уходит в JSON. Play уже не активен, поэтому `stop(user)` больше не срабатывает. |
| 6 | `module_loader::unload` | Как сейчас: `stop_tasks` → слой уничтожается целиком → FreeLibrary. |
| 7 | `load` + `register_content` | Как сейчас. Новый модуль заново регистрирует системы, типы, схемы, спавнеры, типы сообщений и подписки шины (#602). |
| 8a | `after_swap` → `attach_to_game_layer` | Как сейчас: уровень документа загружается в новый слой. |
| 8b | `play_session::after_module_swap` | Вместо `start()` — `restore(snapshot)` (§6). Успех: Play продолжается, пользователь видит отчёт. Неудача: откат (§9). |

Снимок — это **только данные**: дерево JSON (`boost::json::value`) с именами типов в виде строк. В нём нет объектов desc типов модуля (их vtable в старой DLL), `std::function`, `std::any` и `entt::entity`. Поэтому после FreeLibrary он остаётся валидным.

## 4. Когда reload разрешён

- Только между кадрами, на главном потоке, вне `context_set::update`. Это уже так: вызов идёт через `next_frame`. Restore проверяет это ASSERT-ом.
- Буферы команд пусты: `apply_commands` выполняется после каждой фазы (`scn_context_set.cpp:159-168`). Снимок это проверяет; непустой буфер — ошибка, а не потеря данных.
- **Reload откладывается** (не отменяется), пока:
  - загружается уровень — существующий `start_blocker` (`edt_editor_system.cpp:921-925`);
  - идёт смена сцены (#564), когда она появится. Это закрывает риск «hot reload посреди смены сцены» (`STAGE2_PLAN-2026-11.md`, раздел рисков);
  - выполняются задачи слоя с флагом «не прерывать», если такой флаг появится. Сейчас задачи останавливает `stop_tasks`, а незавершённые попадают в отчёт.
- Отложенный reload выполняется в первом кадре, когда условие снято. Пользователь видит статус «reload ждёт окончания загрузки/перехода».
- Pause и Step не мешают reload. Режим, `pending_steps` и `frames_run` входят в снимок.

## 5. Снимок

### 5.1. Формат

Один документ на набор:

```json
{
  "__type": "play_snapshot", "__version": 1,
  "module": { "name": "game", "copy": "<pid>-<n>" },
  "set": { "mode": "pause", "pending_steps": 0, "frames_run": 1234, "time_scale": 1.0, "seed": 42 },
  "blackboard": [ { "key": "...", "type": "...", "value": { } } ],
  "worlds": [ {
    "name": "main", "kind": "play", "systems": [ "game::move", "..." ],
    "time": { "world_time": 20.5, "fixed_time": 20.48, "fixed_accumulator": 0.004 },
    "rng": { "state": "…", "sequence": "…" },
    "ctx": [ { "type": "game::score", "value": { "points": 17 } } ],
    "entities": [
      { "snap": 1, "node_path": [ 4021, 77 ], "components": { "scn::local_transform": { }, "game::health": { "hp": 3 } } },
      { "snap": 2, "components": { "game::bullet": { "owner": { "$snap": 1 } } } }
    ]
  } ],
  "report": { "dropped_components": [ ], "dropped_ctx": [ ], "mail_in_flight": 0, "stopped_tasks": 0 }
}
```

- Это тот же сериализатор и тот же формат сущностей, что у #599. Им же пользуется #552.
- Типы компонентов записываются по имени регистрации в слое (`ecs::component_registry`), а не по `type_hash`. Хэш не обязан совпасть между сборками, если тип переименовали или перенесли.
- Время, `fixed_stepper` и `ecs::rng` берутся из `world_context` и ctx (`scn_world_context.cpp:12-45`). `rng` восстанавливается через `ecs::rng::from_state`.

### 5.2. Три категории компонентов

| Категория | Примеры | В снимке | После restore |
|---|---|---|---|
| **Со схемой** | `local_transform`, компоненты модуля со схемой, `res_handle` (как тег) | значение по схеме | десериализуется по схеме **нового** модуля |
| **Производные** | `world_transform`, `bone_matrices_component`, `mesh_component` (смещения в буферах геометрии), записи `rnd::material_instance_cache` | нет | пересчитываются: restore испускает `hierarchy_updated`/`transform_updated` для всех сущностей и вызывает restore-хуки спавнеров движка, которые строят производные данные из тегов |
| **Без схемы** | любой тип модуля без схемы | нет, только имя типа и число сущностей в `report` | теряются: предупреждение в логе и уведомление |

Производные компоненты движок помечает при регистрации явно; это делает #599. Поэтому «нет схемы» у движкового типа не путается с «производный». Новый движковый компонент без схемы и без пометки попадает в отчёт и ловится тестом (§11).

**GPU-ресурсы.** Сырых GL-хэндлов в компонентах сцены нет. GPU-данные держат кэши движка (геометрия, `material_instance_cache`) по `res::tag`. Кэши живут в базе, а не в слое, и при reload не сбрасываются. Restore запрашивает ресурсы по тегам через `res::resource_system` — это попадание в кэш, без повторной загрузки с диска. Desc-ресурсы **типов модуля** уничтожаются вместе со слоем и загружаются заново по тегам уже в новом слое.

### 5.3. Ресурсы ctx, blackboard, почта, шина

- **Ресурсы ctx** (`reg.ctx()`): тип со схемой сохраняется, как компонент. Пример — счёт игры в ресурсе `game::score`. Тип без схемы теряется и попадает в отчёт. Движковые ресурсы времени, `rng` и ввода не сериализуются как значения: время и `rng` идут отдельными полями (§5.1), `input_state` пишет роутер в следующем кадре.
- **Blackboard набора** (`set_channel::blackboard()`): значения со схемой сохраняются, без схемы — в отчёт.
- **Почта набора в полёте** (outbox кадра N ждёт обмена в N+1) **отбрасывается**. В отчёте — число отброшенных конвертов. Почта живёт один кадр, а её типы регистрирует новый модуль. Перенос почты не стоит отдельного кода.
- **Шина мира** (#602) доставляет события в том же кадре, поэтому между кадрами её очередь пуста и терять нечего. Подписки регистрирует новый модуль в `register_content`.
- **Хранилище слоя модуля** (данные, переживающие смену сцены по #564) уничтожается со слоем. Правило то же: значения со схемой — в снимок, остальное — в отчёт. До #564 хранилища нет, правило записано заранее.
- `ecs::event<T>` (очереди сущностей без данных, например `transform_updated`) не сохраняются. Между кадрами они уже обработаны, а restore испускает их заново (§5.2).

## 6. Идентичность сущностей и ссылки

**Runtime-сущности без `node_id`.**

- Каждая сущность в снимке получает `snap` — плотный номер, локальный для этого снимка. Он не хранится в мире и после restore больше не нужен.
- Сущности уровня (`node_id_component`) дополнительно пишут `node_path`. При restore компонент ставится с тем же путём, и `node_index` перестраивается своими хуками, так что `ecs::entity_ref{context, path}` продолжают работать.
- Порядок сущностей в снимке — порядок хранилища `entt` на момент снимка. Restore создаёт сущности в том же порядке.

**Ссылки между сущностями.**

- В схеме нужен вид поля «сущность» (#599). Сериализатор пишет `{"$snap": N}`; пустая ссылка или ссылка на мёртвую сущность пишется как `null`.
- Restore идёт в два прохода. Сначала создаются все сущности и строится таблица `snap → entt::entity`. Затем десериализуются компоненты, и ссылки разрешаются по таблице.
- Сырые `entt::entity` в движковых компонентах переназначаются так же: `parent_component`, `children_component`, `skinning_component::skeleton_entity`. Это поля вида «сущность» в их схемах.
- `ecs::entity_ref{context, path}` пишется как есть: путь стабилен.
- Ссылки, которые лежат вне компонентов и ресурсов со схемой (поля систем, лямбды задач, кэши модуля), не переживают reload — это следует из правила «поля систем не сохраняются».

**Редактор.** Выделение, инспектор и камера Play ссылаются на сущности. Они запоминаются по `snap` и после restore переводятся по таблице. Не нашлось — выделение снимается без ошибки.

## 7. Удалённая система, тип или поле

Restore сверяет снимок со слоем нового модуля:

| Что пропало | Поведение |
|---|---|
| Тип компонента или ресурса ctx | Компонент не ставится, сущность остаётся. Явное предупреждение `egLOG_WARN("hot_reload", …)` с именем типа и числом сущностей, запись в отчёте, уведомление в редакторе. Тихого переиспользования нет. |
| Система из списка мира | Мир создаётся без неё. Предупреждение и запись в отчёте. Новые системы модуля, которых не было в снимке, **не** добавляются: список систем мира — это данные Play (`world_desc.systems`), и он меняется в документе, а не reload-ом. |
| Поле схемы удалено или переименовано | Поле игнорируется, остальное десериализуется. Предупреждение один раз на тип. |
| Новое поле в схеме | Значение по умолчанию из схемы, без предупреждения. |
| Поле сменило тип | Значение по умолчанию и предупреждение один раз на тип. |
| Мир или вид мира (`context_kind`) | Снимок с миром, которого нельзя создать, — ошибка restore → откат (§9). |

Пропажа типа, системы или поля — **не** ошибка restore. Это ожидаемая правка кода, и Play продолжается на новой DLL. Откат (§9) — только для случаев, когда восстановленный набор нельзя считать целым.

**Поля систем** (AC S541-3: «поля систем дают предупреждение»). Системы-объекты с состоянием создаются заново. Один раз за reload пишется список систем модуля, зарегистрированных как объект, а не как функция: их поля сброшены. Если реестр систем не отличает одно от другого, #601 добавляет признак в `system_entry`.

## 8. Время, Pause, Step, детерминизм

- Сохраняются:
  - режим набора (`play`/`pause`/`step`), `pending_steps`, `frames_run`, `time_scale`, seed;
  - `world_time`, `fixed_time`, накопитель `fixed_stepper`, состояние `rng` каждого мира.
- Restore ставит режим последним, после создания всех миров. В паузе Play остаётся в паузе.
- `app::frame_control` (глобальное удержание времени) лежит вне слоя, reload его не трогает.
- **Продолжение не побитово совпадает** с прогоном без reload, и это осознанно:
  - id `entt` новые;
  - порядок обхода view может отличаться;
  - системы с полями начинают с нуля.
- Детерминизм внутри одного прогона сохраняется. `rng` продолжает тот же поток; порядок доставки почты не зависит от id (`WORLD_MESSAGING.md` §5).

## 9. Откат

Ошибка restore — это:

- исключение или ошибка десериализатора;
- снимок, который не читается;
- мир, который нельзя создать;
- ASSERT-условие §4.

Порядок:

1. Частично восстановленный набор `"play"` уничтожается.
2. `project_module_host` возвращает **предыдущую копию** DLL: она ещё лежит в `.cache/modules/<pid>-<n>`. Это тот же путь, что и откат при неудачном `load` (`core_project_modules.cpp:555`), но запущенный после успешной загрузки. #601 добавляет для этого `revert()` с теми же hooks. Предыдущая копия удаляется только после успешного restore.
3. Тот же снимок восстанавливается в слое старого модуля. Play продолжается (AC S541-3). Пользователь видит ошибку restore и причину.
4. Если не удалось и это, Play останавливается с ошибкой, редактор возвращается в режим правки (как `editor_mode_controller::after_module_swap` сейчас). Уровень документа не страдает: он восстанавливается отдельно (шаг 8a).

Диагностическая копия последнего снимка всегда пишется в `<проект>/.cache/hot_reload/last_play_snapshot.json`. Её можно приложить к багу; в git и в поставку она не попадает.

## 10. Ссылки на код старой DLL

Слой по-прежнему уничтожается целиком до FreeLibrary (`MODULE_LAYER.md`: «выгрузка = уничтожение слоя целиком»). Отдельного отсоединения хранилищ не нужно. Вариант C добавляет только два новых места, и оба безопасны:

- **снимок** — чистые данные (§3);
- **отчёт** — строки.

Проверки — в тестах #600, перечислены в §11.

## 11. Тесты (для #600/#601)

1. **Круг registry → снимок → registry** на мире со всеми движковыми компонентами со схемой: значения совпадают, ссылки переназначены, `node_index` целый. Тестом владеет #599.
2. Каждый зарегистрированный движковый компонент либо имеет схему, либо помечен как производный. Тест падает на новом типе без того и другого.
3. Тестовый модуль, две сборки: правка функции системы → reload в Play.
   - Сущности, счёт (ресурс ctx со схемой), `world_time`, seed, `frames_run` и пауза сохранились.
   - Runtime-сущность со ссылкой на другую сущность восстановилась со ссылкой.
4. Тот же модуль после reload:
   - ни одной регистрации старой копии: счётчики областей, как в `module_loader`;
   - прогон под ASan без ошибок.
5. Удалённый тип компонента и удалённая система дают предупреждение и записи в отчёте; Play продолжается.
6. Сломанный restore (тестовый хук, бросающий ошибку) приводит к возврату старой DLL, Play продолжается, снимок тот же.
7. Reload во время загрузки уровня откладывается и выполняется после неё.

## 12. Отклонённые альтернативы

- **Stop → reload → Start** (решение 3 владельца от 2026-10-18; так работает сейчас) теряет всё состояние Play. Отменено владельцем в #541.
- **Подмена хранилищ в живом registry.** `registry.reset(id)` для типов модуля, затем перенос данных в хранилища нового модуля; идея `component_scope` из SPIKE-218.
  - Плюс: id сущностей и движковые компоненты сохраняются побитово.
  - Минусы: нужен учёт владения каждым хранилищем, а в production его нет. Планы систем, meta и спавнеры слоя всё равно пересоздаются. Любое пропущенное хранилище — вызов кода выгруженной DLL.
  - Сериализатор нужен и так: перенос значений между версиями типа, #552.
- **Снимок памяти** (memcpy компонентов) ломается на любой смене layout типа. `DISTRIBUTION.md` §4 уже отказался от него для уровней.

## 13. Вопросы владельцу
