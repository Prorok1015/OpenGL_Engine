# ADR: hot reload игрового модуля во время Play (вариант C)

**Issue:** #598 (S541-0) · эпик #541 · **Статус:** предложен, ждёт утверждения владельцем · Отменяет: решение 3 владельца от 2026-10-18 в `DISTRIBUTION.md` («Hot reload во время Play: Stop → reload → Start») и порядок #222 для Play · Основа: `DISTRIBUTION.md` §4–§5, `MODULE_LAYER.md`, `WORLD_CONTEXT.md` (Play, US-63-B), `WORLD_MESSAGING.md` §1, `WORLD_BUS.md` (#602), `DESC_SCHEMA.md`, `SPIKE-218-entt-dll.md`, `STAGE2_PLAN-2026-11.md` §2.6 · Код по ADR — #599 (сериализатор), #600 (reload в Play), #601 (несовместимые изменения и откат); писать его можно только после утверждения.

## 1. Решение

Во время Play пересборка `game.dll` не останавливает игру:

1. **до** подмены DLL снять снимок живых миров набора `"play"` (только данные, без указателей на код);
2. уничтожить слой старого модуля и выгрузить старую DLL (как сейчас);
3. загрузить новую DLL и создать её слой (как сейчас);
4. восстановить набор `"play"` из снимка в новом слое;
5. Play продолжается с того же кадра, в той же паузе, с тем же временем, seed и состоянием `rng`.

Правила владельца (#541) не меняются: **поля систем не сохраняются**, **компоненты без схемы не переживают reload** (предупреждение в логе, уведомление, запись в отчёте). Состояние игры живёт в компонентах и ресурсах со схемой; всё остальное — производные данные или состояние кода.

**Главная цена — схемы.** Сейчас ни у одного runtime-компонента движка нет схемы: схемы есть только у desc-классов. Поэтому #599 — это прежде всего схемы примерно для 25 компонентов движка. Как вводить вариант C по частям, решает вопрос 1 (§14).

## 2. Как устроено сейчас (факты для решения)

- **Reload.** `project_module_host::reload(module, hooks)` (`core_project_modules.cpp:470-560`) вызывается из `game_reloader` через `next_frame`, то есть между кадрами, на главном потоке. Шаги:
  1. `prepare` — новая копия загружается и проверяется;
  2. `hooks.before_swap()`;
  3. `unload`;
  4. `load`;
  5. при неудаче `load` — `previous()`;
  6. `hooks.after_swap(report)`.

  Повторный вход запрещён флагом `m_reloading` (:432, :472).
- **`reload_hooks::before_swap` возвращает `void`** (`core_project_modules.h:72-78`), поэтому отменить замену из хука нельзя.
- **Stop → reload → Start.** `module_swap_gate::before_swap` первым вызывает Play-хук.
  - `play_session::before_module_swap` → `stop(stopped_for_reload)`;
  - `after_module_swap` → `start(module_reloaded)`, при необходимости `pause()` (`edt_play_session.cpp:224-242`).
- **Смена слоя в редакторе.** `follow_game_layer_change(before)` (`edt_editor_system.cpp:1158-1171`):
  - вызывает `stop(user)`, если Play ещё активен;
  - отсоединяет уровень документа.

  После смены (:1173-1177) набор `level` переводится в `edit`, и уровень присоединяется снова.
- **`start_blocker`** (:921) блокирует только старт Play при загрузке уровня. С `game_reloader` он не связан.
- **Каждый слой имеет свой `res::resource_system`** поверх базового (`scn_scene_layer.h:42, 78`). Ресурсы, загруженные через слой, умирают вместе со слоем.
- **Буферы команд между кадрами могут быть непусты.** Система контекста с бо́льшим id ставит команды в контекст с меньшим id, а применяются они после следующей фазы получателя (`scn_context_set.cpp:159-168`).
- **Пути registry → desc нет** (`WORLD_MESSAGING.md` §1). Компоненты и desc — разные типы:
  - спавнеры копируют поля вручную (`simple_spawner<T>`, `scn_registration_scope.cpp:85-91`);
  - связи «компонент → desc» нет;
  - `ecs::component_registry` хранит только имя ↔ `type_hash`, в production его никто не заполняет.
- **Схемы** (`desc_schema.h:34-49`).
  - Виды полей: скаляры, `vec2/3/4`, `quat`, `color`, `string`, `enumeration`, `res_tag`, `desc_ref`, `node_ref`, `entity`, `structure`, `array`, `custom`.
  - `entity` есть только для runtime-блобов: `deduce_kind` для C++-типов его не выводит, а `entt::entity` выводится как `enumeration`.
  - Вида `mat4` нет.
  - `schema_kind::component` существует, но им описаны только 4 desc-класса (`camera`, `directional_light`, `screen_anchor`, `skybox`).
- **Состояние времени.**
  - У `ecs::rng` нет чтения и записи внутреннего состояния: `m_state`/`m_inc` закрыты, а `from_state` сидирует, а не восстанавливает (`ecs_random.hpp:19-25`).
  - У `fixed_stepper` нет чтения и записи накопителя, а `alpha()` возвращает float с потерей точности.
  - `scn::fixed_time` — это только `{float dt}`, накопленного фиксированного времени нет.
  - У `context_set::m_frames_run` нет сеттера, у `world_context::set_time_scale` доступ только для `context_set`.
  - `world_time{double}` читается и пишется через ctx.

## 3. Последовательность

### 3.1. Фаза до подмены (новая, в `game_reloader`)

Проверки и снимок выполняются **до** `project_module_host::reload`, потому что из `before_swap` отменить замену нельзя.

1. **Можно ли сейчас (§5).**
   - Нельзя → reload откладывается: статус «reload ждёт: …», повтор в каждом кадре, пока условие держится.
   - Нельзя навсегда (Play в состоянии, которое не снимается, §4.4) → поведение по вопросу 2 (§14).
2. **Снимок.** `play_session::capture_for_reload()` строит снимок (§4) и диагностическую копию (`<проект>/.cache/hot_reload/last_play_snapshot.json`).
   - Ошибка снимка → поведение по вопросу 2. Рекомендация: старый путь Stop → reload → Start с предупреждением «состояние Play не сохранено: <причина>».
3. Только после этого вызывается `project_module_host::reload(module, hooks)`.

### 3.2. Подмена (существующий `swap()`, изменены хуки)

| Шаг | Где | Что |
|---|---|---|
| `before_swap` | `play_session::suspend_for_swap()` | Набор `"play"` уничтожается (`destroy_set`: задачи, привязки роутера). `play_session` переходит во внутреннее состояние **`suspended`** (§3.4). Событие Stop не публикуется, `user://` не трогается, снимок `m_before` для будущего Stop сохраняется. |
| `follow_game_layer_change(before)` | редактор | Play не активен, поэтому `stop(user)` не срабатывает. Уровень документа уходит в JSON, как сейчас. |
| `unload` → `load` | `module_loader` | Как сейчас: `stop_tasks` → слой уничтожается целиком → FreeLibrary → новая DLL → `register_content`. |
| `follow_game_layer_change(after)` | редактор | Как сейчас: `level` → `edit`, уровень присоединяется. |
| `after_swap(report)` | `play_session::resume_after_swap(report)` | Решение по исходу (§3.3). |

### 3.3. Исход замены

| `reload_report` | Слой | Что делает `play_session` |
|---|---|---|
| `reloaded` | новый модуль | `restore(snapshot)` в новом слое (§6) |
| `rolled_back` (новая не загрузилась, хост вернул предыдущую копию) | новый слой **старого** модуля | `restore(snapshot)` — снимок снят с этого же модуля, совпадение полное |
| `refused` из `prepare` (новая копия не прошла проверку, `core_project_modules.cpp:498-505`) | хуки **не вызывались**, старый слой и `"play"` живы | снимок выбрасывается, Play идёт дальше как был; пользователь видит причину |
| `refused` после `before_swap` (старый модуль не выгрузился) | старый слой жив, `"play"` уже уничтожен | Stop с сообщением (вопрос 3, §14) |
| `lost` (модуля нет) | пустой слой | Stop с ошибкой (вопрос 3) |

Снимок снимается на **каждом** входе reload: `game_reloader::reload`, `reload_quiet` (live-режим) и `reload_after_background`.

### 3.4. Состояние `play_session` между `before_swap` и `after_swap`

- **Наружу** (меню, `play.status`, MCP) состояние остаётся `playing`/`paused`, с флагом `reloading: true`.
- `play.*` и пункты меню в это время возвращают `busy` «module reload in progress».
- `edt::view_set()` возвращает пустой набор, и Game view показывает надпись «Reloading…». Кадр рисуется только в пути отката (§9), обычный reload укладывается в один вызов между кадрами.
- **`restore` повторяет `start()` с отличиями:**
  - новый набор `"play"` на game layer создаётся с теми же опциями (`hot_reload = false`), seed и time scale;
  - `level` → `set_active(false)`, `extract = false`;
  - камера редактора внедряется в двойник активного мира;
  - документ блокируется;
  - **профиль `user://` не пересоздаётся** и не перемонтируется (данные игры за сессию сохраняются);
  - `m_before` не перезаписывается: Stop после reload возвращает редактор в состояние до первого Start.

### 3.5. Откат после успешной замены — `project_module_host::revert()`

Восстановление может не удаться уже после того, как новая DLL загрузилась (§9). Повторно войти в `swap()` из `after_swap` нельзя (`m_reloading`). Поэтому:

1. `resume_after_swap` уничтожает частично восстановленный набор, оставляет `play_session` в `suspended` со снимком и ставит `revert` в `next_frame`.
2. **`project_module_host::revert(module, hooks)`** — новый API (#601). Он вызывает обычный `swap()` с такими параметрами:
   - `copy = m_copies[module].previous`, и больше ничего. `m_copies` заранее **не** переставляется: `swap()` сам делает `previous = exchange(current, *copy)` при успехе (`core_project_modules.cpp:541-543`), а двойная перестановка вернула бы всё обратно;
   - `previous = nullptr`. Если старая копия не загрузится, исход `lost`, и запасной путь `swap()` не может вернуть только что упавшую сборку;
   - признак «копию не удалять»: `drop_copy()` (:536, :549) не трогает папку предыдущей копии, если её загрузка не удалась. Папка остаётся для диагностики и для следующей попытки.

   Любой исход `revert`, кроме `reloaded`, означает Stop с ошибкой.

   Предыдущая копия в `.cache/modules/<pid>-<n>` не удаляется, пока restore не прошёл.
3. Гейт проходит `detach`/`attach` уровня второй раз, как при любой замене.
4. `before_swap` второго прохода **не снимает новый снимок**: набора `"play"` нет, а `play_session` уже в `suspended`. Используется прежний снимок.
5. `after_swap` второго прохода → `restore(snapshot)` в слое старого модуля.
   - Успех: Play продолжается (AC S541-3), пользователь видит ошибку первого restore.
   - Неудача: Stop с ошибкой, редактор в режиме правки. Снимок остаётся на диске.

## 4. Снимок

### 4.1. Формат

Один JSON-документ (`boost::json::value`) на набор. Типы записываются **именами регистрации**, а не `type_hash`. В снимке нет объектов desc-типов модуля, `std::function`, `std::any` и `entt::entity`, поэтому после FreeLibrary он остаётся валидным.

```json
{
  "__type": "play_snapshot", "__version": 1,
  "module": { "name": "game", "copy": "<pid>-<n>" },
  "set": { "mode": "pause", "pending_steps": 0, "frames_run": 1234, "time_scale": 1.0, "seed": 42 },
  "blackboard": [ { "key": "hud.score", "type": "i32", "value": 17 } ],
  "worlds": [ {
    "name": "main", "kind": "play", "systems": [ "game::move" ],
    "time": { "world_time": 20.5, "fixed_accumulator": 0.004 },
    "rng": { "state": "…", "inc": "…", "seed": "…" },
    "ctx": [ { "type": "game.score", "value": { "points": 17 } } ],
    "entities": [
      { "snap": 1, "node_path": [ 4021, 77 ], "components": { "scn.local_transform": { }, "game.health": { "hp": 3 } } },
      { "snap": 2, "components": { "game.bullet": { "owner": { "$snap": 1 } } } }
    ]
  } ],
  "report": { "dropped_components": [ ], "dropped_ctx": [ ], "dropped_blackboard": [ ], "mail_in_flight": 0, "bus_pending": 0, "stopped_tasks": 0 }
}
```

- **Буферы команд** перед снимком сбрасываются через `apply_commands()` каждого контекста в порядке id. Команды, поставленные «на после следующей фазы» другого контекста, применяются чуть раньше — в момент снимка, до фазы `input` следующего кадра. Это записано в отчёт (число команд). Сериализовать сами команды не стоит: это `std::function` с кодом модуля.
- **Сущности камеры редактора** (`editor_camera_tag`, `prefab_camera_tag`) в снимок не входят. Restore внедряет камеру заново, как `start()`.

### 4.2. Регистрация компонентов (новое, #599)

Чтобы снять мир по типам, нужен перечислимый реестр «имя ↔ тип ↔ схема ↔ функции доступа». `ecs::component_registry` расширяется:

```cpp
reg.add<scn::local_transform>("scn.local_transform", schema);   // схема — schema_kind::component
reg.add_derived<scn::world_transform>("scn.world_transform");    // производный: не снимается, пересчитывается
reg.add_ctx<game_score>("game.score", schema);                   // ресурс ctx: entt ctx не перечислим, поэтому по реестру
```

- **Движок** регистрирует все свои runtime-компоненты в базе. Модуль регистрирует свои через `layer.components()`, как сейчас, но со схемой.
- **Без схемы:** `add<T>(name)` по-прежнему разрешён, тип попадает в отчёт как «без схемы».
- **Реестр перечислим.** Порядок перечисления — порядок регистрации (сначала база, затем слой). Это и порядок восстановления (§6).
- **Новые виды полей схемы:**
  - `entity` для C++-полей (`entt::entity` → `{"$snap": N}` в снимке; в desc на диске запрещён);
  - `mat4` (или `custom`-кодек `glm::mat4` в схеме ядра);
  - `ecs::entity_ref` как `structure` из `{context: string, path: array<u64>}`.

### 4.3. Компоненты движка

| Категория | Компоненты | В снимке |
|---|---|---|
| Данные | `local_transform`, `name_component`, `node_id_component`, `animation_controller_component` (включая `current_time` — живое состояние), `animated_node_component`, `bone_component`, `object_component`, `scene_anchor_component`, `renderable`, `directional_light`, `mouse_controller_component`, `screen_anchor_component` (`entity_ref`), **`mesh_component`** (диапазоны вершин и индексов из `mesh_node_desc`, а не кэш), `camera_component` (без `m_viewport`: его раздаёт Game view) | по схеме |
| Ссылки на ресурсы | `geometry_component`, `skeleton_component`, `sky_component`, `animation_collection_component`, `material_desc_component`, `prefab_instance`, `component_tracker` | по схеме, см. ниже |
| Ссылки на сущности | `parent_component`, `children_component`, `skinning_component::skeleton_entity` | по схеме с видом поля `entity` |
| Производные | `world_transform`, `bone_matrices_component`, `depth_level`, `screen_anchor_result` | нет; пересчитываются (§6, шаг 5) |
| Только редактор | `editor_camera_tag`, `prefab_camera_tag` | нет; камера внедряется заново |

- **`material_desc_component`** может держать материал без тега (inline). Такой материал пишется значением по схеме `rnd::material_desc`, она уже есть. С тегом пишется тег.
- **`prefab_instance::local_overrides`** и **`component_tracker`** держат desc-объекты и JSON, в том числе типов модуля. Они сериализуются **через desc** (`serialize` своего типа) в момент снимка, то есть до FreeLibrary. Desc-тип без сериализации попадает в отчёт.
- **Тест (#599):** каждый компонент движка зарегистрирован со схемой, как производный или как «только редактор». Новый тип без регистрации роняет тест.
- **Проверка перед снимком** (поэтапность, вопрос 1):
  - обойти **непустые** хранилища registry каждого мира Play;
  - не учитывать хранилище самих сущностей `entt` и хранилища, опустевшие после `clear()`;
  - каждое найденное хранилище сопоставить с записью реестра по `type_hash`.

  Хранилище движка без записи (или без схемы и пометки) переводит этот reload на запасной путь, и сообщение называет тип. Тест #600: незарегистрированный компонент движка в мире Play даёт запасной путь и сообщение с его именем.

### 4.4. Что не переносится

- **Компоненты и ресурсы ctx без схемы** — в отчёте имя и число сущностей, в лог предупреждение, в редакторе уведомление.
- **Blackboard набора.** У значений blackboard нет поиска схемы по ключу. Переносятся только значения типов, зарегистрированных в `channel_registry` со схемой (расширение `add<T>(schema)`); остальные попадают в отчёт.
- **Почта набора в полёте** и **события шины мира, ждущие доставки** (`WORLD_BUS.md` §3.5) отбрасываются, в отчёте пишется их число.
- **Задачи слоя** останавливает `stop_tasks`, незавершённые попадают в отчёт.
- **Поля систем** не переносятся. Один раз за reload пишется список систем-объектов модуля; признак «объект, не функция» в `system_entry` добавляет #601.

## 5. Когда reload разрешён

Проверяется в `game_reloader` до подмены (§3.1); новый предикат `reload_options.defer` возвращает причину.

- Только между кадрами, на главном потоке, вне `context_set::update`. Так уже и есть, restore дополнительно проверяет это ASSERT-ом.
- **Откладывается**, пока:
  - грузится уровень или добавляемый ассет — тот же признак, что у `start_blocker`, но подключённый к `game_reloader`;
  - restore ждёт ресурсы (§6, шаг 6);
  - идёт смена сцены #564 (когда она появится);
  - выполняется `revert` (§3.5).
- Отложенный reload выполняется в первом кадре без этих условий.
- Pause и Step не мешают: режим, `pending_steps` и `frames_run` входят в снимок.

## 6. Восстановление

1. Создать набор `"play"` (§3.4) и миры по списку систем из снимка. Системы, которых нет в новом модуле, пропускаются (§7). Режим набора на время restore — внутренний `pause`.
2. Перед первой сущностью мира вызвать `node_index::get(reg)`, чтобы хуки `node_id_component` нашли индекс.
3. **Проход 1:** создать все сущности в порядке снимка и поставить `node_id_component` (где есть путь). Таблица `snap → entt::entity` теперь полная.
4. **Проход 2:** по сущностям в порядке снимка поставить компоненты в порядке реестра (сначала движок, затем модуль), ссылки разрешить по таблице.
   - Наблюдатели `on_construct` (модуля и движка) видят сущность в том же порядке «сущность за сущностью», что при спавне из desc, и любая ссылка уже разрешима.
   - `hot_reload_manager` к набору `"play"` не подключён (`hot_reload = false`).
   - **Наблюдатели модуля на время restore заглушены** (вопрос 5). Восстановленная сущность уже существовала, и её появление не новое событие. Наблюдатель «пуля создана → выстрелы +1 / звук» иначе посчитал бы её второй раз поверх восстановленного счёта.
     - Модуль подключает наблюдатели через `module_context::observe<T>` (новое в #600, RAII как подписки шины). Restore отключает их и включает снова после шага 5.
     - Наблюдатель, подключённый напрямую к `registry.on_construct`, restore не видит. Правило в документации модуля: так не делать.
     - Наблюдатели движка, которые строят индексы (`node_index`), работают как обычно.
5. Ресурсы ctx со схемой, `world_time`, накопитель `fixed_stepper`, состояние `rng`, blackboard. Затем испустить `hierarchy_updated`/`transform_updated` для всех сущностей с трансформом, чтобы производные компоненты пересчитались в первом кадре.
6. **Ресурсы.** Desc и ресурсы, загруженные через ресурсы слоя, умерли вместе со старым слоем: restore **загружает их заново по тегам** (асинхронно). То, что держит базовый кэш (общие ресурсы движка), остаётся попаданием в кэш.
   - **Барьер:** набор стоит во внутренней паузе, пока все `res_handle` восстановленных компонентов не загрузятся или не упадут.
   - `frames_run` и время не идут. Game view показывает «Reloading… (N ресурсов)».
   - Меню Play и команды MCP `play.resume`/`play.step`/`play.pause` в это время возвращают `busy`, как во время самой замены (§3.4).
   - Упавший ресурс — предупреждение, как при обычной загрузке уровня.
7. Восстановить режим набора, `pending_steps` и `frames_run`. Пауза остаётся паузой.
8. **Состояние редактора.**
   - Выделение в редакторе хранит путь: после restore оно находит узел по пути, а runtime-сущность без пути снимается.
   - Сырые `entt::entity` редактора сбрасываются в `null` при `suspend_for_swap`, потому что тот же id может достаться другой сущности: `game_view::selection` (`edt_game_view_logic.h:32-37`) и `viewport_panel::m_rotate_ent`.

**Новые API (#599/#600):**

- `ecs::rng::state()`/`set_state(state, inc, seed)`;
- `fixed_stepper::accumulator()`/`set_accumulator(double)`;
- `context_set::restore_run_state(frames_run, pending_steps)`;
- перечисление и `emplace` по имени через расширенный `component_registry`;
- `project_module_host::revert`;
- `reload_options.defer`.

## 7. Удалённая система, тип или поле

Restore сверяет снимок с реестрами нового слоя:

| Что пропало | Поведение |
|---|---|
| Тип компонента или ресурса ctx | Компонент не ставится, сущность остаётся. Явное предупреждение `egLOG_WARN("hot_reload", …)` с именем и числом, запись в отчёте, уведомление. Тихого переиспользования нет. |
| Система из списка мира | Мир создаётся без неё, предупреждение и отчёт. Новые системы модуля сами не добавляются: список систем — это данные Play из `world_desc.systems` (вопрос 7). |
| Поле схемы удалено или переименовано | Поле игнорируется, предупреждение один раз на тип. |
| Новое поле | Значение по умолчанию из схемы, без предупреждения. |
| Поле сменило тип | Значение по умолчанию, предупреждение один раз на тип. |
| Мир или вид мира | Ошибка restore → откат (§3.5). |

Пропажа типа, системы или поля — ожидаемая правка кода, а не ошибка (вопрос 4).

## 8. Время, Pause, Step, детерминизм

- **Сохраняются:**
  - режим набора, `pending_steps`, `frames_run`, `time_scale`, seed;
  - у каждого мира: `world_time`, накопитель `fixed_stepper`, полное состояние `rng`.
- `delta_time`, `fixed_time`, `update_alpha` не сохраняются: их пишет `begin_frame` каждого кадра.
- `app::frame_control` лежит вне слоя, reload его не трогает.
- **Продолжение не побитово совпадает** с прогоном без reload, и это осознанно:
  - id `entt` новые;
  - порядок обхода view может измениться;
  - системы с полями начинают с нуля;
  - сброс буферов команд сдвигает их на одну фазу (§4.1).
- Детерминизм внутри прогона сохраняется: `rng` продолжает тот же поток.

## 9. Откат: что считается ошибкой restore

Ошибки restore:

- исключение или ошибка десериализатора;
- снимок, который не читается;
- мир, который нельзя создать;
- ASSERT-условие §5.

Порядок отката — §3.5. Пропавшие типы, системы и поля — не ошибка (§7). Упавший ресурс — не ошибка (§6, шаг 6).

## 10. Ссылки на код старой DLL

- Слой по-прежнему уничтожается целиком до FreeLibrary.
- Снимок — чистые данные: desc-объекты типов модуля превращаются в JSON до выгрузки (§4.3).
- Отчёт — строки.
- Сырые `entt::entity` редактора сброшены (§6, шаг 8).

## 11. Тесты

- **#599:**
  1. круг registry → снимок → registry для каждого компонента движка со схемой; ссылки переназначены, `node_index` целый;
  2. полнота регистрации компонентов движка (§4.3);

  1. тестовый модуль, две сборки, правка функции системы во время Play: сущности, счёт (ресурс ctx со схемой), `world_time`, seed, `frames_run`, пауза и профиль `user://` сохранились;

  4. reload во время загрузки уровня откладывается;
  5. барьер ресурсов: Play не идёт, пока меши не загружены.
- **#601:**
  1. удалённый тип и удалённая система дают предупреждение и отчёт, Play продолжается;
  2. сломанный restore (тестовый хук) запускает `revert`: старая DLL, тот же снимок, Play продолжается;
  3. второй сбой приводит к Stop с ошибкой;
  4. `refused`/`lost` после снимка приводят к Stop.

## 13. Отклонённые альтернативы

- **Stop → reload → Start** — так работает сейчас; теряет всё состояние Play. Отменено владельцем в #541. Остаётся запасным путём только по вопросам 1–2.
- **Подмена хранилищ в живом registry** (`registry.reset(id)` для типов модуля, `component_scope` из SPIKE-218).
  - Плюс: id сущностей и компоненты движка сохраняются побитово, схемы движка не нужны.
  - Минусы: нужен учёт владения каждым хранилищем, а в production его нет. Планы, meta, спавнеры и ресурсы слоя всё равно пересоздаются. Пропущенное хранилище означает вызов кода выгруженной DLL.
  - Перенос значений между версиями типа модуля всё равно требует сериализатора.
- **Снимок памяти** ломается на любой смене layout.

## 14. Вопросы владельцу

Термины:

- **«Компонент»** — кусок данных объекта игры: здоровье, позиция, счёт.
- **«Схема»** — описание полей компонента; по нему движок умеет его сохранять.
- **«Снимок»** — сохранённое состояние запущенной игры.

1. **Поэтапность (главный).** Пример: игра запущена, вы поправили код и пересобрали. Но в сцене есть объект движка, который ещё не умеет сохраняться.
   - **(а) рекомендация:** в этом случае игра перезапускается с начала, как сейчас, и редактор пишет, какой тип ещё не умеет сохраняться. Когда сохраняться научатся все типы, перезапусков не будет. Так #600 можно делать параллельно с работой над схемами.
   - **(б)** не включать сохранение игры при перезагрузке, пока сохраняться не научатся все типы движка.
2. **Не удалось сохранить состояние игры** перед перезагрузкой (ошибка в данных). Пример: «состояние сохранить не вышло — перезапустить игру с начала с предупреждением (рекомендация) или не перезагружать код, пока вы сами не остановите игру?»
3. **Перезагрузка сорвалась уже после сохранения.**
   - `refused` — старую сборку не удалось выгрузить, новая не загружена;
   - `lost` — не загрузились ни новая, ни старая.

   Пример: «новая сборка не встала, и игровой код не работает — остановить игру с сообщением (рекомендация)?»
4. **В новой сборке удалён тип данных или система.** Пример: «вы удалили компонент "щит" — продолжить игру без щитов с предупреждением (рекомендация) или вернуть старую сборку?»
5. **Реакции «объект создан» при восстановлении.** Пример: игра считает выстрелы по появлению пуль. После перезагрузки пули восстанавливаются — считать ли их второй раз?
   - **рекомендация:** нет, реакции игры при восстановлении молчат;
   - альтернатива: правило для программиста игры — такие реакции не должны менять сохраняемые данные.
6. **Сохранять ли не только объекты, но и общие данные игры:** счёт, настройки уровня, общую доску значений между мирами (ctx, blackboard). Пример: «очки и номер волны тоже сохраняются (рекомендация) или только объекты на сцене?»
7. **Список систем (логики) мира.** Пример: «вы добавили в код новую систему "магнит" — включить её в уже запущенной игре сразу или только после перезапуска Play?»
   - рекомендация: только после перезапуска, потому что список систем мира — это данные сцены.
