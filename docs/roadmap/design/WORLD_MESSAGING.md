# Дизайн: обмен данными между мирами (world contexts)

**Issue:** #268 · **Статус:** утверждён владельцем 2026-10-19 (решения в конце) · Основа: `WORLD_CONTEXT.md` (решения владельца 1, 4, 6; Q4 «канал сообщений — при появлении реального сценария»; PR-6 = чистка), `CHIMERA_ROADMAP.md` ADR-05 (идентичность), ADR-07 (Play), ADR-09 (игровой UI); EPIC-63 Play (#39), EPIC-67/69 UI (#42/#44), EPIC-57 identity (#27); детерминированные снимки #260 · Сценарий, ради которого пишется: «UI-мир + 3D-мир в одном уровне» и Play-двойник со своими каналами

## 1. Как устроено сейчас (aibranch @ 88af3c4, после PR-4 #264 и #260)

- **Наборы.** `context_manager` обходит наборы в порядке создания, затем `hot_reload->tick()` (`scn_context_manager.cpp:42-51`); `context_set` держит контексты по id, режим, seed, порядок фаз (`scn_context_set.h:174-182`).

Решение владельца 1 («все фазы одного контекста подряд») в коде **не реализовано**: PR-1…PR-3 сохранили чередование. После каждой фазы каждого контекста применяется его command buffer (`:88`).

Трекинг доступа знает `bind_res` (`ecs_system_access.hpp:13,17-18,51,75`), признак типа — `ecs_traits.hpp:7,41-53`.

- **Вне фаз чужие registry читают легально** (политика WORLD_CONTEXT, PR-6 не трогает): редактор (`edt_editor_system.cpp:117-121,147-159`), экстрактор (`scn_render_data_extractor.cpp:49-51`), `gs::route_input` (`gs_input_routing.cpp:6-16`).

## 2. Случаи → примитивы

| Случай | Что нужно | Примитив |
|---|---|---|
| 1. HUD (здоровье, счёт), миникарта/радар | последнее значение | **blackboard набора** (типизированные ключи) |
| 1. Маркер над 3D-объектом | позиция объекта + камера 3D-мира **того же кадра** | **якорь, разрешаемый в extract** (`screen_anchor{entity_ref}`) — без лага |
| 1. Debug-оверлеи | рисуются в 3D-мире | **локально в мире** (`packet.debug_draws`, `scn_render_data_extractor.cpp:178-198`), обмена нет |
| 2. Условие: в зоне / вне зоны, «нажми E» | уровень, а не фронт | **blackboard** (`zone.<id>.inside = bool`); фронты получатель выводит сам, сравнивая с прошлым значением |
| 2. Разовое событие: квест выполнен, смерть, конец уровня | ровно один раз | **почта набора** (адресное сообщение или широковещание) |
| 3. Команда: UI → 3D (дверь, предмет, пауза), рычаг A → дверь B, настройки → 3D | исполняет получатель своей системой в своей фазе | **почта набора**; цель — `entity_ref`, не `entt::entity` |
| 4. Перенос сущности между мирами | идентичность, атомарность | **отложено** (§9 п.7): нужен EPIC-55 (сериализация компонентов) и EPIC-57 (`stable_id`) |
| 5. Время суток, погода, настройки | общее для набора | **blackboard**; один владелец-контекст или внешний писатель (редактор, оболочка игры) |

**Отклонённые альтернативы.**
- *`bind_res` read-only внутри набора* — чужие `entt::entity` и id потоков в коде систем; запрещено решением 4.
- *Команды через чужой `entity_changer`* — запись в чужой registry по чужому `entt::entity`, видимость зависит от порядка фаз.
- *Общий «level state» registry* — удалён в PR-2; возврат = глобальный registry без владельца.
- *Глобальная шина (синглтон)* — смешает `level`, `preview:*`, `play`.
- *Немедленная доставка в порядке выполнения* — результат зависит от порядка фаз и id.
- *Маркеры через blackboard* — лаг в кадр, маркер «плывёт». *Маркер компонентом в 3D-мире + screen-space пасс* — без лага, но UI-разметка уезжает из UI-документа (ADR-09); этот путь — для debug-оверлеев.

## 3. Решение

**Канал живёт в `context_set`** (`scn::set_channel`): blackboard + почта. Системы по-прежнему видят **только свой registry**: движок кладёт в ctx каждого контекста ссылки на ресурсы канала (`ecs::blackboard_reader`, `ecs::blackboard_writer`, `ecs::inbox<T>`, `ecs::outbox<T>`). Изменения в `ecs_invoker`/`runtime_context` не нужны — это обычные ctx-ресурсы, `ecs_system_access` отслеживает их чтение/запись без доработок. Наборы не видят каналы друг друга: `preview:*` и Play-двойник получают свои каналы при создании набора, ни одна системная API не адресует другой набор. Адресовать любой набор может только код вне фаз через `context_manager` (редактор, `play_session`, оболочка игры).

**Двойная буферизация, лаг ровно один кадр.** Записи кадра N (в blackboard и outbox) становятся видимы в кадре N+1 всем контекстам набора одинаково. Обмен происходит в одной точке — `context_set::begin_frame_channel()` в начале `context_set::update`, до `begin_frame` контекстов. Поэтому результат **не зависит** от порядка «фаза × все миры» / «мир целиком» и от порядка id — канал снимает вопрос порядка с повестки (рекомендация в §4).

**Ссылки на сущности** — `ecs::entity_ref{context, path}`: имя контекста в наборе + путь `node_id` (`scn_node_index.h:14`). Разрешает ссылку **получатель в своём registry** (`node_index::get(reg).find(path)`) или экстрактор вне фаз. Сущности рантайма без пути получают id из `stable_id_component` (ADR-05/EPIC-57) — генератор на набор, сидированный `derive_seed(set.seed, …)`, чтобы id совпадали между прогонами; до EPIC-57 ссылаются только на авторские узлы. `entt::entity` в канале не встречается: в C++20 поля payload статически не перечислить, поэтому `channel_registry::add<T>()` проверяет тип по схеме desc (#128), когда она зарегистрирована, иначе правило держит ревью.

```cpp
namespace ecs {
	struct entity_ref { std::string context; std::vector<uint64_t> path; bool operator==(const entity_ref&) const = default; };
	struct address { std::string context; };                 // пусто = широковещание по набору
	template<class T> struct bb_key { std::string_view name; }; // "hud.health"; тип проверяется ASSERT при первом доступе

	class blackboard_reader {                                  // снимок кадра N-1, неизменяем весь кадр
	public: template<class T> const T* find(bb_key<T>) const;
	        template<class T> T get_or(bb_key<T>, T fallback) const; };
	class blackboard_writer {                                  // пишет в задний буфер; видно в N+1
	public: template<class T> void set(bb_key<T>, T value); }; // несколько писателей ключа за кадр → побеждает больший id контекста + egLOG_WARN

	template<class T> struct envelope { std::string from; address to; uint32_t seq; T payload; };
	template<class T> class outbox { public: void send(address to, T payload); };
	template<class T> class inbox  { public: std::span<const envelope<T>> messages() const; }; // все фазы и fixed-шаги кадра
}
namespace scn {
	class set_channel {                                        // член context_set, не frame-allocator память
	public:
		void begin_frame(context_set& set);                    // swap blackboard; outbox[] по id контекста → inbox[]
		void post_external(address to, auto payload);          // редактор/play_session/оболочка: from = "", раньше всех
		blackboard_writer& external_blackboard();              // настройки, флаги оболочки
		void clear();                                          // load_level / clear набора
	};
	// context_manager::post(set, address, payload) и ::blackboard(set) — вход для кода вне фаз.
	// Отложено (§9 п.7): bool context_manager::transfer(set, const ecs::entity_ref& src, std::string_view dst_context);
}
```

**Правила доставки.** Типы сообщений регистрирует модуль (`channel_registry::add<T>()`). Порядок в `begin_frame`: внешние, затем outbox контекстов по возрастанию id контекста, внутри — по `seq` (порядок отправки). Нет адресата → сообщение отброшено с `egLOG_WARN("scene", …)`. Inbox живёт кадр; команду для `fixed_update` получатель переносит в компонент в `pre_update`. Лимит сообщений на тип за кадр ловит пинг-понг. Blackboard переживает пересоздание писателя (`reload_context`, `scn_context_set.cpp:135-152`), inbox — нет. **Edit/Pause:** канал заморожен со временем набора (outbox копится до лимита), **Step** — один обмен: Edit-сцена не исполняет команды незапущенных игровых систем.

**Реализация (W1, #269).** Уточнения, не меняющие утверждённый дизайн:
- Широковещание (`address{}`) идёт всем остальным контекстам набора, **не отправителю**; своё сообщение контекст адресует себе по имени.
- В замороженных кадрах (Edit/Pause) обмена нет, а inbox очищается (сообщение не видно дважды); outbox продолжает копиться до лимита.
- Blackboard хранит последнее значение, пока его не заменят; при записи ключа несколькими писателями за кадр побеждает больший id контекста (внешний писатель проигрывает любому контексту).
- Лимит: 1024 сообщения на тип за кадр (outbox контекста, внешние посты и доставка), лишнее отбрасывается с `egLOG_WARN`; значение меняется `set_channel::set_message_limit`.
- Проверка типа сообщения по схеме desc откладывается до готовности #128; пока `channel_registry::add<T>()` требует только копируемость `T`.

**Маркеры (якоря).** UI-элемент хранит `screen_anchor{entity_ref target, glm::vec3 offset}`. В стадии `extract` (после всех `update`, вне фаз) экстрактор находит цель в контексте `target.context` того же набора, берёт `world_transform` и камеру этого контекста **текущего** кадра и пишет экранную позицию + флаг «за камерой/вне экрана» в пакет UI-пасса. Лага нет; UI-системы видят результат прошлого кадра только если им нужна логика по позиции (редко). Делается в EPIC-67, здесь фиксируется контракт.

**Зоны.** Мир-владелец зоны пишет состояние, а не событие: `bb_key<bool>{"zone.<node_id>.player_inside"}` каждый кадр (или при изменении — blackboard хранит последнее). UI показывает/прячет кнопку по значению; фронт «вошёл» UI вычисляет сам. Пара enter/exit как события допустима только при гарантии обоих концов; рекомендация — состояние.

**Один мир с зонами или два мира.** Один мир, если области делят физику, ИИ, время и сущности часто пересекают границу; потоковая подгрузка чанков = инстансы префабов в том же мире, переноса нет. Два мира — при разном времени/режиме/системах или изоляции: UI, интерьер-инстанс, мини-игра, превью. Перенос между 3D-мирами редок, откладывается без ущерба для этапа D.

## 4. Порядок кадра

| Стадия кадра / место | Пишет | Читает | Лаг |
|---|---|---|---|
| `ui` кадра N-1 (редактор, оболочка) | `post_external`, `external_blackboard`; привязки ввода | — | доставка в N |
| `update`: `route_input` | `input_state`/`input_focus` по слоям (§6) | области захвата (`input_capture.regions`) из кадра N-1 против курсора **текущего** кадра | раскладка UI — 1 кадр, курсор — 0 |
| `update`: `set.begin_frame_channel` | swap blackboard; outbox(N-1) → inbox(N) по id контекста | — | — |
| `update`: фазы контекстов (`input`…`late_update`) | `blackboard_writer`, `outbox` (задний буфер) | `blackboard_reader`, `inbox` (кадр N-1) | 1 кадр |
| `post_update` | сброс дельт ввода | — | — |
| `extract` | пакеты, `screen_anchor` → экран | registry всех контекстов набора, текущий кадр | 0 |

**«Фаза × все миры» vs «мир целиком».** Канал от выбора не зависит (обмен только на границе кадра набора). Рекомендация: реализовать утверждённое решение 1 (мир целиком) отдельным нейтральным PR — в контенте один мир на уровень, межмировых зависимостей внутри кадра после PR-6 нет. Свой command buffer по-прежнему применяется после каждой фазы своего контекста.

## 5. Детерминизм

- Порядок обмена фиксирован: внешние → контексты по id → `seq`; не зависит от порядка фаз, адресов, хешей. Перебор ключей blackboard (отладка, сохранение) — по имени ключа (отсортированный контейнер), не по `unordered_map`.
- Нет wall-clock и `random_device`; `stable_id` рантайма — из `derive_seed(set.seed, …)`.
- #260: при `dt = 0` системы пишут те же значения → blackboard сходится за кадр, «settled» не меняется; visual-smoke (один мир) не затронут — пустой канал = no-op. Тест: два контекста, N кадров, inbox/blackboard побайтно равны между прогонами **и** между порядками фаз.
- Повтор Play: канал живёт и умирает с набором `play`, каждый Play начинается с пустого.

## 6. Ввод для «UI-мир + 3D-мир»

Сейчас клик по UI доходит до 3D: default target — весь набор (§1). Правило поверх `input_router`, без новых привязок от панелей:
- `world_desc.input_layer` (int, по умолчанию 0) → поле контекста. Больший слой — выше (UI = 1).
- Контекст сообщает, где он забирает ввод: ctx-ресурс `inp::input_capture{std::vector<rect> regions; bool keyboard}`. UI-система пишет экранные прямоугольники своих интерактивных элементов (кнопки, панели, модалка — весь экран) по раскладке своего кадра.
- `route_input` внутри выигравшей привязки/цели: контексты по убыванию слоя; первый, чья область (из кадра N-1) содержит **текущий** курсор, получает полное состояние мыши, остальные — нейтральное. Проверка идёт по курсору этого кадра, поэтому клик по неподвижной кнопке не протекает в 3D даже в первом кадре; лаг остаётся только у раскладки (движущийся/только что появившийся виджет). Клавиатура — контексту с `keyboard = true` наивысшего слоя (фокус поля ввода, модалка). Ни одна область не задета → как сейчас (все контексты цели — полное). Захват «липкий» до отпускания кнопки, нажатой над UI (drag с UI не протекает в 3D, и наоборот).
- Без `input_layer`/`input_capture` поведение идентично текущему; в редакторе правило работает внутри привязки панели к набору (Game view → `play`).

## 7. Рендер для «UI-мир + 3D-мир»

Минимальное изменение (ADR-09 всё равно добавляет UI-пасс):
- `camera_component`: `layer` (int, по умолчанию 0), `clear` (`all | depth | none`, по умолчанию `all`), `projection` (`perspective | ortho`). Экстрактор пишет `render_priority = layer` (поле уже есть) и ортопроекцию.
- `render_frame` группирует пакеты по `render_priority` по возрастанию и прогоняет цепочку пассов на каждую группу (сейчас одна цепочка на все пакеты). Так skybox/transparent 3D-мира заканчиваются до UI. Opaque-пасс уважает `clear` (`rnd_opaque_pass.cpp:60-65`): оверлей чистит только глубину.
- Редактор: `camera_redirector` даёт backbuffer-камерам одного набора с одинаковым viewport **общую** цель, Game view показывает её. Порядок между наборами не нужен: виден один набор (`level` или `play`), превью рисуют в свои цели.
