# EPIC-57: Asset Identity & Database — постоянный ID ассета, база ассетов, обратные зависимости

**Theme:** infrastructure (resource, editor)
**Status:** design (стадия 3, без кода); развилки решены (Р27, Р28)
**Issue:** [#27](https://github.com/Prorok1015/OpenGL_Engine/issues/27)
**Depends on:** #24 (Problems), #7 (`__guid`/`__version`, сделано). Стыки: #28 EPIC-58 (миграция — владелец команды), #26 EPIC-56 (документы), #46 EPIC-71 (cook/манифест), #583 (пакеты), #570 (`assets://`)

---

## 1. Цель

- У каждого файла ресурсного дерева есть **постоянный ID**, который не меняется при переименовании и переносе.
- Ссылки в данных хранят ID, поэтому rename/move не ломает их.
- Редактор и агент видят, **кто ссылается** на ассет (обратные зависимости), и получают отчёт при rename/move/delete.

Критерии эпика из #27: «Rename/move не ломает ссылки», «Обратные зависимости видны в отчёте».

## 2. Решения, на которых стоит дизайн

**Владелец, Р3 в #27** (2026-11-05; уточнение заменяет ADR-05 из `CHIMERA_ROADMAP.md` §4 там, где они расходятся):

- Sidecar **`.resource`** рядом с **каждым** файлом ресурсного дерева, включая desc (`main.desc.resource`, `colormap.png.resource`). На папки не заводится.
- `.resource` — **единственный источник ID**; `__guid` внутри desc не нужен.
- Содержимое `.resource`: `__guid`, `__version`, `importer` и `settings` (настройки импорта), флаги ассета (например, «только для редактора»).
- **База ассетов** (ID ↔ путь, обратные зависимости):
  - строится обходом `.resource`, кэш в `cache://` с проверкой по времени и размеру;
  - обновляется наблюдателем файлов;
  - отсутствующий `.resource` создаёт редактор;
  - «осиротевший» `.resource` находится по хэшу содержимого, редактор предлагает связать;
  - пропавшие и лишние `.resource` видны в Problems (#24), в браузере ассетов скрыты.
- **Рантайм-ключ — ID**, строковый `res::tag` — способ адресации из кода, разрешается в ID.
- Ссылки сериализуются как `{guid, path}`. Ссылка только с путём (старые файлы, ручная правка, агент) остаётся валидной; guid дописывается при сохранении или миграцией. Миграция — только явной командой (Р3 в `CHIMERA_PLAN-2026-11.md`).
- Идентичность содержит guid **и хэш содержимого**, чтобы позже лёг манифест удалённого хранилища `assets://` (#570).
- Shipping: `.resource` в архивы не попадают; cook (#46) собирает один манифест (ID → архив, смещение, размер, тип, зависимости), переписывает ссылки на ID и хранит таблицу «путь → ID» для адресации из кода.

**Координатор (техревью PR #749, 2026-11-12):**

- Р-А: форма ссылки — объект `{guid, path}` (§4.4).
- Р-Б: rename сразу переписывает пути в ссылающихся файлах (§6.4).
- Стык с EPIC-58: команда миграции, бэкап, отчёт и подъём `format_version` манифеста — только у EPIC-58 (S4 #754); EPIC-57 регистрирует свои шаги (§8).

**Владелец, #568 (2026-11-12):**

- Р27 (Р-В): ссылки `{guid, path}` включаются **сразу**, мажорным подъёмом module API в этом эпике (4.0); игр на движке нет, ломать API допустимо. В тот же мажор входят #632 и #668. Мажор — **один PR** подъёма версии, всё остальное — уже на 4.x (§7.1).
- Р28 (Р-Г): ID → путь → обычный поиск по слоям; перекрытие ассета движка работает и для ссылок с ID, Problems предупреждает.

Расхождение документов: `CHIMERA_ROADMAP.md` ADR-05 (`__guid` в desc, `.meta` для png/glb, `res::tag` — ключ) и `DATA_FORMATS_V2.md` §`__guid` устарели в этих пунктах; пометки со ссылкой сюда — в story S57-13.

## 4. Модель идентичности

### 4.1. ID

- `res::asset_id` — 128-битный UUID (значение из `.resource` `__guid`, текст — 36 символов UUID v4, как у `desc::generate_guid()`).
- В памяти — два `uint64_t`; новый тип, **не поле `res::tag`** (см. §7).
- ID есть только у файлов ресурсного дерева с `.resource` (`res://`, `engine://`, позже `package://`). У `memory://`, `user://`, `cache://`, `code://`, `edt://` и сгенерированных подресурсов (`memory://overrides/…`, выход импортёра) ID нет: они адресуются тегом, как сейчас.

### 4.2. Файл `.resource`

```json
{
    "__type" : "resource_meta",
    "__version" : 1,
    "__guid" : "6f1c0b52-6d2f-4c1a-9a7e-3d1f2b8c9e01",
    "importer" : "texture",
    "settings" : { "srgb" : true, "mips" : true },
    "flags" : [ "editor_only" ]
}
```

- Имя — `<имя файла>.resource` рядом с файлом.
- Пишется отформатированным JSON (как desc после #559), ключи в этом порядке.
- `importer`/`settings` — место для EPIC-62/EPIC-34 (повторный импорт с сохранением ID); в этом эпике только читаются и сохраняются как есть.
- Хэш содержимого в `.resource` **не пишется**: он менялся бы при каждой правке файла и шумел бы в VCS. Хэш живёт в базе (§4.3).
- Агент не пишет `.resource` напрямую: `desc.write`/`desc.create` на `*.resource` — отказ; ID меняют только команды `asset.*` и действия Problems.

### 4.3. База ассетов

- Кэш в `cache://asset_db/` (пересобираемый, не в VCS).
- Запись на файл: `id`, `path` (тег), `size`, `mtime`, `content_hash` (`"fnv1a64:<hex>"`, алгоритм в префиксе — позже `sha256:` для #570 без смены формата), `type` (вид ассета по суффиксу), `desc_type` (`__type` из заголовка desc-файла: по нему фильтрует пикер ссылок EPIC-56), `flags`, **прямые ссылки** (список `{id?, path, json_pointer}`).
- Обратный индекс строится из прямых ссылок при загрузке базы.
- Проверка свежести — `(size, mtime)` файла и его `.resource`; хэш пересчитывается только у изменившихся.
- Обновление — подписка на `resource_system::subscribe_changes` для `res://` (уже включена: `report_changes`), батчами на главном потоке.
- **Запись кэша атомарна** (временный файл + rename, как у `vfs_resolver`) и под файловой блокировкой проекта: второй редактор на том же проекте кэш не пишет (читает или пересобирает в памяти).
- Владелец — редактор (`edt::asset_database`); движку нужен только интерфейс разрешения (§5).
- **Content roots не перекрываются** (#856): если один корень лежит в другом (`["res", "res/sub"]`), один файл попал бы под два тега `res://`, а любой обход корней встретил бы его дважды. Поэтому `prj::parse_manifest` отказывает по путям из манифеста без учёта регистра, а `prj::verify_project_mounts` при открытии проекта — по реальным путям, которые может сблизить ссылка. Исключать внутренний корень из обхода внешнего не стали: `res://sub/x.png` по-прежнему резолвился бы через внешний слой.

### 4.4. Ссылка в данных

Форма — объект (Р-А, решение координатора):

```json
"material" : { "guid" : "6f1c0b52-…", "path" : "res://materials/red.mat.desc" }
```

- Читатели принимают обе формы: строку (только путь) и объект.
- Объект ссылки отличается от inline-desc отсутствием `__type`.
- Разрешение: есть `guid` и он в индексе → путь из индекса → обычный поиск по слоям (Р-Г, §9); иначе — по `path`, как сейчас.
- Писатели (редактор, MCP, импорт) пишут объект, если у цели есть ID; иначе строку.
- Inline-читатели (`desc_describe_ops.h`, `get_field_desc`) разбирают объект и зовут экспортируемый `resource_system::resolve_reference(guid, path)`: как именно ссылка превращается в файл, решает движок, а не код модуля (§7.1).
- Строка `путь|guid` отклонена: inline-читатель `res_tag`-поля (`desc_describe_ops.h:242-250`) в старом модуле построил бы тег `res://a.desc|<guid>` — тихая порча данных.

## 5. Рантайм: ключ — ID

После мажора 4.0 (§7.1) функции кэша и алиасов `resource_system` больше не inline, поэтому кэш свободно меняет ключ и раскладку.

- В движке появляется **`res::asset_index`** (экспортируемый интерфейс): `std::optional<asset_id> id_of(const tag&)`, `std::optional<tag> path_of(asset_id)`.
  - В редакторе его реализует база ассетов (§4.3).
  - В Shipping — манифест cook (#46); до #46 Shipping работает без индекса (ключ — тег, как сейчас).
- **Кэш по ID:** `require_block` и бывшие inline-функции (`key_for`, `warmup`, `pin_resource`, `push_resource_to_cache`, `find_cached`, `resolve_alias`) переводят тег в ID через индекс; ключ кэша — `{id, type}` для файлов с ID и `{tag, type}` для остальных (`memory://`, сгенерированные). Одна карта, без второй рядом.
- `resolve_reference(guid, path)`: guid в индексе → путь из индекса; иначе `path`; дальше — обычный поиск по слоям (Р-Г).
- **Следствия:**
  - блок, взятый как `require("res://a.desc")` до переименования `a` → `b`, — тот же, что `require("res://b.desc")` после него: загруженный ресурс переживает rename без перезагрузки, закреплённый модулем — тоже. Старый путь `a` после rename не разрешается (журнала старых путей нет, решение координатора в #770);
  - два написания одного файла (регистр на Windows) — один блок; копия с тем же ID (§10) получает ID в индексе только у файла, который выбирает `path_of`, копия кэшируется по своему тегу;
  - `res_handle::get_tag()` показывает путь на момент запроса (для логов и UI); сравнение хендлов — по блоку, не по тегу.
  - Рёбра графа (`m_dependents`) и `signal_changed` переходят на ID там, где он есть.
- **Порядок rename и наблюдателя:** наблюдатель отдаёт `deleted(a)` + `created(b)` (или `renamed`), и `signal_changed(a)` выселил бы блок раньше, чем база сопоставит пару. Поэтому батч изменений `res://` сначала обрабатывает база (пары по guid, §6.4), и только потом `resource_system` получает «переименован», а не «удалён».
- Без индекса (Shipping до #46, тесты) поведение прежнее: ключ — тег.

Сделано (#770, часть 1 — движок):
- `res::asset_index` (`res_asset_index.h`).
- `resource_system::set_asset_index`, `delivering_batch()` и `apply_asset_batch(through, moved)`.
- Привязка `tag → ключ` (решение координатора в #770). Первая запись тега (блок, закрепление, алиас, ребро, наблюдатель) привязывает его к ключу: ID как тег `asset-id://<uuid>`, если индекс его даёт, иначе сам тег. Существующие записи ищутся по привязке. Перепривязка — только на главном потоке, в `set_asset_index` и `apply_asset_batch`: записи переезжают на новый ключ (кэш, закрепления в root и слоях, алиасы, рёбра, наблюдатели), ни одна не теряется.
- `signal_changed` файла с ID: есть на диске — выселение по ID сразу; нет — ждёт batch владельца индекса. То же для `remove` / `rename` через `resource_system`.
  - Номер batch назначается, когда наблюдатель его создаёт, и в очередь главного потока batch кладётся под тем же замком: порядок в очереди совпадает с порядком номеров.
  - Ждущая запись на mount с отчётом получает номер batch, где есть её путь; на mount без отчёта — первого batch, созданного после неё. `apply_asset_batch(n)` решает только записи с номером ≤ n.
  - Запись, которую ни один batch не назвал (файл ушёл и вернулся за один опрос наблюдателя, имя, которое наблюдатель пропускает), ждёт до `set_asset_index`.
  - `remove` / `rename` регистрируют запись до операции. Уже ждущий файл сохраняет свою запись и номер. Запись считает незавершённые операции и подтверждается событием с диска или успешной операцией; отказ операции снимает её, только если других операций нет и подтверждения не было. `forget` ставит только успешная операция.
  - Перед `forget_erased` проверяется, что файла действительно нет (во всех корнях `res://`): файл, созданный заново до решения batch, или файл того же пути в нижнем корне (тег теперь отдаёт его) выселяется без потери закреплений.
  - Перенос с тем же ID сохраняет блок и закрепления; наблюдатели и отображения алиасов следуют за файлом. Наблюдатель получает новый путь, `unwatch` находит его по тегу регистрации.
  - Всё прочее выселяется; удалённое через `remove`/`rename` забывается, как `erase`.
  - `set_asset_index` выселяет все ждущие сразу.
- `resolve_reference`: guid → `path_of` → путь.
- Коллизия при перепривязке (#858): у нового ключа уже есть живой блок другого написания, а под старым ключом жив свой. Тогда старый блок остаётся под ключом как вытесненный: запросы получают живой, а вытесненный считается в `pending_loads()`, записывает свои рёбра, держит рёбра ключа и выселяется вместе с ключом. Когда держателей у него не остаётся, он уходит. Закрепление нового ключа не меняется.
- Контракт индекса: отвечает из неизменяемого снимка, не ждёт и не зовёт `resource_system` (debug-проверка).
- Публичный `cache_key{tag, type}`, `res_resource_block`, `res_handle` и ключ раскладки модуля не меняются: inline-код `res_system.h` и `res_handle` к данным-членам `resource_system` не обращается.

Сделано (#770, часть 2 — редактор):
- `edt::asset_index_snapshot` (`Editor/code/editor_system/assets/edt_asset_index.h`) — `res::asset_index` над записями `edt::asset_database`: неизменяемые карты «путь → ID» (по ключу слияния, так что написания одного файла на Windows — один ID) и «ID → путь», подменяемые на главном потоке.
- Дубликаты ID: ID получает файл по правилу §10 (`edt::holds_id_before`, то же, что у Problems); копия загружается как отдельный файл. Предупреждение — одно на пару (ID, путь копии) за сессию.
- Перенос, найденный обходом (batch отложен за обходом и получил номер больше): связь передаёт его снова с каждым следующим `apply_asset_batch`, пока не пройдёт batch с большим номером.
- Если база выбросила изменения, ждавшие обхода (больше лимита), связь снимает индекс и ставит его заново после следующего обхода. Обход без отложенных изменений двигает `applied_through()` до последнего полученного batch.
- `edt::asset_index_link` (тот же файл) связывает базу и `resource_system`:
  - индекс подключается после первого обхода базы;
  - после каждого batch базы: пересборка снимка и `apply_asset_batch(applied_through(), moved)`;
  - если записи изменились вне batch, `poll()` пересобирает снимок и зовёт `apply_asset_batch` без переносов;
  - индекс снимается до того, как база уходит.
- `asset_database::applied_through()` — номер последнего batch `res://`, который база взяла в себя (номер читается в её listener'е через `delivering_batch()`). Batch, отложенный из-за идущего обхода, засчитывается после повтора. Плюс `walked_once()`.
- Редактор (`edt_editor_system`) держит связь рядом с базой и опрашивает её в том же тике.

## 6. Редактор и агент

### 6.1. Создание `.resource`

- Новый файл, появившийся во время работы редактора (через редактор, MCP `desc.create/write`, импорт, экспорт, или снаружи — наблюдатель) — `.resource` создаётся сразу, автоматически.
- Файлы существующего проекта без `.resource` — только явной командой миграции (§8), не молча при открытии. До миграции они видны в Problems «нет ID» и работают по пути.
- Проект из шаблона получает **свежие** ID (шаблон хранит `.resource`, при создании проекта guid перевыпускаются, ссылки внутри шаблона переписываются).
  Сделано (#765): `prj::create_project` принимает `prepare`, редактор передаёт `edt::give_template_fresh_ids` (`Editor/code/editor_system/controller/edt_template_ids.h`) — в staging-папке до переименования: `.resource` шаблона получают новые guid, файлы без `.resource` (шаблон `Editor/data/templates/projects/empty` их не хранит) — новые, корневой `__guid` desc и ссылки `{guid, path}` на старые ID переписываются.
- `__guid` в desc **продолжает писаться до миграции проекта** (иначе сохранение до миграции теряет id и `level_guid`). После шага `asset_ids` (§8) desc этого проекта сохраняются без `__guid`; `level_guid` и Save As берут ID из `asset_index` (новый файл — новый `.resource`).
  Сделано (#772) правилом по файлу, без флага проекта: сохранение **держит `__guid`, который был у файла, и никогда не придумывает новый**.
  - `desc_adapter_t::serialize` пишет `get_guid()` экземпляра только если он не пуст.
  - Уровень: тот же файл — `level_guid` (то, что было в файле). Save As на новый путь и первое сохранение нового уровня — без `__guid`; ID даёт `.resource` от базы (`queue_new_file`) или от миграции. Save As поверх другого файла держит его корневой `__guid` (`edt::desc_root_guid`) — из того слоя, откуда файл читает `res://`, без лимита размера; файл есть, но не читается — Save As отказывает.
  - `level_guid` — не ID уровня, а `__guid` его файла до миграции. ID уровня — `asset_index::id_of(level_tag)`; сейчас его никто не спрашивает.
  - Процесс-декодер импорта отказывает выводу с `__guid` на любой глубине.
  - Шаг `assets.ids_drop_desc_guid` (§8) снимает `__guid`, после него его не пишет никто. Проект до миграции ничего не теряет: по `__guid` никто не ищет, а ссылки по ID появляются только с `assets.refs`.

### 6.2. Problems (#24), источник `assets`

- нет `.resource` (предупреждение, действие «создать»);
- `.resource` без файла — «сирота»: если в базе есть файл без `.resource` с тем же хэшем, действие «связать»;
- **два файла с одним ID** (копия файла вместе с `.resource`) — ошибка, действие «выдать новый ID копии» (копией считается более новый по mtime);
- ссылка на ID, которого нет в базе (сломанная ссылка) — ошибка с переходом к месту ссылки.

Браузер ассетов и `asset.query` скрывают `*.resource`.

### 6.3. Обратные зависимости

- Панель/секция «Используется в» у выбранного ассета; MCP `asset.usages {path|guid}` → `[{file, json_pointer}]`.
- Прямые ссылки собираются статически тем же обходом, что проверка перед Play: поля-теги по схеме, `__parent`, компонент-строка префаба, манифест проекта, «свободные» строки с протоколом в полях без схемы (как предупреждения).

### 6.4. Rename / move / delete (редактор и MCP `asset.rename/move/delete`)

- Включается `file_operations` для `res://` **только в редакторе** (в Shipping — нет).
- `.resource` переносится вместе с файлом, одной операцией.
- **Отказ:** файлы слоя движка (`core/res`, видимые через `res://` проекта и `engine://`); на Windows — смена только регистра имени (файловая система её не различает, тег — различает).
- Ссылки с `guid` не ломаются; путь в них и **ссылки только с путём** в ссылающихся файлах переписываются в той же операции (Р-Б), одна запись в истории.
- Результат — отчёт: перенесено, какие файлы переписаны, что не удалось.
- Delete: если есть ссылающиеся — отказ с их списком, если не задан `force`; при `force` ссылки становятся сломанными и видны в Problems.
- **Пары rename сопоставляются по guid внутри `.resource`**: `.resource` с guid, который только что «удалён», — это перенос. Эвристика наблюдателя по `(size, mtime)` для этого не используется.
- Внешний rename (проводник, `git mv`): если `.resource` переехал вместе с файлом — база связывает по guid, ссылки целы. Если файл переехал без `.resource` — «сирота» + «нет ID» с одинаковым хэшем → действие «связать».

## 8. Миграция существующих проектов (стык с #28 — решение координатора)

**EPIC-58 владеет** командой «Обновить проект», бэкапом, отчётом и подъёмом `format_version` манифеста (только EPIC-58 S4, #754). EPIC-57 только **регистрирует два шага проекта** (`project_step`) и номер версии манифеста не задаёт и не хардкодит.

1. **`asset_ids`** — до типовых миграций desc:
   - создать `.resource` у каждого файла ресурсного дерева без него; если в desc есть `__guid` — взять его (у уровней он уже используется как `level_guid`), иначе новый;
   - удалить `__guid` из desc — отдельным шагом `assets.ids_drop_desc_guid` (post, #772): у desc с `.resource` снимается корневой `__guid`, а `__guid`, не совпавший с ID его `.resource`, — строка в отчёте;
   - созданные файлы — в отчёт EPIC-58, чтобы откат их удалил.
2. **`asset_refs`** — после типовых миграций: переписать ссылки на объекты `{guid, path}` по базе.

- Редактор открывает проект без миграции: всё работает по путям, Problems показывает «нет ID».
- Проект с перекрывающимися content roots (§4.3) миграция не сканирует: манифест не проходит `prj::parse_manifest` и считается invalid (#856).
- Повторный запуск шагов ничего не меняет.
- Деревья репозитория (`core/res`, `projects/sandbox`, `tests/static_game`) получают `.resource` один раз отдельной story (S57-6), ID фиксированы и попадают в SDK.
  Сделано (#768): `tools/ci/asset_ids.py` — `--write <деревья>` создаёт недостающие `.resource` (desc берёт корневой `__guid`, остальные — новый UUID; существующие не трогает, повторный запуск ничего не меняет), `--check` (CI, job без сборки) требует `.resource` у каждого файла `core/res`, `projects/sandbox/res`, `tests/static_game/project/res` в байтах `res::write_asset_meta`, без сирот и повторов ID. Обход — как у базы ассетов редактора (скрытые и `res::is_ignored_asset_name`, ссылки, сабмодуль `samples` пропускаются); таблица игнорируемых имён `tests/data/asset_ignored_names.txt` общая для `--self-test` и `tests/res_repo_layout_tests.cpp`, тот же тест проверяет и сами `.resource`.

## 10. Риски

- **Копирование файла вместе с `.resource`** даёт два файла с одним ID — ловится базой (§6.2), но до исправления ссылки по этому ID неоднозначны. ID держит один файл — по одному правилу для Problems и индекса (`edt::holds_id_before`): файл нижнего слоя (на ID ассета движка ссылаются другие), затем более старый по mtime, затем меньший путь. Ссылки по ID разрешаются в него; копия загружается как отдельный файл.
- **Шум в VCS:** число файлов в дереве удваивается. `.resource` маленькие, стабильные (без хэша), меняются только при смене настроек импорта.
- **Внешние инструменты** (`git mv`, проводник) переносят `.resource` только если пользователь переносит оба файла; иначе — «сирота» и ручное «связать».
- **Регистр путей:** теги сравниваются с учётом регистра, а Windows — нет. Два тега одного файла станут одним ID через базу — это исправление, но смена поведения кэша; покрыть тестом.
- **Производительность первого обхода** большого дерева (хэш всех файлов). Хэш считается лениво, по `(size, mtime)`, в фоне через `job_service`; запросы по ещё не обойдённым путям работают по тегу.
- **Два редактора на одном проекте** — кэш базы под блокировкой (§4.3).
- **Агент пишет ссылки строкой** — остаются валидными; rename (Р-Б) и шаг `asset_refs` доводят их до объектов.
