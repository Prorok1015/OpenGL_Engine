# EPIC-57: Asset Identity & Database — постоянный ID ассета, база ассетов, обратные зависимости

**Theme:** infrastructure (resource, editor)
**Status:** design (стадия 3, без кода)
**Issue:** [#27](https://github.com/Prorok1015/OpenGL_Engine/issues/27)
**Depends on:** #24 (Problems), #7 (`__guid`/`__version`, сделано). Стыки: #28 EPIC-58 (миграция), #26 EPIC-56 (документы), #46 EPIC-71 (cook/манифест), #583 (пакеты), #570 (`assets://`)

---

## 1. Цель

- У каждого файла ресурсного дерева есть **постоянный ID**, который не меняется при переименовании и переносе.
- Ссылки в данных хранят ID, поэтому rename/move не ломает их.
- Редактор и агент видят, **кто ссылается** на ассет (обратные зависимости), и получают отчёт при rename/move/delete.

Критерии эпика из #27: «Rename/move не ломает ссылки», «Обратные зависимости видны в отчёте».

## 2. Решения владельца, на которых стоит дизайн

Р3 в #27 (2026-11-05, уточнение заменяет ADR-05 из `CHIMERA_ROADMAP.md` §4 там, где они расходятся):

- Sidecar **`.resource`** рядом с **каждым** файлом ресурсного дерева, включая desc (`main.desc.resource`, `colormap.png.resource`). На папки не заводится.
- `.resource` — **единственный источник ID**; `__guid` внутри desc не нужен.
- Содержимое `.resource`: `__guid`, `__version`, `importer` и `settings` (настройки импорта), флаги ассета (например, «только для редактора»).
- **База ассетов** (ID ↔ путь, обратные зависимости):
  - строится обходом `.resource`, кэш в `cache://` с проверкой по времени и размеру;
  - обновляется наблюдателем файлов;
  - отсутствующий `.resource` создаёт редактор;
  - «осиротевший» `.resource` находится по хэшу содержимого, редактор предлагает связать;
  - пропавшие и лишние `.resource` видны в Problems (#24), в браузере ассетов скрыты.
- **Рантайм-ключ — ID**, строковый `res::tag` — способ адресации из кода, разрешается в ID.
- Ссылки сериализуются как `{guid, path}`. Ссылка только с путём (старые файлы, ручная правка, агент) остаётся валидной; guid дописывается при сохранении или миграцией. Миграция — только явной командой (Р3 в `CHIMERA_PLAN-2026-11.md`).
- Идентичность содержит guid **и хэш содержимого**, чтобы позже лёг манифест удалённого хранилища `assets://` (#570).
- Shipping: `.resource` в архивы не попадают; cook (#46) собирает один манифест (ID → архив, смещение, размер, тип, зависимости), переписывает ссылки на ID и хранит таблицу «путь → ID» для адресации из кода.

Расхождение документов: `CHIMERA_ROADMAP.md` ADR-05 (`__guid` в desc, `.meta` для png/glb, `res::tag` — ключ) и `DATA_FORMATS_V2.md` §`__guid` устарели в этих пунктах. В рамках эпика они получают пометку со ссылкой сюда.

## 4. Модель идентичности

### 4.1. ID

- `res::asset_id` — 128-битный UUID (значение из `.resource` `__guid`, текст — 36 символов UUID v4, как у `desc::generate_guid()`).
- В памяти — два `uint64_t`; новый тип, **не поле `res::tag`** (см. §7).
- ID есть только у файлов ресурсного дерева с `.resource` (`res://`, `engine://`, позже `package://`). У `memory://`, `user://`, `cache://`, `code://`, `edt://` и сгенерированных подресурсов (`memory://overrides/…`, выход импортёра) ID нет: они адресуются тегом, как сейчас.

### 4.2. Файл `.resource`

```json
{
    "__type" : "resource_meta",
    "__version" : 1,
    "__guid" : "6f1c0b52-6d2f-4c1a-9a7e-3d1f2b8c9e01",
    "importer" : "texture",
    "settings" : { "srgb" : true, "mips" : true },
    "flags" : [ "editor_only" ]
}
```

- Имя — `<имя файла>.resource` рядом с файлом.
- Пишется отформатированным JSON (как desc после #559), ключи в этом порядке.
- `importer`/`settings` — место для EPIC-62/EPIC-34 (повторный импорт с сохранением ID); в этом эпике только читаются и сохраняются как есть.
- Хэш содержимого в `.resource` **не пишется**: он менялся бы при каждой правке файла и шумел бы в VCS. Хэш живёт в базе (§4.3).

### 4.3. База ассетов

- Кэш в `cache://asset_db/` (пересобираемый, не в VCS).
- Запись на файл: `id`, `path` (тег), `size`, `mtime`, `content_hash` (`"fnv1a64:<hex>"`, алгоритм в префиксе — позже `sha256:` для #570 без смены формата), `type` (вид ассета по суффиксу), `flags`, **прямые ссылки** (список `{id?, path, json_pointer}`).
- Обратный индекс строится из прямых ссылок при загрузке базы.
- Проверка свежести — `(size, mtime)` файла и его `.resource`; хэш пересчитывается только у изменившихся.
- Обновление — подписка на `resource_system::subscribe_changes` для `res://` (уже включена: `report_changes`), батчами на главном потоке.
- Владелец — редактор (`edt::asset_database`); движку нужен только интерфейс разрешения (§5).

### 4.4. Ссылка в данных

Форма ссылки — **развилка Р-А** (§9). Рекомендация — объект:

```json
"material" : { "guid" : "6f1c0b52-…", "path" : "res://materials/red.mat.desc" }
```

- Читатели принимают обе формы: строку (только путь) и объект.
- Объект ссылки отличается от inline-desc отсутствием `__type`.
- Разрешение: есть `guid` и он в индексе → файл по ID (путь в ссылке не важен); иначе — по `path`, как сейчас.
- Писатели (редактор, MCP, импорт) пишут объект, если у цели есть ID; иначе строку.

## 5. Рантайм: «ключ — ID» без поломки ABI

`res::tag`, `res_handle<T>`, `res_dep` входят в `module_layout_key`; `cache_key` строится inline в коде модуля. Менять их раскладку — мажорный подъём API и отказ всем модулям. Поэтому:

- В движке появляется **`res::asset_index`** (экспортируемый интерфейс): `std::optional<asset_id> id_of(const tag&)`, `std::optional<tag> path_of(asset_id)`.
  - В редакторе его реализует база ассетов (§4.3).
  - В Shipping — манифест cook (#46); до #46 Shipping работает без индекса (ключ — тег, как сейчас).
- `resource_system::find_or_insert_cache(cache_key)` (экспортируемая, не inline) внутри переводит `{tag, type}` → `{id, type}` через индекс и хранит блоки во **внутренней** карте по ID; для файлов без ID — по тегу, как сейчас. Раскладка `cache_key` не меняется.
- Следствия:
  - `require("res://a.desc")` и `require("res://b.desc")` после переименования `a` → `b` дают **один и тот же блок**; загруженный ресурс переживает rename без перезагрузки.
  - `res_handle::get_tag()` показывает путь на момент запроса (для логов и UI); сравнение хендлов — по блоку, не по тегу.
  - Рёбра графа (`m_dependents`) и `signal_changed` переходят на ID там, где он есть: изменение файла по новому пути находит тех же зависимых.
- Объём изменений — внутри `res_system.cpp`; новые экспортируемые функции — minor-подъём API.

## 6. Редактор и агент

- **Создание `.resource`:**
  - Новый файл, появившийся во время работы редактора (через редактор, MCP `desc.create/write`, импорт, экспорт, или снаружи — наблюдатель) — `.resource` создаётся сразу, автоматически.
  - Файлы существующего проекта без `.resource` — только явной командой миграции (§8), не молча при открытии. До миграции они видны в Problems «нет ID» и работают по пути.
- **Problems** (#24), источник `assets`:
  - нет `.resource` (предупреждение, действие «создать»);
  - `.resource` без файла — «сирота»: если в базе есть файл без `.resource` с тем же хэшем, действие «связать»;
  - **два файла с одним ID** (копия файла вместе с `.resource`) — ошибка, действие «выдать новый ID копии» (копией считается более новый по mtime);
  - ссылка на ID, которого нет в базе (сломанная ссылка) — ошибка с переходом к месту ссылки.
- **Браузер ассетов и `asset.query`** скрывают `*.resource`.
- **Обратные зависимости:**
  - панель/секция «Используется в» у выбранного ассета;
  - MCP `asset.usages {path|guid}` → `[{file, json_pointer}]`;
  - прямые ссылки собираются статически тем же обходом, что проверка перед Play: поля-теги по схеме, `__parent`, компонент-строка префаба, манифест проекта, «свободные» строки с протоколом в полях без схемы (как предупреждения).
- **Rename / move / delete** (редактор и MCP `asset.rename/move/delete`):
  - включается `file_operations` для `res://` **только в редакторе** (в Shipping — нет);
  - `.resource` переносится вместе с файлом, одной операцией;
  - ссылки с `guid` не ломаются; путь в них и **ссылки только с путём** в ссылающихся файлах переписываются (развилка Р-Б);
  - результат — отчёт: перенесено, какие файлы переписаны, что не удалось;
  - delete: если есть ссылающиеся — отказ с их списком, если не задан `force`; при `force` ссылки становятся сломанными и видны в Problems.
- **Внешний rename** (проводник, `git mv`): если `.resource` переехал вместе с файлом — база связывает по ID, ссылки целы. Если файл переехал без `.resource` — «сирота» + «нет ID» с одинаковым хэшем → действие «связать».

## 7. Влияние на module API и форматы

| Что | Влияние |
|---|---|
| `res::tag`, `res_handle`, `res_dep`, `res_resource_block`, `cache_key` | Раскладка **не меняется** (§5) |
| `res::asset_index`, `asset_id`, новые функции `resource_system` | Экспорт, **minor** |
| Форма ссылки-объекта (§4.4) | Читается inline-кодом модуля (`res_tag_json.h` `value_to<res::tag>`, `desc_describe_ops.h` для `res_handle`-полей компонентов модуля). Старый модуль не прочтёт объект → **требует решения** (развилка Р-В) |
| `__guid` в desc | Перестаёт писаться (`desc_adapter_t::serialize`); при чтении переносится в `.resource` миграцией |
| Формат проекта | `k_manifest_format_version` 1 → 2 после миграции (§8, стык #28) |
| Editor API | Новые MCP-команды `asset.*` (minor), `.resource` скрыт в `asset.query` |

## 8. Миграция существующих проектов (стык с #28)

Команда «Обновить проект» (редактор и MCP, только явно), с резервной копией и отчётом (механизм бэкапа и отчёта — общий с #28):

1. Создать `.resource` у каждого файла ресурсного дерева без него. Если в desc есть `__guid` — **взять его** (у уровней он уже используется как `level_guid`), иначе новый.
2. Удалить `__guid` из desc.
3. Переписать ссылки на объекты `{guid, path}` (по базе).
4. Поднять `k_manifest_format_version` до 2.

- Редактор открывает проект версии 1 без миграции: всё работает по путям, Problems показывает «нет ID».
- Проект версии 2 в старом редакторе — отказ по версии манифеста (уже есть).
- Файлы движка (`core/res/*`) получают `.resource` в репозитории один раз (тот же шаг, выполненный над движком), их ID фиксированы и попадают в SDK.

## 9. Развилки для владельца

**Р-А. Форма ссылки в JSON.**
- А1 (рекомендую): объект `{"guid": "...", "path": "res://..."}`. Явно, без разбора строк; отличается от inline-desc отсутствием `__type`. Цена: читатели тега (схема `json_fits`, `res_tag_json`, `get_field_desc`, preflight, `component.set`, виджет инспектора) учатся объекту — они собраны в нескольких местах.
- А2: одна строка `res://a/b.desc|<guid>` (`|` запрещён в путях Windows). Поле остаётся строкой, меньше правок в читателях, но это разбор строки внутри тега, и на POSIX `|` в имени файла допустим.

**Р-Б. Rename переписывает пути в ссылающихся файлах?**
- Б1 (рекомендую): да, сразу, в той же операции, с отчётом. Иначе ссылки только с путём (агент, ручная правка, файлы до миграции) ломаются, а путь в `{guid, path}` устаревает и вводит в заблуждение при чтении файла.
- Б2: нет; путь обновляется при следующем сохранении ссылающегося файла. Меньше записей на диск и в VCS, но пути в файлах устаревают.

**Р-В. Новая форма ссылки и модули, собранные под старый API.**
- В1 (рекомендую): мажорный подъём module API в той story, где писатели начинают писать объект (вместе с отложенными до мажора #632 и #668). Старые модули отклоняются с «rebuild the project», как при 2.0.
- В2: писать объект только в файлы, которые читает движок, а в компоненты модулей — строку. Хрупко: какой компонент чей, решается только при загрузке.

**Р-Г. Ассет движка и файл проекта по тому же пути.**
- Сейчас файл проекта с путём ассета движка подменяет его для всех ссылок по пути.
- Г1 (рекомендую): ссылка с `guid` указывает на конкретный файл; подмена работает только для ссылок по пути. Problems предупреждает «перекрывает ассет движка».
- Г2: путь важнее guid, если файл по пути существует. Ломает rename (на старом месте может появиться новый файл).

## 10. Риски

- **Копирование файла вместе с `.resource`** даёт два файла с одним ID — ловится базой (§6), но до исправления ссылки по этому ID неоднозначны: разрешаются в старший по mtime файл.
- **Шум в VCS:** число файлов в дереве удваивается. `.resource` маленькие, стабильные (без хэша), меняются только при смене настроек импорта.
- **Внешние инструменты** (`git mv`, проводник) переносят `.resource` только если пользователь переносит оба файла; иначе — «сирота» и ручное «связать».
- **Регистр путей:** теги сравниваются с учётом регистра, а Windows — нет. Два тега одного файла станут одним ID через базу — это исправление, но смена поведения кэша; покрыть тестом.
- **Производительность первого обхода** большого дерева (хэш всех файлов). Хэш считается лениво, по `(size, mtime)`, в фоне через `job_service`; база доступна частично до конца обхода (запросы по ещё не обойдённым путям работают по тегу).
- **Агент пишет ссылки строкой** — остаются валидными; Б1 и «Обновить проект» доводят их до объектов.
