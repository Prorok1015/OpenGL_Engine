# EPIC-80: Игровой код в wasm-песочнице — три режима сборки

**Theme:** infrastructure
**Status:** idea (заготовка, без плана и без места в очереди)
**Issue:** [#1084](https://github.com/Prorok1015/OpenGL_Engine/issues/1084)
**Depends on:** #1004 (переделка редактора), EPIC-79 (#1068); правила веб-переносимости CONSTRAINT_22–25 (`docs/agent/CONSTRAINTS.toon`)

## 1. Цель

Решение владельца (2026-11-16): один исходник игрового кода собирается в трёх режимах.

| Режим | Где | Зачем |
|---|---|---|
| Песочница (wasm) | редактор по умолчанию; браузер — только он | модуль не портит память редактора и не лезет в файлы; надёжная горячая перезагрузка |
| Нативная DLL | редактор по выбору | отладка в IDE, профилирование (как сейчас `game.dll`) |
| Нативный статический | shipping-сборка | максимальная скорость, один машинный код |

Это первый шаг к веб-версии движка и редактора (wasm + `net://`): игровой код в браузере может быть только wasm.

## 2. Главное условие: API сначала под границу

wasm-модуль живёт в своей линейной памяти и не может получить указатель на `entt::registry` или компонент движка. Поэтому API игры:
- один C++-заголовок, против которого пишется игровой код;
- в режиме песочницы его функции — импорты из движка: идентификаторы сущностей, явные вызовы, view компонентов с копированием и записью обратно;
- в нативных режимах тот же заголовок реализован прямыми inline-вызовами движка (view — прямой указатель), без накладных расходов.

Проектируется сначала граница, нативная реализация выводится из неё. Обратный порядок (нативный API с прямыми указателями, потом перенос) не работает.

Следствие: большая часть текущего ABI модулей (ключ раскладки #614/#922, пины vtable, «поля только в конец») для песочницы не нужна — её заменяет явный API. Для нативной DLL правила остаются.

## 3. Риски

- **Расхождение режимов.** wasm32: `size_t` и указатели 4 байта, в нативе 8; выход за границы массива в wasm часто тихо читает свою память, в нативе падает (или наоборот). Защита: CI гоняет игровые тесты во всех режимах; фиксированные типы в данных (CONSTRAINT_25).
- **Отладка** wasm в IDE слабее — для неё остаётся нативная DLL.
- **Скорость** песочницы ниже нативной (ожидание ~1.2–2× при AOT) — тяжёлые системы остаются в движке; нужен замер на типичной игровой системе.

## 4. Открытые вопросы (DISCOVER)

- Рантайм в нативном редакторе: wasmtime / WAMR / wasm3; AOT или JIT.
- Цепочка сборки: `clang --target=wasm32-wasi` или Emscripten; где компилируется (локально / сервер для веба).
- wasm32 или memory64.
- Форма API: view, события, ресурсы (`res::` через движок), системы ECS из модуля.
- Миграция существующих модулей (`gs::game_module`) — переходный период с обоими API.
