## 1. Цель

- Любой desc-тип со схемой и флагом `is_document` открывается в редакторе как **документ данных** и правится инспектором из схемы. Изменения сохраняются в файл, отменяются и повторяются.
- Инспектор из схемы умеет строки, enum, списки (add/remove/**reorder**), словари, optional, структуры; показывает **итог против своего значения** (что унаследовано от `__parent`, что задано в файле) и сбрасывает поле к унаследованному.
- Ссылки выбираются **типизированным пикером**: в desc-ссылку можно положить только desc нужного типа, в тег — только файл подходящего расширения.

Критерии эпика из #26: «Любой `is_document` тип открывается и редактируется», «Списки поддерживают add/remove/reorder», «Пикер ссылок типизирован».

**Пользовательский сценарий владельца (F33, демо 2026-11-04, первый в тройке приоритетов):** «Параметры игры в Inspector — скорость, размер поля, цель победы, длительность эффектов без пересборки DLL». Модуль игры регистрирует схему своего документа-конфига, документ правится в инспекторе, игра читает значения в Play и подхватывает правку без пересборки.

## 3. Документ данных

### 3.1. Какие файлы открываются

- Файл `*.desc`, чей `__type` — тип со схемой и `is_document`. Тип читается из заголовка файла (`__type`), без загрузки ресурса.
- `is_document` ставится:
  - в C++ — **нешаблонным** сеттером `desc_system` (`mark_document(type_name)`) или `register_document<T>(name)`, который вызывает его после `schema_generator::make()`; inline-шаблоны, компилируемые в модуль, не меняются (окно 4.0 не нужно). Вариант `schema_kind::document` отклонён: конфликтует с `component`/`structure` и с ключом `"kind"` JSON-схемы;
  - модулем игры — тем же сеттером через `gs::module_context` (сценарий F33);
  - JSON-схемой — как сейчас (`"is_document": true`).
- **Тип документа должен быть привязан к схеме целиком** (все поля описаны схемой, без `custom` без кодека): только тогда итог цепочки `__parent`, собранный глубоким слиянием JSON (§3.2), совпадает с тем, что даёт рантайм (`copy_to` + `deserialize`). `mark_document` проверяет это и отказывает с понятной ошибкой.
- `desc_system::document_types()` перечисляет их (для «Создать документ…» и проверок); флаг выводится в `component.schema` и JSON Schema.
- **Движковые** типы в этом эпике документами не становятся (Р-Д, решение владельца Р31): только механизм и конфиги игры из модуля.

### 3.2. Модель

`edt::data_document : document` (`kind()` = `"data"`), по одному на открытый файл:

- **Своё** (`own`): JSON файла как он записан, с `__parent` и только заданными полями, после миграции в памяти (§3.4).
- **База** (`base`): глубокое слияние цепочки `__parent` (каждый родитель мигрирован в памяти тем же реестром) поверх значений схемы по умолчанию; без `__parent` — значения по умолчанию. База **пересчитывается**, когда меняется файл любого родителя цепочки (подписка на изменения их тегов).
- **Показ**: `schema_ui::compose(schema, {base, own})`; правка — `schema_ui::apply_edit(own, …, base, before, after)`: в файл попадают только поля, отличные от базы (`schema_ui::edit_component` уже это делает, нужна обёртка для документа).
- **Сохранение** пишет `own` — **не** `serialize` экземпляра, который сплющил бы наследование:
  - проверка `validate_desc_tree` (та же, что у MCP `desc.write`);
  - `stamp_tree` (текущая `__version`, порядок служебных ключей); `__guid` файла сохраняется;
  - красивый JSON (#559): **первое** сохранение файла с ручным форматированием переформатирует его — сказано в подсказке сохранения и в документации;
  - сохранение без изменений ничего не пишет;
  - запись через резолвер (`store_sync`, его песочница) и `signal_changed` — игра и редактор подхватывают через горячую перезагрузку.
- **Файл изменился на диске**, пока документ открыт (агент через `desc.write`, внешний редактор, VCS): версия файла (`code_version_of`) сверяется при сохранении; при расхождении — вопрос «перезагрузить / перезаписать / отмена». Чистый документ перезагружается молча.
- **Несколько документов** открыты одновременно (Р-А), каждый в своём док-окне (Р-Г). `document_manager` держит их список; доступ — через общие `find`/`active`/`close` без отдельного API (EPIC-59 потом обобщит).
- **Файл уже открыт** (как документ данных, префаб или сцена) — повторное открытие переводит фокус на него, второй экземпляр не создаётся.

### 3.3. Отмена и повтор

- Запись истории хранит **снимок `own` до и после** правки (одна правка инспектора может менять несколько указателей и чистить пустые родительские объекты — `prune_empty_parents`); ключ — путь файла.
- Одна правка инспектора = одна запись; правка, отложенная до отпускания виджета (`commit_if_idle`), — тоже одна.
- Отмена и повтор восстанавливают `own` **байт в байт**.
- Edit > Undo/Redo работают по активному документу (`document_manager::active()`), сохранение ставит точку `mark_saved`.
- Активный документ: явное открытие (превью префаба или агент) делает документ активным, даже если фокус остаётся в другом окне; тихое открытие (ссылка из Problems) активность не берёт. Дальше активность переходит при смене фокуса окна (`data_document_host::follow_focus`): окно данных — его документ, превью префаба — документ превью, любое другое обычное окно — сцена, служебные окна (меню, попапы, хост докспейса) ничего не меняют.

### 3.4. Версии (EPIC-58 §7.3, Р26)

- Открытие файла старой версии — миграция `own` в памяти тем же реестром (`migrate_tree`); файл не трогается.
- Окно документа показывает бейдж «устарел: vN → vM, Project → Migrate Project» (данные: `__version` файла, `current_version` типа).
- Сохранение пишет новую версию **с предупреждением** (вопрос перед первой записью такого файла).
- Файл новее, чем знает движок, — не открывается, понятная ошибка (как загрузка).

### 3.5. Создание документа

«Создать документ…» в браузере ассетов (контекстное меню папки): выбор типа из `document_types()`, имя файла; файл создаётся с `__type` и значениями по умолчанию через `create_sync` (не поверх существующего) и открывается.

## 4. Инспектор из схемы

Общий для компонентов и документов (`schema_ui`); всё ниже работает в обоих местах.

### 4.1. Итог против своего, сброс

- У каждого поля — метка «задано здесь», если указатель есть в `own` (для компонента — в `overrides`).
- Действие «Сбросить» (кнопка у поля и пункт контекстного меню) убирает указатель — поле снова унаследовано. Для группы/структуры — сброс всех её указателей.
- Подсказка у метки: «унаследовано от <родитель>» / «по умолчанию схемы».
- Метка — кнопка с меню: «Reset to inherited» (убирает только указатель) и, у присутствующего optional, «Unset»: при значении у родителя пишет `null`, иначе убирает указатель (с initializer-ом в схеме — оставляет `null`); оба — одна запись истории. Элементы списка без меток (список — одна запись).
- Два вида `null` (#861). У члена `std::optional` (`field_schema::nullable`) `null` — значение поля: nullopt. У остальных optional-полей (data-defined и `.optional()` у обычного члена) чтение заменяет `null` на default или на пустое значение вида. Поэтому там Unset пишет `null` только поверх значения родителя, а там, где значение уже равно прочитанному из `null`, выключен с подсказкой. `null` и отсутствующее значение с default показываются этим default, а не «(not set)».

### 4.2. Optional

- «Set» (уже есть) и **«Unset»** (новое): убирает значение из файла.
- `std::optional<T>` в C++ выводится как поле вида `T` с `optional = true` (сейчас — `custom`); `nullopt` ↔ поле отсутствует. Меняет вывод вида поля — окно 4.0 (§4.4, S56-2).

### 4.3. Списки

- **Reorder:** кнопки вверх/вниз у строки и перетаскивание за ручку; одна правка = одна запись истории.
- Больше 50 строк — постраничный показ (вместо обрезки).
- Элемент-структура проверяется по своей схеме (экспортируемый код `desc_schema_ops.cpp`; окно 4.0 не нужно).
- Override списка — целиком (как сейчас: массив в merge patch заменяется целиком); метка «задано здесь» — у всего списка.

### 4.4. Словари (Р-Б: решено — `field_kind::map` в окне 4.0)

- Новый `field_kind::map` — ключ строка, значение — вид `element` (не контейнер):
  - C++: `std::map<std::string, T>` / `std::unordered_map<std::string, T>`; JSON-схема: `"kind": "map", "element": …`; JSON-значение — объект.
  - **Правило приоритета:** у типа есть `json_codec` → поле остаётся `custom` (кодек работает только при `custom`). Иначе `component_tracker::tracked_components` и подобные поля перестали бы читаться. S56-2 перечисляет все затронутые типы (поиск по `has_json_codec` и по `map`/`unordered_map`/`optional` в описанных типах) и добавляет тест совместимости: сцена-образец до и после читается и пишется одинаково.
- Инспектор: строка на ключ (значение по виду элемента), «+ Add» с вводом ключа (пустой и повторный ключ — отказ), переименование ключа, удаление; порядок показа — по ключу.
- Override — по ключу (указатель `/field/<key>`), сброс ключа возвращает значение базы.
- Runtime-схемы с blob-раскладкой (`dyn_blob`, песочница #606) словарь не принимают — как массивы структур сейчас (схема отклоняется с понятной ошибкой).
- **Окно 4.0** (#758): S56-2 идёт сразу после S56-1, PR помечается «4.0-window». Если окно закроется раньше — запасной вариант: подсказка `.dict(element)` только для инспектора поверх `custom`-поля (проверки и агент словарь не видят).

### 4.5. Типизированный пикер ссылок

- Кнопка «…» у поля `res_tag`/`desc_ref` открывает всплывающий список: поиск по имени, путь, значок вида ассета. Только файлы `res://` проекта.
- **Фильтр:**
  - `desc_ref` с `ref_type` — только desc этого `__type` (или типа, наследника по реестру desc);
  - `res_tag` — по `field.filter` (расширения);
  - без ограничений — все файлы ресурсного дерева проекта.
- **Тип desc-файла:** запись базы ассетов S57-3 (#760) хранит поле `desc_type` — `__type` из заголовка desc-файла, читается при обходе вместе с хэшем (решение координатора). Пока S57-3 не влита, пикер временно читает заголовки найденных desc-файлов сам; после — берёт `desc_type` из базы.
- **Разделение со S57-9:** S57-9 владеет кодеком ссылок и существующим путём drop (`ASSET_PATH`); S56-9 (#798) — только UI пикера и фильтр по `ref_type`/расширениям (тот же фильтр применяется к drop через функцию S57-9).
- **Запись:** через кодек EPIC-57 — объект `{guid, path}` после S57-9, до него — строка `res://…`. Пикер не пишет ссылку с ID до миграции `.resource` проекта (EPIC-58 §7.3).
- Текстовый ввод остаётся (для путей, которых ещё нет), с прежней пометкой «нет протокола».

## 5. Сценарий F33: конфиг игры из `game.dll`

- Модуль описывает структуру конфига (`BOOST_DESCRIBE_STRUCT` + `field_attrs` с диапазонами и подсказками) и помечает её документом (§3.1).
- В проекте лежит файл `res://config/game.desc` этого типа (создаётся «Создать документ…»); двойной щелчок в браузере открывает документ, правка — в инспекторе, сохранение — Ctrl+S.
- Игра читает конфиг через `require<T>` и подписку на перезагрузку (или берёт хендл каждый кадр). В Play правка видна **после сохранения** (горячая перезагрузка по `signal_changed`) — Р-В, решение владельца Р30.
- Пример в шаблоне проекта (`Editor/data/templates/projects/empty`) и тест на тестовом модуле (`tests/module_dll`): правка через документ → Play читает новое значение без пересборки.

## 6. Агент (MCP)

- Документы данных агент правит уже существующими `desc.read`/`desc.write` (с проверкой схемы, вопросом человеку на замену файла). Новых команд эпик не добавляет.
- `desc.read` читает файл на диске и **не видит несохранённых правок** человека — сказано в документации MCP (S56-12).
- Документ, открытый у человека, при записи агентом получает «файл изменился на диске» (§3.2).

## 7. Влияние на API и форматы

| Что | Влияние |
|---|---|
| Флаг документа из C++ (`mark_document` / `register_document<T>` после `make()`) | Нешаблонный экспорт — minor, без окна 4.0 |
| `field_kind::map`, вывод `std::optional<T>` | Меняют `deduce_kind` в inline-шаблонах (`bind_described` в коде модуля) → **окно 4.0** (#758), S56-2, «4.0-window» |
| Проверка элементов-структур списков | Экспортируемый `desc_schema_ops.cpp` — без окна |
| `data_document`, список документов в `document_manager` | Editor API: новые классы и функции — minor editor API |
| Файлы данных | Формат не меняется: сохраняется то же, что пишет `desc.write`; ручное форматирование переформатируется при первом сохранении (#559) |

## 9. Риски

- **Сплющивание наследования** при неправильном пути сохранения — закрыто §3.2 (пишется `own`), тест: файл с `__parent` после правки одного поля сохраняет `__parent` и только это поле.
- **Смена `deduce_kind` ломает существующие поля с `json_codec`** — правило приоритета и тест совместимости сцены (§4.4).
- **Итог `__parent` в редакторе расходится с рантаймом** для типов не целиком на схеме — закрыто проверкой в `mark_document` (§3.1).
- **Две правки одного файла** (человек в документе, агент через `desc.write`) — сверка версии при сохранении (§3.2).
- **Окно 4.0:** словари и `std::optional` должны войти до конца стадии 3, иначе — запасной вариант (§4.4).
- **Пикер и ID:** до S57-9 пикер пишет пути; после — объекты. Тест обеих форм.
- **Большие списки и словари** — постраничный показ, без обрезки данных.
