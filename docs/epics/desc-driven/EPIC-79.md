# EPIC-79: Desc Binary Data — большие числовые данные desc в двоичном файле рядом

**Theme:** desc-driven
**Status:** in progress (PR1 — формат, чтение и запись пары; PR2 — геометрия читает `.bin`; PR3a — писатели геометрии пишут `.bin`)
**Issue:** [#1068](https://github.com/Prorok1015/OpenGL_Engine/issues/1068)
**Depends on:** EPIC-77 (#1007, `*.geom.desc`), EPIC-58 (#28, версии и миграция), EPIC-57 (#27, принадлежащие боковые файлы)

---

## 1. Цель

Вершины и индексы меша лежат в `*.geom.desc` числами JSON. Импорт большой модели даёт сотни мегабайт текста, разбор занимает секунды, лимит `res::max_geometry_json_bytes` (256 МБ) достигается быстро.

Решение: большие числовые массивы desc уходят в двоичный файл рядом с desc. В JSON остаётся только описание диапазона. Первые потребители — вершины и индексы геометрии (PR2).

## 2. Формат

### 2.1. Имя файла выводится, а не хранится

| desc | двоичный файл | промежуточный файл записи |
|---|---|---|
| `res://a/robot.geom.desc` | `res://a/robot.geom.bin` | `res://a/robot.geom.bin.new` |

- Правило: `<name>.<ext>.desc` → `<name>.<ext>.bin`, та же папка. У имени без внутреннего расширения (`a.desc`, `.geom.desc`) двоичного файла нет.
- Пути в JSON нет. Поэтому нет и проверок пути: `..`, протоколов, ссылок, чужих корней.
- Переименование и перенос desc не меняют его содержимое (файл `.bin` переезжает вместе с ним, PR4).
- `.bin` и `.bin.new` desc — не ассеты, **только если их desc лежит рядом**: `<x>.<y>.bin` и `<x>.<y>.bin.new` пропускаются, когда в той же папке того же слоя есть обычный файл (не ссылка) `<x>.<y>.desc`. Имя владельца даёт `res::desc_binary_owner_name` (`res_asset_meta.h`, те же правила основы, что у `binary_tag`), проверку соседа — `res::is_desc_binary_entry(папка, имя, is_dir)` (`res_asset_walk.h`, один `symlink_status`). Чужие `.bin` остаются ассетами: `scene.gltf.bin` (буфер glTF, desc рядом нет), `terrain.lod0.bin`, `foo.bin`. `res::is_ignored_asset_name` остаётся правилом только по имени и `.bin` не трогает. Правило соседа применяют все обходы: `res::walk_asset_layers`, инкрементальный список базы ассетов (и новый ID: `queue_new_file`; появление или удаление desc заново смотрит его `.bin`/`.bin.new`), панель слоёв ассетов, `asset.query`, `edt_template_ids`, скан миграции проекта, `tools/ci/asset_ids.py`. Пропущенный файл не получает записи в базе ассетов и `.resource`; его `.resource`, если есть, пропускается вместе с ним.

### 2.2. Тот же слой

В слоёной `res://` двоичный файл берётся из **того же слоя** (корня монтирования), что и desc, а не первым найденным по приоритету. Иначе desc верхнего слоя соединился бы с `.bin` нижнего.

- Реализация: `vfs_resolver::read_beside(anchor, tag, ...)` находит слой desc тем же `resolve_tag`, что и обычное чтение, и читает `.bin` из этого корня через `platform::beneath::read_beneath` (без следования ссылкам).
- `res::resource_system` не получает новых полей и публичных методов: `res_desc_binary.cpp` достаёт резолвер корня через `friend struct detail::desc_binary_access`.
- Слой desc при чтении `.bin` находится **заново по имени**, а не берётся из загрузки desc: система ресурсов не сообщает, из какого корня пришёл файл, а поле для этого нарушило бы раскладку. Поэтому, если у протокола больше одного корня (`vfs_resolver::root_count() > 1`), хэши проверяются всегда (`verify_hash` считается `true`). Несовпадение — ошибка `hash`, чужие данные не отдаются никогда.

### 2.3. Раскладка файла

| Смещение | Размер | Что |
|---|---|---|
| 0 | 4 | magic `SNKB` |
| 4 | 4 | версия, `u32` little-endian, сейчас 1 |
| 8 | … | данные диапазонов |

- Порядок байтов — little-endian (и для значений).
- `offset` считается **от начала файла** и не меньше 8 (размер заголовка). Писатель выравнивает начало каждого диапазона на 16 байт, читатель выравнивания не требует.
- Значения копируются в вектор вызывающего через `memcpy` (`res::copy_binary_values`), без невыровненного `reinterpret_cast`.

### 2.4. Диапазон в JSON

```json
"vertices": { "offset": 16, "size": 288, "sha256": "<64 hex>", "layout": "f32x3" }
```

`layout` — из закрытого словаря: `u8`, `u32`, `f32`, `u32xN`, `f32xN` (N от 1 до 32, без ведущего нуля). Всё остальное — отказ.

## 3. Проверки при чтении

Каждая — отказ с сообщением, где назван файл и диапазон (`range 1 (offset 48, size 12)`). Вид ошибки — `res::desc_binary_error`.

| Проверка | Вид |
|---|---|
| файла нет | `missing` |
| файл короче заголовка, не тот magic, не та версия | `header` |
| `offset + size` в `u64` с проверкой переполнения; `offset` внутри заголовка; диапазон вне файла; диапазоны одного запроса пересекаются | `range` |
| неизвестный `layout`; `size` не кратен размеру элемента | `layout` |
| SHA-256 диапазона не совпадает с записанным | `hash` |
| диапазоны или файл больше лимита — **до чтения** файла | `too_large` |
| не обычный файл (например, папка на месте `.bin`), ошибка чтения | `io` |
| больше `desc_binary::max_ranges` (64) диапазонов в одном запросе | `range` |

- Лимит по умолчанию — `res::desc_binary::max_file_bytes` (= `max_geometry_json_bytes`); вызывающий может передать меньший.
- При любом `verify_hash` проверяются: число диапазонов, раскладки, границы диапазонов (до чтения), заголовок и размер файла. У vfs-резолвера размер проверяется **до** чтения файла. Резолвер не-vfs не сообщает размер заранее: файл читается целиком, размер проверяется после; ошибка чтения — `io`, если файл существует, иначе `missing`.
- Диапазон нулевого размера допустим (его `offset` всё равно не меньше 8 и не дальше конца файла); пересечений он не даёт.
- `offset` и `size` в JSON — целые от 0 до 2^53. Дробное число, строка или значение больше 2^53 — отказ `binary_range_from_json` (читатель JSON на `double` не хранит такие точно).

## 4. Хэш

- SHA-256 (`cmn::sha256_hex`) — сверка пары desc ↔ `.bin`, не защита: кто правит проект, правит оба файла.
- Хэш каждого диапазона **всегда записан в desc** (`binary_range_from_json` без `sha256` отказывает): он нужен и для сверки, и для будущего хранилища по хэшу (раздел 9), даже если при обычной загрузке его не проверяют.
- Проверка — параметр чтения `verify_hash`. Обязательна при импорте, приёме ответа декодера, миграции, сохранении и в проверке проекта. При обычной загрузке адаптер геометрии просит проверку всегда (`verify_hash` = `true`), а `resource_system` пропускает SHA-256 для пары, которую его кэш знает неизменной, или при выключенной отладочной настройке (раздел 7.2, #1126).
- Если рядом лежит `.bin.new`, хэши `.bin` проверяются всегда, независимо от `verify_hash`: иначе не отличить устаревший `.new` от незавершённого сохранения.
- При нескольких корнях протокола хэши проверяются всегда (раздел 2.2).

## 5. Запись пары и восстановление

Порядок записи (без смены имён в git). Обычный путь — `desc_binary::save(system, desc, chunks, write_desc)`: он сам держит `save_lock` от шага 1 до шага 3 и между ними вызывает `write_desc(ranges)` (шаг 2; `false` — сохранение останавливается до коммита, старая пара читается). Отдельные шаги без замка невозможны: `write_pending` и `commit_pending` принимают `const save_lock&` и бросают `std::logic_error`, если замок другого desc (`save_lock::guards`).

1. `desc_binary::write_pending(system, lock, desc, chunks)` — пишет `<name>.<ext>.bin.new` (`store_sync`), возвращает диапазоны с `offset` и `sha256` и записанные байты (`desc_binary_written::file`).
2. Вызывающий пишет desc с новыми диапазонами.
3. `desc_binary::commit_pending(system, lock, desc, written)` — коммитит **проверенные байты**, а не перечитанные: если `.new` уже не содержит `written.file` (другое сохранение записало свой), отказ без какой-либо записи. Иначе `.bin` получает эти байты (замена через временный файл и rename, как любой `store`), затем `.new` удаляется, **только если всё ещё равен им**: сравнение на io-потоке непосредственно перед удалением (compare-before-remove).

Порядок чтения: сначала читается и проверяется `.bin`. Если рядом есть `.new`, хэши `.bin` проверяются (нужно, чтобы отличить устаревший `.new`). `.new` читается целиком, только если `.bin` не совпал с desc; иначе не читается (кроме удаления устаревшего в режиме `commit`).

| Сбой | Что на диске | Что делает читатель |
|---|---|---|
| до шага 2 | старая пара цела, рядом `.new` | хэши старой пары сходятся — читает её, `.new` не читает; режим `commit` удаляет устаревший `.new` |
| между шагами 2 и 3 | новый desc, старый `.bin` (или его нет), `.new` | хэш `.bin` не сходится, хэши `.new` сходятся — читает `.new`, `from_staged = true`, ничего не пишет; режим `commit` сам завершает шаг 3 проверенными байтами, если слой desc верхний и доступен на запись |
| после замены `.bin`, до удаления `.new` | пара согласована, лишний `.new` | читает `.bin`; режим `commit` удаляет `.new`, иначе его перезапишет следующее сохранение |

### 5.1. Режимы чтения (`desc_binary_recovery`)

- `use_staged` (по умолчанию) — чтение **ничего не пишет**: совпадающий с desc `.new` отдаётся с `from_staged = true`.
- `commit` — только для путей сохранения и редактора. Под `save_lock` коммитит проверенные байты `.new` (как шаг 3) и удаляет **устаревший** `.new` (`.bin` совпадает с desc) — только в этом режиме и всегда со сравнением перед удалением.
- Read-only монтирование, нижний слой и `limit_writes_to` слоя запрещают запись и в режиме `commit`: данные возвращаются, на диске ничего не меняется.

### 5.2. Гонки

- `save_lock` упорядочивает сохранения и восстановления одного desc **только внутри одного процесса**: это мьютекс процесса, другой процесс (второй редактор, `desc_resave`, внешний инструмент) его не видит. Внутри процесса сохранение и восстановление-с-коммитом упорядочены таблицей в `res_desc_binary.cpp` (мьютекс таблицы и `weak_ptr<std::recursive_mutex>` на тег `.bin`, мёртвые записи удаляются). Вложенный захват в одном потоке допустим. `write_pending` и `commit_pending` сами замок не берут, а требуют его параметром (замок именно этого desc), `save` и чтение в режиме `commit` берут его сами. Полей у `resource_system` не добавлено.
- **Между процессами** защищают только проверка `.new` перед записью `.bin` (check-before-write) и сравнение перед удалением (compare-before-remove), `save_lock` здесь не действует: восстановление не удалит `.new` более нового сохранения. Окно между сравнением и действием остаётся; два редактора на одном проекте не поддерживаются.

- `res://` смонтирован без `file_operations` (rename и remove там запрещены). Шаг 3 делает `vfs_resolver::commit_staged(staged, target, bytes)`, удаление устаревшего — `vfs_resolver::remove_if_same`: только верхний корень, под политикой записи, без общего rename. Записи этого процесса идут через тот же io-поток, поэтому между сравнением и удалением внутри процесса ничего не вклинится.
- Hot reload: при **перезагрузке** несовпадение хэша означает «оставить прежнее состояние и ждать следующего изменения», ошибка — только при первой загрузке. Это решает потребитель (PR2); PR1 отдаёт различимый вид ошибки `hash`.

## 6. ABI

- Новые типы (`res::binary_range`, `res::binary_layout`, `res::desc_binary_data`, …) не входят в `gs::module_layout_key`; модуль их не создаёт в inline-коде движка.
- Новые экспорты: свободные функции `res::desc_binary::*` (`save`, `write_pending`/`commit_pending` с `const save_lock&`) и класс `res::desc_binary::save_lock` (одно поле `std::shared_ptr`, метод `guards`), `res::parse_binary_layout`, `res::to_json(binary_range)`, `res::binary_range_from_json`; методы `vfs_resolver::read_beside`, `exists_beside`, `root_count`, `writes_beside`, `commit_staged`, `remove_if_same`. Полей в существующих типах не добавлено, ключ раскладки не меняется (`docs/abi/changes/1068.md`). Модулю, который вызывает `res::desc_binary`, нужен движок с #1068.

## 7.1. Сделано в PR2

- **Где диапазоны.** `geometry_desc::deserialize` видит в `"vertices"`/`"indices"` объект-диапазон и записывает его не в поля (раскладка `geometry_desc` не меняется), а в боковую таблицу по адресу объекта (`geom/rnd_geometry_binary.h`, внутренний заголовок). Состояние: `none` (массивы), `not_loaded` (диапазоны есть, данных нет), `loaded` (адаптер заполнил векторы). Копия (`copy_to`, конструктор копирования, присваивание — теперь вне строки) переносит состояние, деструктор его убирает. Массивы читаются как раньше. Страховки: конструктор по умолчанию (тоже вне строки) стирает запись, оставшуюся по его адресу (объект уничтожен без нашего деструктора); `serialize` отказывает любой геометрии с непустым `layout` и пустыми `vertices`, что бы ни говорила таблица. Таблица временная: в PR5 её заменяет член `geometry_desc` в той же партии изменения ключа раскладки.
- **Зависимость.** `geometry_desc_adapter::collect_dependencies` добавляет ребро на `.bin` (`desc_binary::binary_tag`), если в тексте у `"vertices"` или `"indices"` объект. Зависимость ничего не грузит (блок сразу готов): данные читает `deserialize` через `desc_binary::read` из слоя desc. Изменение `.bin` перезагружает геометрию через граф.
- **Чтение.** `geometry_desc_adapter::deserialize` читает оба диапазона одним `desc_binary::read`; `verify_hash` = `true` (до #1126 — константа `verify_hash_on_load`; теперь решает `resource_system`, раздел 7.2). Раскладка вершин — `u8` или `f32`/`f32xN`, где элемент — вся вершина и все атрибуты float (`/vertices/layout`); индексов — только `u32` (`/indices/layout`). Ошибка `desc_binary` — `res::load_error` с путём диапазона из сообщения (`range N`).
- **Проверки до GPU** (`detail::check_geometry_data`, только для данных из `.bin`; старые массивы проверяются после миграции в PR3a/PR4): шаг вершины не 0 (`/layout`), байты вершин кратны шагу (`/vertices`), индексов кратно 3 и каждый меньше числа вершин (`/indices`), есть float `position` (`/layout/position`), `position` и `uv` конечны (`/vertices`). Сохранённые `bounds` при данных из `.bin` не читаются: если ключ есть, границы (uv треугольника, как у импортёра) и дерево строятся заново из проверенных данных; без ключа их нет, как и сейчас у файлов без `bounds`. Цена построения дерева — замер PR3a.
- **Чтение как `desc_base`.** Запрос `.geom.desc` как `desc_base` идёт через общий `desc_adapter_t`: векторы пусты, состояние `not_loaded`. `serialize` такого объекта бросает `std::runtime_error` (пустой меш не пишется), а загруженного из `.bin` — тоже (обратно в массивы не пишется; явный писатель — `write_geometry_files`, PR3a). `desc_system::reduce_to_parent` с таким родителем пишет desc целиком (с `__parent`, если форма читается обратно так же) и пишет WARN, не бросает. `desc_resave` пропускает geometry с диапазонами (строка «skipped» в отчёте, не ошибка).

- **Версия.** `geometry_desc` — версия 2, шаг 1→2 пустой: массивы остаются верными, версия 2 говорит старому движку «здесь могут быть диапазоны» (он откажет, а не прочтёт объект как массив). ## 9. Позже: хранилище по хэшу

Видение владельца для будущего сетевого протокола ресурсов (как Git LFS / DDC): если `.bin` рядом с desc нет, данные ищутся по SHA-256 диапазона в хранилищах — локальном кэше или на сервере.

- Хранилища задаёт только человек в настройках; путь или адрес из данных (desc, ответ декодера) не принимается.
- Найденные байты сверяются с хэшем из desc до использования.
- Правило «имя `.bin` выводится из desc» остаётся: хранилище — запасной источник тех же байт, а не другое имя.
- Сейчас этого нет; от формата требуется только одно — хэш всегда записан в desc (раздел 4).
