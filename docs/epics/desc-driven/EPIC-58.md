### 1.1. Версия на тип desc и цепочка шагов — есть (#86)

### 1.7. Чего не хватает до AC эпика

1. Явной команды «мигрировать проект». Сейчас файл обновляется молча, только если его открыл и сохранил редактор.
2. Плана (dry-run): файлы, типы, версии «с → на», что будет потеряно, какие типы неизвестны.
3. Бэкапа, журнала незавершённой миграции и отката, включая удаление созданных файлов.
4. Отчёта.
5. Шагов уровня проекта: `format_version` манифеста, `engine_version`, а также точек, куда EPIC-57 подключит создание `.resource` и перевод ссылок (Р3, #27).
6. Миграций типов модулей (декларативных для runtime-схем) и честного `unknown_type` — сейчас незарегистрированный тип v1 молча проходит.
7. Политики для Shipping (cook).

## 2. Модель версий

### Варианты

| | Где версия | Плюсы | Минусы |
|---|---|---|---|
| **A. На тип** (как сейчас) | `__version` у каждого типизированного объекта | вложенные объекты разных типов мигрируют независимо; шаг пишет владелец типа (движок или модуль); уже работает | «устарел ли проект» требует скана файлов |
| B. На файл | одна версия в корне файла | быстро проверить файл | у вложенного `camera_desc` своя история; модульный тип внутри движкового файла не версионируется |
| C. На проект | одно число в `project.snkproj` | мгновенная проверка | глобальный счётчик для движка и всех модулей; модуль нельзя развивать без движка |

### Рекомендация: A + отметка в проекте

- **Правда** — версия на тип (A), как в ADR-06. `.resource` версионируется так же: у него свой `__version` и свои шаги (§3.4).
- **Отметка о последней миграции** — `project.snkproj` → `migrated_with: "<engine_version>"` и `applied_steps: [...]`. Это подсказка для быстрого «нечего делать», источник правды — скан. Пишется только в S4.
- **Новые поля манифеста** требуют подъёма `format_version`. Номер не фиксируется в этом документе: следующий свободный на момент PR, согласуется с PR-6 EPIC-57, который тоже поднимает формат манифеста.
- **`format_version` манифеста** — версия формата самого `project.snkproj`; её шаги — шаги уровня проекта (§3.3).

## 3. Реестр миграций

### 3.1. Шаги с контекстом — без поломки ABI

**Ограничение.** `register_migration` inline и пишет прямо в `m_migrations` (`desc_system.h:412`). Каждый модуль держит копию этого кода, поэтому сменить тип `m_migrations` или сделать старую сигнатуру обёрткой нельзя: модуль, собранный раньше, писал бы в член другой раскладки.

**Решение** (ведущая сессия, ревью #748):

- `m_migrations` и старая `register_migration` **не трогаются**.
- Новый член **в конец класса**:
  ```cpp
  struct migration_step {
  	std::string summary;                                          // одна строка: что делает шаг; в план и отчёт
  	std::function<void(json::object&, migration_context&)> fn;
  };
  std::unordered_map<std::string, std::map<int, migration_step>> m_described_migrations;
  ```
- Новая перегрузка **out-of-line**, `SNK_API` в `desc_system.cpp`:
  ```cpp
  void register_migration(std::string_view type, int from_version, std::string_view summary,
  	std::function<void(json::object&, migration_context&)> fn);
  ```
- `current_version` и `migrate_typed` смотрят в оба реестра. Шаг `(type, from)` в обоих реестрах — ошибка регистрации.
- **Module API: минор 3.16** (или следующий свободный на момент PR) — модулю, который регистрирует шаги с контекстом, нужен движок с новым членом. Строка в истории версий в `app_module_entry.h`.
- **Контекст шага:**
  ```cpp
  struct migration_context {
  	std::string_view type;
  	int from_version;
  	std::string_view file;            // для отчёта; пусто при миграции из памяти
  	void warn(std::string message);   // потеря данных или допущение -> отчёт и лог
  };
  ```
- Шаги движка переходят на новую перегрузку (с `summary`); 3→4 prefab/world пишет `ctx.warn` о частичном override камеры.

### 3.2. Типовые шаги не трогают ссылки и id

Типовой шаг видит только JSON объекта, но не проект: ни резолвер, ни базу ассетов. Отсюда правило:

- типовой шаг **не переписывает ссылки** (путь ↔ id) и не создаёт файлы;
- перевод ссылок и создание `.resource` — шаги уровня проекта (§3.3). Создание `.resource` идёт в фазе `pre` (до типовых шагов), перевод ссылок — в фазе `post`; оба видят базу ассетов.

`migration_context` поэтому не даёт доступа к проекту, и это записано в комментарии к нему.

### 3.3. Шаги уровня проекта: две фазы

**Владение** (решение ведущей сессии, стык EPIC-57/58):
- EPIC-58 владеет командой миграции, бэкапом, журналом, отчётом и шагом `format_version` манифеста;
- EPIC-57 только **регистрирует** свои шаги в этом реестре и формат `.resource` не дублирует.

```cpp
enum class project_phase { pre, post };   // pre — до типовых миграций файлов, post — после

struct project_step {
	std::string id;          // "engine.manifest_format", "assets.ids", "assets.refs"; уникален, пишется в отчёт и проект
	project_phase phase;
	std::string summary;
	bool (*needed)(const project_scan&);              // дешёвая проверка по результату скана
	void (*plan)(const project_scan&, migration_plan&);
	void (*apply)(migration_apply_context&);           // пишет, создаёт и удаляет файлы только через контекст
};
```

**Порядок apply:**
1. шаги `pre`;
2. типовые миграции файлов;
3. шаги `post`;
4. проверка.

Внутри фазы шаги идут в порядке регистрации. Шаги движка регистрируются раньше шагов модулей.

**Шаги:**

| id | Фаза | Владелец | Что делает |
|---|---|---|---|
| `engine.manifest_format` | pre | EPIC-58 | поднимает `format_version` манифеста до текущего |
| `assets.ids` | pre | EPIC-57 (S57-9) | создаёт отсутствующие `.resource`, переносит `__guid` из desc в `.resource` |
| `assets.refs` | post | EPIC-57 | переписывает ссылки на форму с id |

**Контекст `migration_apply_context` даёт шагам:**
- запись файла внутри корня проекта, с бэкапом;
- **создание файла** — регистрируется в списке созданных, откат его удаляет;
- удаление ключа или файла — с бэкапом;
- `warn`;
- доступ к базе ассетов: перестроить и прочитать. После шагов `pre` база ассетов перестраивается до типовых миграций и проверки.

**Записи в проекте:** `applied_steps` в `project.snkproj` перечисляет выполненные шаги. Шаг идемпотентен; запись нужна для отчёта и быстрого `needed`.

**Место кода.** `project_system` (`core/core/project`) сейчас не зависит от `desc`. Реестр шагов и `migrate_project` живут в **новом компоненте `core/core/project_migration`** (зависит от `project`, `desc`, `res`); `prj` остаётся без `desc`.

### 3.4. Версия `.resource`

`.resource` — свой версионируемый формат (Р3). Для него действует то же правило, что для desc:
- версия на формат `.resource` (`__version`);
- шаги — в том же реестре, под псевдотипом `resource_meta`;
- скан (§4.1) читает `.resource` и относит их к тем же классам.

Это хук для EPIC-57: формат `.resource` можно менять с первого дня без отдельного механизма.

### 3.5. Типы модулей

- **C++-тип модуля** регистрирует шаги через `registration_scope::migration` **своего слоя**. Выгрузка модуля снимает шаги вместе со слоем.
- **Тип по runtime-схеме** (JSON) получает декларативные шаги (DESC_SCHEMA.md §2.6):
  ```json
  "version": 3,
  "migrations": [{ "from": 1, "rename": { "/hp": "/health" } },
                 { "from": 2, "remove": ["/legacy"], "set_default": { "/armor": 0 } }]
  ```
  Проверка регистрации: `version == 1 + число шагов`, шаги без пропусков. Хелперы `migrations::rename/remove/set_default` доступны и C++-шагам.
- **Неизвестный тип.** Скан берёт `desc_system` **игрового слоя** (типы модуля — в дочернем слое) и проверяет `is_registered(type) || find_schema(type)`.
  - Незарегистрированный тип → класс `unknown_type`, а не «v1, всё в порядке», как сейчас делает `migrate_typed`.
  - Файл с таким объектом **не переписывается**, команда завершается кодом «частично» (§4.3).

## 4. Команда миграции

### 4.1. Ядро

`prj::migrate_project(project, options) → migration_report` в `core/core/project_migration`. Три фазы.

1. **scan.** Обход content roots проекта — только слой проекта, не движка: `*.desc`, `*.resource`, `project.snkproj` и другие файлы версионируемых форматов из §1.5, которые лежат в проекте. Для каждого файла — разбор JSON и пары `(type, version, current)` по всем типизированным объектам. Класс файла:
   - `current`;
   - `outdated`;
   - `newer`;
   - `unknown_type`;
   - `invalid`;
   - для ресурса без sidecar — `missing_resource` (для шага `assets.ids` EPIC-57).
2. **plan (dry-run).** Нужные `project_step` и миграция `outdated` в памяти. В план попадают шаги (`summary`), `ctx.warn`, создаваемые файлы, diff-статистика (полный diff — по флагу). На диск ничего не пишется.
3. **apply.** Только если план не пуст и нет `newer`/`invalid`; `unknown_type` пропускаются и не мешают остальному.
   1. **Журнал:** `report.json` со статусом `in_progress` и полным планом — **до первой записи** (§5).
   2. **Бэкап** изменяемых файлов (§5).
   3. **Наблюдатель файлов** проекта приостанавливается на время записи. Перезагрузка документов и ресурсов — один раз после apply.
   4. **Шаги проекта фазы `pre`** (в том числе `assets.ids` EPIC-57), затем перестройка базы ассетов.
   5. **Типовые миграции файлов**, затем **шаги `post`** (`assets.refs`). Каждый файл пишется атомарно, только внутри корня проекта (`platform::beneath`, TOCTOU-безопасная запись #414).
   6. **Проверка:**
      - каждый записанный файл читается с диска **мимо кэша ресурсов**: `migrate_tree` → `create_instance` → `stamp_tree`;
      - результат сравнивается с записанным после нормализации заголовка. Ключ `__guid` в desc **не считается расхождением**: `stamp_tree` пишет его, пока EPIC-57 не перенесёт id в `.resource` (`assets.ids`), а в проекте без этого шага он остаётся;
      - `.resource` проверяются разбором.
   7. **Отметка в `project.snkproj`:** `engine_version`, `migrated_with`, `applied_steps`.
   8. **Отчёт:** `ok` или `partial`.

   Любая ошибка на шагах 3–7 — **автоматический откат** (§5) и статус `rolled_back`.

### 4.2. Редактор

**Поток при «проект старше».** Проект не смонтирован, а миграции нужны загруженные модули проекта. Варианты:
- (а) кнопка «Мигрировать…» перезапускает редактор с `--migrate`;
- (б) монтировать проект и модули без сцен в текущем процессе.

**Выбор: (а).** Перезапуск — уже существующий путь (`start_editor_on`). Режим `--migrate` без `--headless`:
- монтирует проект и загружает модули;
- **не открывает стартовый уровень и документы**;
- показывает окно плана.

После подтверждения — apply и окно отчёта, затем «Открыть проект» (обычный перезапуск без флага) или «Выйти».

**Прочее:**
- **Меню** `Project → Migrate Project…` — то же через перезапуск с `--migrate`. Нужно, когда обновился модуль игры, а движок — нет.
- **Уведомление при открытии:** если скан (фоновая задача `ds::task_system`) нашёл `outdated` или `unknown_type` — «N файлов в старом формате — Project → Migrate Project».
- **Журнал сбоя:** при открытии проекта, а также в режиме `--migrate`, найден отчёт со статусом `in_progress` → предложить откат (§5).
- **Сохранение одного устаревшего файла** (⚑ решение владельца):
  - (а) как сейчас — файл переходит на текущую версию, плюс уведомление «старые версии редактора его не откроют»;
  - (б) запрет до миграции проекта.

  Рекомендую (а).

### 4.3. CLI

- `editor --headless --project <dir> --migrate [--dry-run] [--report <file>] [--force]`.
- **Коды выхода:**

  | Код | Значение |
  |---|---|
  | 0 | нечего делать или успех |
  | 2 | отказ: ошибка ввода или `invalid` без `--force` |
  | 4 | частично: есть `unknown_type` или `newer` |
  | 5 | откат после ошибки |
- `--dry-run` печатает план и ничего не пишет — для CI проекта игры.
- `--migrate-rollback <id>` — откат по журналу или бэкапу (§5).

### 4.4. MCP (агент)

- `project.migration_plan` — только чтение, план. Политика агента: allow.
- `project.migrate` — apply:
  - **только текущий проект** редактора;
  - **без `--force`** (`invalid` агенту не переписать);
  - записи только внутри корня проекта (`platform::beneath`);
  - политика: ask по умолчанию, в headless — по `--agent-policy`;
  - ответ — отчёт.

## 5. Бэкап, журнал и откат

- **Где:** `<project>/.snk/migrations/<UTC-время>-<engine_version>/`. Не в `.cache/`: его чистят, а бэкап должен пережить очистку.
  - `.snk/` добавляется в `.gitignore` шаблона проекта (`Editor/data/templates/projects/empty/.gitignore`) — в S3.
  - Каталог, не zip (решение 4): легко сравнить и восстановить вручную.
- **Содержимое:**
  - `backup/` — копии изменяемых файлов с относительными путями, включая `project.snkproj`;
  - `report.json` — он же журнал: план, статус, хеши «до» и «после», **список созданных файлов**;
  - `report.md` — короткий текст для человека.
- **Журнал сбоя.** `report.json` со статусом `in_progress` пишется до первой записи и обновляется после каждого файла. Если процесс упал, при следующем открытии проекта (или `--migrate`) статус `in_progress` означает незавершённую миграцию — предложить откат.
- **Откат** (автоматический при ошибке apply, ручной — `--migrate-rollback <id>` или меню «Restore from migration backup…»):
  1. восстановить файлы из `backup/`;
  2. **удалить созданные файлы** (например, новые `.resource`) по списку из отчёта;
  3. перестроить базу ассетов.

  Перед ручным откатом проверяются хеши «после»: если файл изменили после миграции, откат отказывает со списком файлов.
- **Хранение:** бэкапы автоматически не удаляются. `--migrate-prune --keep N` удаляет старые, но никогда — каталог со статусом `in_progress` (S11).
- **Проект под git** (VCS-сервис #561): план предупреждает о незакоммиченных изменениях в файлах, которые будут переписаны.

## 6. Отчёт

`report.json` + `report.md` в каталоге миграции:
- `id`, время, версии движка «до» и «после», версии загруженных модулей;
- `status`: `in_progress | ok | partial | rolled_back | dry_run`;
- по файлам: путь, класс, шаги (`type v1→v4: summary`), предупреждения, хеш «до» и «после»;
- шаги проекта и созданные файлы;
- не мигрированные файлы с причиной (`unknown_type: mod.foo (модуль game не загружен)`, `newer: v5 > v4`, `invalid: …`);
- путь к бэкапу.

Редактор показывает отчёт в окне: предупреждения сверху, ссылки открывают файл.

## 7. Совместимость

### 7.1. Версии и модули

- **Старый редактор, новые файлы** — без изменений: «newer than supported» → отказ загрузки с понятным текстом. Проект новее движка не открывается (код 3).
- **Модули:** типы модуля мигрируют только при загруженном модуле. Типы незагруженного модуля — `unknown_type`, их файлы не трогаются.
- **Hot reload модуля с другой раскладкой схемы** (миграция blob'ов, DESC_SCHEMA.md «Ограничения для host API») — **вне эпика**: это рантайм, не файлы проекта.

### 7.2. Пользовательские данные и Shipping

- **Снимки мира и привязки ввода игрока** (решение S10): `older` → миграция в памяти тем же реестром; `newer` → понятный отказ.
- **Рантайм-цепочка миграций** в игре нужна только для `user://` (сохранения и настройки игрока). Команда проекта их не видит.
- **Shipping (cook):** cook **отказывает** на устаревших данных проекта и называет команду `--migrate`. Это делает данные детерминированными и заставляет мигрировать явно. Флаг `--allow-outdated` мигрирует копию в памяти в собранный пакет, источники не трогает. В собранной игре цепочка шагов для данных проекта не нужна: данные уже текущие.

### 7.3. Документы и инспектор (EPIC-56, #26)

- **Открытие документа старой версии** — миграция в памяти, как сейчас (`desc_adapter_t`).
- **Сохранение** пишет новую версию (§4.2, решение 2).
- **Инспектор** документа показывает бейдж «устарел: vN → vM, Project → Migrate Project». Данные для бейджа: `__version` файла и `current_version` типа.
- **Пикер ссылок EPIC-56** зависит от id ассетов (#27). Миграция `.resource` (§3.3) должна пройти до того, как пикер начнёт писать ссылки с id.
