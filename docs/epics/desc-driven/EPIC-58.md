### 1.7. Чего не хватает до AC эпика

1. Явной команды «мигрировать проект»: сейчас файл обновляется молча, только если его открыл и сохранил редактор.
2. Плана (dry-run): какие файлы, какие типы, с какой версии на какую, что будет потеряно.
3. Бэкапа перед перезаписью и отката.
4. Отчёта: изменённые файлы, предупреждения шагов (потеря данных), файлы, которые не удалось мигрировать.
5. Шагов уровня проекта: манифест `format_version`, `engine_version` после миграции, будущие шаги вроде выдачи GUID (#27).
6. Миграций для типов модулей по схеме (декларативные шаги) и поведения, когда модуль не собран.

## 2. Модель версий

### Варианты

| | Где версия | Плюсы | Минусы |
|---|---|---|---|
| **A. На тип** (как сейчас) | `__version` у каждого типизированного объекта | вложенные объекты разных типов мигрируют независимо; шаг пишет владелец типа (движок или модуль); уже работает | «устарел ли проект» требует скана файлов |
| B. На файл | одна версия в корне файла | быстро проверить файл | у вложенного `camera_desc` своя история; модульный тип внутри движкового файла не версионируется |
| C. На проект | одно число в `project.snkproj` | мгновенная проверка | глобальный счётчик для типов движка и всех модулей — нельзя развивать модуль без движка |

### Рекомендация: A + отметка в проекте

- Правда — версия на тип (A), как в ADR-06.
- Проект хранит **отметку о последней миграции**: `project.snkproj` → `migrated_with: "<engine_version>"`. Это не ограничение, а подсказка: если она совпадает с текущей версией движка и модули не менялись, скан можно пропустить. Решения на ней не строятся, источник правды — скан.
- `format_version` манифеста — отдельная версия формата самого `project.snkproj` (как сейчас), получает шаги в том же реестре (§3.3).

## 3. Реестр миграций

### 3.1. Типовые шаги (есть) + метаданные и предупреждения (новое)

Шаг сейчас — `void(json::object&)`. Добавляется **контекст шага**:

```cpp
struct migration_context {
	std::string_view type;
	int from_version;
	std::string_view file;            // откуда объект, для отчёта (пусто при загрузке из памяти)
	void warn(std::string message);   // потеря данных или допущение -> в отчёт и в лог
};
void register_migration(std::string_view type, int from_version, std::string_view summary,
	std::function<void(json::object&, migration_context&)> fn);
```

- `summary` — одна строка «что делает шаг», она попадает в план и отчёт.
- Старая сигнатура остаётся оберткой (summary пустой, warn → лог), чтобы не ломать модули.
- Шаг 3→4 prefab/world переводит WARN о частичном override камеры на `ctx.warn`.

### 3.2. Типы модулей

- **C++-тип модуля** регистрирует шаги через `registration_scope::migration` своего слоя, как движок. Выгрузка модуля снимает его шаги вместе со слоем.
- **Тип по runtime-схеме** (JSON) получает декларативные шаги, как в DESC_SCHEMA.md §2.6:
  ```json
  "version": 3,
  "migrations": [{ "from": 1, "rename": { "/hp": "/health" } },
                 { "from": 2, "remove": ["/legacy"], "set_default": { "/armor": 0 } }]
  ```
  Хелперы `migrations::rename/remove/set_default` используются и в C++-шагах. Проверка регистрации: `version == 1 + число шагов`, шаги без пропусков.
- **Модуль не собран или не загружен.** Тип в файле неизвестен. Скан относит файл к «не мигрирован: тип X неизвестен (модуль Y не загружен)» и **не переписывает** его. Команда завершается с кодом «частично» (§4.4), а не молча.

### 3.3. Шаги уровня проекта (новое)

Часть миграций не про тип объекта, а про проект целиком:
- `format_version` манифеста;
- выдача `__guid` всем ассетам и `.meta` для png/glb (EPIC-57, #27 PR-6);
- переезд каталогов.

Отдельный маленький реестр:

```cpp
struct project_step {
	std::string id;                 // "engine.manifest.v2", "engine.asset_guids"; уникален, пишется в отчёт и проект
	std::string summary;
	bool (*needed)(const project_scan&);           // нужен ли шаг этому проекту
	void (*plan)(const project_scan&, migration_plan&);
	void (*apply)(migration_apply_context&);        // пишет только через контекст (бэкап, атомарность)
};
```

- Выполненные шаги перечисляются в `project.snkproj` → `applied_steps: [...]`. Шаг идемпотентен, и запись нужна только для отчёта и быстрого `needed`.
- Порядок: шаги проекта, затем типовые миграции файлов. GUID (#27) нужен раньше, чем шаги, которые на него ссылаются.

**⚑ Стык с #27 (PR-6, id ассетов).** Предлагаю выдачу GUID оформить как `project_step` этого реестра, а не отдельной командой. Решение — через ведущую сессию.

## 4. Команда миграции

### 4.1. Ядро (core, без UI)

`prj::migrate_project(project, options) → migration_report` в `core/core/project`. Три фазы:

1. **scan** — обойти content roots проекта (`res://` слоя проекта, не движка): `*.desc`, `project.snkproj`, другие файлы с известным версионируемым форматом (§1.5). Для каждого файла:
   - разобрать JSON;
   - для каждого типизированного объекта получить `(type, version, current)`;
   - отнести файл к одному из классов: `current | outdated | newer | unknown_type | invalid`.
2. **plan (dry-run)** — для `outdated` выполнить миграцию в памяти и собрать:
   - список шагов (`summary`);
   - предупреждения `ctx.warn`;
   - diff-статистику: число изменённых ключей; полный diff по флагу.

   Плюс нужные `project_step`. Ничего не пишется.
3. **apply** — только если план не пуст и нет `newer`/`invalid` (их без `--force` не трогаем):
   1. бэкап (§5);
   2. запись каждого файла атомарно через TOCTOU-безопасную запись vfs (#414);
   3. **проверка**: каждый записанный файл заново загружается штатным путём (`desc_adapter_t`), сериализуется (`stamp_tree`) и сравнивается с записанным;
   4. обновление `project.snkproj`: `engine_version` = текущая, `migrated_with`, `applied_steps`;
   5. отчёт (§6).

   Любая ошибка на шагах 2–4 → **автоматический откат** из бэкапа и отчёт со статусом `rolled_back`.

### 4.2. Редактор

- **Открытие проекта.** Диалог «проект старше движка» (`edt_engine_version_prompt.cpp`) получает третью кнопку «Мигрировать…». Она открывает план (dry-run) в модальном окне: список файлов, шаги, предупреждения (жёлтым — потеря данных), место бэкапа. Подтверждение → apply → окно отчёта.
- **Меню** `Project → Migrate Project…` — тот же план для текущего проекта. Нужен, когда версия движка не менялась, но обновился модуль игры.
- **Уведомление** при открытии, если скан нашёл `outdated` или `unknown_type`: «N файлов в старом формате — Project → Migrate Project». Скан фоновой задачей (`ds::task_system`), чтобы не держать открытие.
- **Сохранение одного устаревшего файла** (статус-кво: файл молча переходит на текущую версию). Варианты:
  - а) оставить как есть, но писать в лог и строку статуса «файл обновлён с vN до vM, старые версии редактора его не откроют»;
  - б) запрещать сохранение устаревшего файла до миграции проекта.

  **Рекомендую (а):** (б) мешает работе, а пофайловое обновление уже есть и безопасно для одного файла. Явная команда нужна для проекта целиком, бэкапа и отчёта.

### 4.3. CLI

- `editor --headless --project <dir> --migrate [--dry-run] [--report <file>] [--force]`.
- Коды выхода:
  - 0 — нечего делать или успех;
  - 4 — частично: есть `unknown_type` или `newer`, остальное мигрировано;
  - 2 — отказ: ошибка ввода или `invalid` без `--force`;
  - 5 — откат после ошибки.
- `--dry-run` печатает план и ничего не пишет; его можно гонять в CI проекта игры.
- Отдельный бинарь не нужен: нужны загруженные модули проекта, а их грузит редактор.

### 4.4. MCP (агент)

- `project.migration_plan` — только чтение, план (dry-run). Политика агента: allow.
- `project.migrate` — apply. Политика: ask по умолчанию, в headless — по `--agent-policy`. Ответ — отчёт целиком.

## 5. Бэкап и откат

- **Где:** `<project>/.cache/migrations/<UTC-время>-<engine_version>/backup/`. Копии только тех файлов, которые будут переписаны, с относительными путями; плюс `project.snkproj`.
  - Вариант — zip. **Рекомендую каталог:** легко сравнить и восстановить вручную, нет зависимости от архиватора.
- `.cache` уже вне контроля версий (`.gitignore` шаблона проекта: `Editor/data/templates/projects/empty/.gitignore:6`).
- **Откат:**
  - автоматический при ошибке apply;
  - вручную — `--migrate-rollback <id>` и пункт меню «Restore from migration backup…». Перед восстановлением проверяется, что файлы не менялись после миграции (хеш из отчёта); иначе — отказ со списком файлов.
- **Хранение:** бэкапы не удаляются автоматически. Отчёт указывает размер, удаление — вручную или командой `--migrate-prune`. Отдельная story, низкий приоритет.
- **Проект под git** (#561, VCS-сервис уже есть): план предупреждает о незакоммиченных изменениях в файлах, которые будут переписаны. Это не запрет, но строка в плане и отчёте.

## 6. Отчёт

`<project>/.cache/migrations/<id>/report.json` и короткий `report.md` (человеку). Содержимое:

- `id`, время, версии движка «до» и «после», версии загруженных модулей;
- `status`: `ok | partial | rolled_back | dry_run`;
- по файлам: путь, класс, шаги (`type v1→v4: summary`), предупреждения, хеш до и после;
- шаги проекта;
- не мигрированные файлы с причиной (`unknown_type: mod.foo (модуль game не загружен)`, `newer: v5 > v4`, `invalid: …`);
- место бэкапа.

Редактор показывает отчёт в окне: предупреждения сверху, ссылки открывают файл в редакторе.

## 7. Совместимость

- **Старый редактор, новые файлы.** Не меняется: «newer than supported» → отказ загрузки с понятным текстом. Проект новее движка не открывается (код 3).
- **Модули.** Миграция типов модуля работает только с загруженным модулем той же или более новой версии. Типы незагруженного модуля попадают в `unknown_type`, файлы не трогаются.
- **Hot reload модуля с другой раскладкой схемы** (DESC_SCHEMA.md «Ограничения для host API»: миграция blob'ов через JSON и шаги) — **вне эпика**. Это рантайм, а не файлы проекта; отдельный issue при работе над host API.
- **Снимки мира и привязки ввода игрока** (§1.5): версия пишется, но не проверяется. Минимум — отказ при `newer` и миграция при `older` тем же реестром (их `__type`) или явный формат-шаг. Пользовательские данные игрока (`user://`) мигрируются при чтении игрой, а не командой проекта: команда проекта их не видит.

## 8. Риски

| Риск | Мера |
|---|---|
| Шаг теряет данные молча | `ctx.warn` обязателен для любого отбрасывания; тест на шаг 3→4 проверяет предупреждение |
| Частичная запись (сбой посреди apply) | бэкап до записи, атомарная запись файла, автооткат |
| Миграция при не собранном модуле портит файлы | `unknown_type` не переписывается; код 4 |
| Большой проект: скан долгий | фоновая задача, отметка `migrated_with` для пропуска |
| Расхождение версий в документации | DESC_SCHEMA.md §1 пишет «prefab/world v3»; при реализации обновить (это не ошибка кода) |
| Конфликт с несохранёнными правками в редакторе | меню миграции требует сохранить или закрыть изменённые документы; после apply документы перезагружаются |
