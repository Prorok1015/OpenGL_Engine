### 1.1. Версия на тип desc и цепочка шагов — есть (#86)

- **Реестр шагов** — `desc_system::register_migration(type, from_version, fn)`, шаг `from → from+1`:

### 1.7. Чего не хватает до AC эпика

1. Явной команды «мигрировать проект». Сейчас файл обновляется молча, только если его открыл и сохранил редактор.
2. Плана (dry-run): файлы, типы, версии «с → на», что будет потеряно, какие типы неизвестны.
3. Бэкапа, журнала незавершённой миграции и отката, включая удаление созданных файлов.
4. Отчёта.
5. Шагов уровня проекта: `format_version` манифеста, `engine_version`, а также точек, куда EPIC-57 подключит создание `.resource` и перевод ссылок (Р3, #27).
6. Миграций типов модулей (декларативных для runtime-схем) и честного `unknown_type` — сейчас незарегистрированный тип v1 молча проходит.
7. Политики для Shipping (cook).

## 2. Модель версий

### Варианты

| | Где версия | Плюсы | Минусы |
|---|---|---|---|
| **A. На тип** (как сейчас) | `__version` у каждого типизированного объекта | вложенные объекты разных типов мигрируют независимо; шаг пишет владелец типа (движок или модуль); уже работает | «устарел ли проект» требует скана файлов |
| B. На файл | одна версия в корне файла | быстро проверить файл | у вложенного `camera_desc` своя история; модульный тип внутри движкового файла не версионируется |
| C. На проект | одно число в `project.snkproj` | мгновенная проверка | глобальный счётчик для движка и всех модулей; модуль нельзя развивать без движка |

### Рекомендация: A + отметка в проекте

- **Правда** — версия на тип (A), как в ADR-06. `.resource` версионируется так же: у него свой `__version` и свои шаги (§3.4).
- **Отметка о последней миграции** — `project.snkproj` → `migrated_with: "<engine_version>"` и `applied_steps: [...]`. Это подсказка для быстрого «нечего делать», источник правды — скан. Пишется только в S4.
- **Новые поля манифеста** требуют подъёма `format_version`. Поднимает его **только EPIC-58 S4 (#754)**; EPIC-57 `format_version` манифеста не трогает. Номер не фиксируется в этом документе: следующий свободный на момент PR S4.
- **`format_version` манифеста** — версия формата самого `project.snkproj`; её шаги — шаги уровня проекта (§3.3).

## 3. Реестр миграций

### 3.1. Шаги с контекстом — без поломки ABI

**Ограничение.** `register_migration` inline и пишет прямо в `m_migrations` (`desc_system.h:412`). Каждый модуль держит копию этого кода, поэтому сменить тип `m_migrations` или сделать старую сигнатуру обёрткой нельзя: модуль, собранный раньше, писал бы в член другой раскладки.

> **С 4.0 (#786) ограничения нет.** Писатели и читатели `desc_system` — `register_migration`, `current_version`, `migrate_tree`, `register_schema`, фабрики и т. д. — вынесены в `desc_system.cpp`. В заголовке не осталось кода, который трогает `m_migrations`, `m_schemas` или `factory_map`; то же у `schema_registry` и `dynamic_desc`, включая конструкторы и деструкторы. Тип реестра теперь можно менять в минорной версии, если не меняется `sizeof(desc_system)`: `scene_layer` держит его по значению (#751).

**Решение** (ведущая сессия, ревью #748):

- `m_migrations` и старая `register_migration` **не трогаются**.
- Новый член **в конец класса**:
  ```cpp
  struct migration_step {
  	std::string summary;                                          // одна строка: что делает шаг; в план и отчёт
  	std::function<void(json::object&, migration_context&)> fn;
  };
  std::unordered_map<std::string, std::map<int, migration_step>> m_described_migrations;
  ```
- Новая перегрузка **out-of-line**, `SNK_API` в `desc_system.cpp`:
  ```cpp
  void register_migration(std::string_view type, int from_version, std::string_view summary,
  	std::function<void(json::object&, migration_context&)> fn);
  ```
- `current_version` и `migrate_typed` смотрят в оба реестра. Шаг `(type, from)` в обоих реестрах — ошибка регистрации.
- **Module API: минор** (следующий свободный на момент PR) — модулю, который регистрирует шаги с контекстом, нужен движок с новым членом. Строка в истории версий в `app_module_entry.h`.
- **Почему не мажор.** Р27 (#568): EPIC-57 сразу поднимает мажор module API (4.0). С мажором S1 мог бы просто сменить тип `m_migrations`. **Выбран минорный вариант:**
  - S1 не ждёт и не блокирует мажор EPIC-57;
  - его можно смержить в любом порядке относительно 4.0;
  - риск — лишний член класса, а не зависимость расписаний.

  Порядок с окном 4.0 (#758): **#751 (S1, минор) → #786 (писатели `desc_system` out-of-line, 4.0) → #787 (слияние двух реестров в один, 4.0, опционально)**.
- **Контекст шага:**
  ```cpp
  struct migration_context {
  	std::string_view type;
  	int from_version;
  	std::string_view file;            // для отчёта; пусто при миграции из памяти
  	void warn(std::string message);   // потеря данных или допущение -> отчёт и лог
  };
  ```
- Шаги движка переходят на новую перегрузку (с `summary`); 3→4 prefab/world пишет `ctx.warn` о частичном override камеры.

### 3.2. Типовые шаги не трогают ссылки и id

Типовой шаг видит только JSON объекта, но не проект: ни резолвер, ни базу ассетов. Отсюда правило:

- типовой шаг **не переписывает ссылки** (путь ↔ id) и не создаёт файлы;
- перевод ссылок и создание `.resource` — шаги уровня проекта (§3.3). Создание `.resource` идёт в фазе `pre` (до типовых шагов), перевод ссылок — в фазе `post`; оба видят базу ассетов.

`migration_context` поэтому не даёт доступа к проекту, и это записано в комментарии к нему.

### 3.3. Шаги уровня проекта: две фазы

**Владение** (решение ведущей сессии, стык EPIC-57/58):
- EPIC-58 владеет командой миграции, бэкапом, журналом, отчётом и шагом `format_version` манифеста;
- EPIC-57 только **регистрирует** свои шаги в этом реестре и формат `.resource` не дублирует.

```cpp
enum class project_phase { pre, post };   // pre — до типовых миграций файлов, post — после

struct project_step {
	std::string id;          // "engine.manifest_format", "assets.ids", "assets.refs"; уникален, пишется в отчёт и проект
	project_phase phase;
	std::string summary;
	bool (*needed)(const project_scan&);              // дешёвая проверка по результату скана
	void (*plan)(const project_scan&, migration_plan&);
	void (*apply)(migration_apply_context&);           // пишет, создаёт и удаляет файлы только через контекст
};
```

**Порядок apply:**
1. шаги `pre`;
2. типовые миграции файлов;
3. шаги `post`;
4. проверка.

Внутри фазы шаги идут в порядке регистрации. Шаги движка регистрируются раньше шагов модулей.

**Шаги:**

| id | Фаза | Владелец | Что делает |
|---|---|---|---|
| `engine.manifest_format` | pre | EPIC-58 | поднимает `format_version` манифеста до текущего |
| `assets.ids` | pre | EPIC-57 (S57-12, #776) | создаёт отсутствующие `.resource`, id берёт из `__guid` desc; снятие `__guid` из desc — `assets.ids_drop_desc_guid` вместе с S57-8 (#772) |
| `assets.refs` | post | EPIC-57 (S57-12, #776) | переписывает ссылки на форму с id; после S57-9 (#773) |

**Контекст `migration_apply_context` даёт шагам:**
- запись файла внутри корня проекта, с бэкапом;
- **создание файла** — регистрируется в списке созданных, откат его удаляет;
- удаление ключа или файла — с бэкапом;
- `warn`;
- доступ к базе ассетов: перестроить и прочитать. После шагов `pre` база ассетов перестраивается до типовых миграций и проверки.

**Записи в проекте:** `applied_steps` в `project.snkproj` перечисляет выполненные шаги. Шаг идемпотентен; запись нужна для отчёта и быстрого `needed`.

**Место кода.** `project_system` (`core/core/project`) сейчас не зависит от `desc`. Реестр шагов и `migrate_project` живут в **новом компоненте `tools/project_migration`** (`snk::project_migration`, STATIC, вне `snk_engine` и SDK; зависит от движка как его потребитель — всё под `core/` собирается как часть `snk_engine`); `prj` остаётся без `desc`.

### 3.4. Версия `.resource`

`.resource` — свой версионируемый формат (Р3). Для него действует то же правило, что для desc:
- версия на формат `.resource` (`__version`);
- шаги — в том же реестре, под псевдотипом `resource_meta`;
- скан (§4.1) читает `.resource` и относит их к тем же классам.

Это хук для EPIC-57: формат `.resource` можно менять с первого дня без отдельного механизма.

### 3.6. Как сделано в S4 (#754)

- **Реестр.** `prj::migration::project_step_registry` — обычный объект, глобального нет. Его передают в `plan_options::project_steps` и `apply_context::project_steps`. Шаги движка добавляет `register_engine_project_steps`.
- **Шаг.** `project_step{ id, phase, summary, needed(const scan_result&), apply(project_step_context&) }`. В плане шаги идут фазами: `pre`, затем `post`; внутри фазы — в порядке регистрации.
- **Контекст шага в S4.** Дает `project.snkproj` в памяти, скан и заметки для отчета. Создание и удаление файлов, база ассетов — S5 (#756).
- **Отличия от §3.3.**
  - Вместо `project_scan` используется `scan_result`.
  - Отдельного `plan()` у шага нет: в план попадают id, фаза и summary шагов, у которых `needed` дает true.
- **`project.snkproj` в apply.** Бэкапится и записывается в журнал как обычный файл. Пишется последним, после `post`: шаги правят его в памяти, затем он получает `migrated_with` этого движка, а в `applied_steps` добавляются выполненные шаги (объединение со старым списком). Не-массив или не-строки в `applied_steps` заменяются — с записью в отчёте. После записи манифест перечитывается и проверяется.
- **`engine_version` и частичная миграция.** `engine_version` этого движка пишет только полная миграция: без файлов, пропущенных из-за незагруженного модуля. Частичная (`partial`) оставляет старую версию, поэтому диалог версии продолжает спрашивать, пока не загружен модуль и миграция не пройдёт целиком.
- **Откат.** Неизменённый манифест восстанавливается из бэкапа целиком. Если его изменили после миграции (более поздняя миграция или правка руками), это не мешает откатить остальные файлы. В манифесте возвращается только штамп этой миграции: `engine_version`, `migrated_with`, `format_version` (если его поднимал `engine.manifest_format`), а из `applied_steps` уходят шаги этой миграции. Остальные ключи остаются как есть.
- **«Нечего делать».** `migration_plan::empty()`: нет файлов, нет нужных шагов и нечего записать в `engine_version` — он не старше движка, или миграция всё равно была бы частичной.
- **Формат манифеста.** `format_version` = 2: добавлены `migrated_with` и `applied_steps`. Парсер знает эти ключи, но в `struct prj::manifest` их нет, ABI модулей не меняется. Формат 1 читается. Повышает формат шаг `engine.manifest_format` (`pre`).
- **Старый редактор и манифест v2.** Редактор до S4 отказывает в открытии проекта: «format 2 is newer than the supported format 1; update the editor». Это ошибка разбора манифеста, а не вопрос о версии: проект не открывается. Проект из командной строки завершает редактор с кодом 2 (`prj::project_error`, `k_exit_project_error`) — и в интерактивном режиме тоже. Так и задумано: новые поля нельзя молча терять.
- **`.resource`.**
  - Сайдкар классифицируется как desc псевдотипа `resource_meta` (`classify_sidecar`): версия сравнивается с `current_version("resource_meta")` слоя. Тип `resource_meta` известен только в корне сайдкара, не во вложенных объектах `.desc`.
  - `settings` принадлежит импортёру: скан туда не смотрит, а миграция (`migrate_sidecar`) не мигрирует и не штампует вложенные `__type`.
  - Сайдкар, который шаги считают текущим, обязан читаться через `res::read_asset_meta`; иначе он `newer`. Проверка после миграции идёт по тому же пути.
  - План отказывает, если шаги `resource_meta` ведут к версии, отличной от той, что читает движок (`res::asset_meta_version`): иначе после миграции база ассетов отвергла бы все сайдкары как `newer_than_engine`. Отсюда правило: первый настоящий шаг `resource_meta` поднимает `res::asset_meta_version` в том же PR.
  - Реальных шагов `resource_meta` в движке нет. Тест регистрирует шаг v1→v2 и ставит `scan_options::resource_meta_version = 2` — это движок, где версия поднята вместе с шагом. Читатель с другой версией подменяется в `tools/project_migration`, без нового экспорта движка.

### 3.7. Как сделано в S5 (#756)

- **Файлы для шагов.** `project_step_context::files` (`project_step_files`): `read`, `exists`, `write`, `create`, `remove`. Шаг сам на диск не пишет.
  - Путь — относительный от корня проекта, внутри content root. Он собирается из частей (`res//a.png` — это `res/a.png`) и сравнивается по ключу `res::asset_name_key`: на Windows регистр букв не различает файлы.
  - Недоступны: `project.snkproj` (его шаг правит через `manifest`); любое имя, которое обход ассетов пропускает (`.snk/`, `.git/`, временные файлы); при content root `.` — `code/` и `build/`, как и в скане. Нарушение — исключение с id шага, вся миграция откатывается.
  - `write` и `remove` перед первым изменением бэкапят файл и добавляют его в журнал (`applied_file`, `written_as = "step:<id>"`). Удалённый файл в журнале — `hash_after = "removed"`; откат, автоматический и ручной, кладёт его обратно из бэкапа.
  - `create` отказывает, если по имени что-то есть, и пишет путь в `created_files` после создания. Откат удаляет такие файлы. `create` на месте файла, который эта миграция удалила, — это изменение того файла, а не новый файл: откат вернёт оригинал из бэкапа.
  - `read` отдаёт то, что эта миграция уже записала (шаг или типовая миграция), иначе — файл с диска. Шаг `pre`, изменивший файл из плана, становится входом типовой миграции: она не затирает правку. Файл из плана, удалённый шагом `pre`, типовая миграция пропускает.
  - `warn(text)` — строка отчёта с id шага.
- **Проверка** после каждой фазы проверяет каждый файл, записанный или созданный шагами. На диске должно быть то, что записано; desc и `.resource` должны быть текущими (`classify_desc`/`classify_sidecar`). Файл плана, который тронул `pre`, проверяется после типовой миграции. Класс desc определяют только `__type` и `__version`: `__guid` в заголовке, добавленный или потерянный, расхождением не считается. Сохранение движком (`desc_adapter_t::serialize`) даёт desc из `res://` новый `__guid`, если его нет; миграция такой `__guid` снимает (#851, §3.8).
- **База ассетов для шагов** — `prj::migration::project_assets` (`pmg_assets.h`): синхронный индекс путь ↔ id по `.resource` на диске. Content roots — слои, как их складывает `res://`: первый корень выше, файл с тем же именем в нижнем не виден (как в редакторе). `id_of`, `paths_of`, `orphans`, `problems`. Строится перед `pre` и после `pre` (до типовых миграций); шаг может вызвать `rebuild()` сам.
  - Отличие от §3.3: не база редактора (`edt::asset_database` асинхронная, с кэшем и наблюдателем, и есть только в редакторе), а свой индекс — миграция идёт и из CLI.
  - Обход и пары `.resource` ↔ файл у индекса и у базы редактора — одни и те же функции движка (`res_asset_walk.h`):
    - `walk_asset_layers`: ссылки и перенаправляющие reparse point не входят, имена — `is_skipped_asset_name`, глубина — `asset_walk_max_depth`, слияние — по `asset_name_key`;
    - `pair_asset_metas`: каждый `.resource` без пары — сирота, в том числе второй sidecar того же файла;
    - `read_asset_meta_file`.
  - Скан миграции берёт оттуда же правило имён.
  - Совпадение с редактором проверяют тесты на одной фикстуре: служебные и скрытые имена, ссылка, два sidecar одного файла, два content root, корень `.` (`TheIndex_ListsWhatTheEditorsAssetDatabaseLists`, `TwoContentRoots_AreStackedAsTheEditorStacksThem`, `TheProjectFolderAsItsContentRoot_IsWalkedAsTheEditorWalksIt`).


### 3.8. Как сделано в S57-12, PR 1 (#776, #851)

- **Регистрация.** `register_asset_project_steps` (`pmg_asset_steps.h`) — шаги EPIC-57; `register_engine_project_steps` — по-прежнему только шаги движка. Команде миграции (S6, S8) — `register_project_steps`: сначала движок, потом ассеты.
- **`assets.ids` (`pre`).**
  - `needed`: в скане есть файл без `.resource` (`scanned_file::has_resource`). Пара `.resource` ↔ файл в скане — по `res::asset_name_key` владельца, как у базы редактора: `a.png.RESOURCE` — это `.resource` файла `a.png`.
  - `apply`: каждому такому файлу — `<file>.resource` (`res::write_asset_meta`, `importer` пустой) через `context.files.create`; откат их удаляет. Файл, у которого индекс уже видит `.resource` (другой регистр, другой корень), пропускается.
  - ID — корневой `__guid` desc, если это валидный id и его не держит ни один файл индекса (сироты тоже) и ни один выданный в этом прогоне; иначе новый. Обе строки повтора — в отчёте: первый файл «ID … from its __guid», следующий «its __guid … is already the ID of …».
  - `__guid` в desc **остаётся** до S57-8 (#772): сейчас его пишут сохранение уровня в редакторе (`level_guid`) и `desc_adapter_t::serialize`, и снятый `__guid` вернулся бы другим. Снимет его шаг `assets.ids_drop_desc_guid` (`post`) вместе с #772.
  - Перекрытый файл нижнего content root тоже получает `.resource`: скан видит каждый корень, иначе шаг был бы нужен всегда.
- **#851.** Типовая миграция, которая сохраняет desc движком, убирает из результата корневой `__guid`, если его не было на входе (вход — текст после шагов `pre`). Был — остаётся тем же. Миграция `__guid` не придумывает.
- **`assets.refs`** — отдельный PR после S57-9 (#773): до этого проверки ссылок требуют строку `res://`.

### 3.5. Типы модулей

- **C++-тип модуля** регистрирует шаги через `registration_scope::migration` **своего слоя**. Выгрузка модуля снимает шаги вместе со слоем.
- **Тип по runtime-схеме** (JSON) получает декларативные шаги (DESC_SCHEMA.md §2.6):
  ```json
  "version": 3,
  "migrations": [{ "from": 1, "rename": { "/hp": "/health" } },
                 { "from": 2, "remove": ["/legacy"], "set_default": { "/armor": 0 } }]
  ```
  Проверка регистрации: `version == 1 + число шагов`, шаги без пропусков. Хелперы `migrations::rename/remove/set_default` доступны и C++-шагам.
- **Неизвестный тип.** Скан берёт `desc_system` **игрового слоя** (типы модуля — в дочернем слое) и проверяет `is_registered(type) || find_schema(type)`.
  - Незарегистрированный тип → класс `unknown_type`, а не «v1, всё в порядке», как сейчас делает `migrate_typed`.
  - Файл с таким объектом **не переписывается**, команда завершается кодом «частично» (§4.3).

## 4. Команда миграции

### 4.1. Ядро

`prj::migrate_project(project, options) → migration_report` в `tools/project_migration`. Три фазы.

1. **scan.** Обход content roots проекта — только слой проекта, не движка: `*.desc`, `*.resource`, `project.snkproj` и другие файлы версионируемых форматов из §1.5, которые лежат в проекте. Для каждого файла — разбор JSON и пары `(type, version, current)` по всем типизированным объектам. Класс файла:
   - `current`;
   - `outdated`;
   - `newer`;
   - `unknown_type`;
   - `invalid`;
   - для ресурса без sidecar — `missing_resource` (для шага `assets.ids` EPIC-57).
2. **plan (dry-run).** Нужные `project_step` и миграция `outdated` в памяти. В план попадают шаги (`summary`), `ctx.warn`, создаваемые файлы, diff-статистика (полный diff — по флагу). На диск ничего не пишется.
3. **apply.** Только если план не пуст, манифест не `newer`/`invalid` и нет файлов `invalid` (с `--force` они пропускаются). Файлы `unknown_type` и `newer` пропускаются и не мешают остальному (статус `partial`, с S6, #757).
   1. **Журнал:** `report.json` со статусом `in_progress` и полным планом — **до первой записи** (§5).
   2. **Бэкап** изменяемых файлов (§5).
   3. **Наблюдатель файлов** проекта приостанавливается на время записи. Перезагрузка документов и ресурсов — один раз после apply.
   4. **Шаги проекта фазы `pre`** (в том числе `assets.ids` EPIC-57), затем перестройка базы ассетов.
   5. **Типовые миграции файлов**, затем **шаги `post`** (`assets.refs`). Каждый файл пишется атомарно, только внутри корня проекта (`platform::beneath`, TOCTOU-безопасная запись #414).
   6. **Проверка:**
      - каждый записанный файл читается с диска **мимо кэша ресурсов**: `migrate_tree` → `create_instance` → `stamp_tree`;
      - результат сравнивается с записанным после нормализации заголовка. Ключ `__guid` в desc **не считается расхождением**: `stamp_tree` пишет его, пока EPIC-57 не перенесёт id в `.resource` (`assets.ids`), а в проекте без этого шага он остаётся;
      - `.resource` проверяются разбором.
   7. **Отметка в `project.snkproj`:** `engine_version`, `migrated_with`, `applied_steps`.
   8. **Отчёт:** `ok` или `partial`.

   Любая ошибка на шагах 3–7 — **автоматический откат** (§5) и статус `rolled_back`.

### 4.2. Редактор

**Поток при «проект старше».** Проект не смонтирован, а миграции нужны загруженные модули проекта. Варианты:
- (а) кнопка «Мигрировать…» перезапускает редактор с `--migrate`;
- (б) монтировать проект и модули без сцен в текущем процессе.

**Выбор: (а).** Перезапуск — уже существующий путь (`start_editor_on`). Режим `--migrate` без `--headless`:
- монтирует проект и загружает модули;
- **не открывает стартовый уровень и документы**;
- показывает окно плана.

После подтверждения — apply и окно отчёта, затем «Открыть проект» (обычный перезапуск без флага) или «Выйти».

**Прочее:**
- **Меню** `Project → Migrate Project…` — то же через перезапуск с `--migrate`. Нужно, когда обновился модуль игры, а движок — нет.
- **Уведомление при открытии:** если скан (фоновая задача `ds::task_system`) нашёл `outdated` или `unknown_type` — «N файлов в старом формате — Project → Migrate Project».
- **Журнал сбоя:** при открытии проекта, а также в режиме `--migrate`, найден отчёт со статусом `in_progress` → предложить откат (§5).
- **Сохранение одного устаревшего файла** — вариант (а), **решение владельца Р26** (#568): как сейчас, файл переходит на текущую версию. Плюс предупреждение в лог и строку статуса: «файл обновлён с vN до vM, старые версии редактора его не откроют». Запрета до миграции проекта нет.

### 4.3. CLI

- `editor --headless --project <dir> --migrate [--dry-run] [--report <file>] [--force]`.
- **Коды выхода:**

  | Код | Значение |
  |---|---|
  | 0 | нечего делать или успех; откат `--migrate-rollback` выполнен |
  | 1 | только `--dry-run`: нужна миграция (план не пуст) |
  | 2 | отказ: ошибка ввода, `invalid` без `--force`, манифест `newer`/`invalid`, в проекте незавершённая миграция, откат отказал (файлы менялись после миграции), игровой модуль проекта не загружен (нет файла или отказ), `--report` не записан после прошедшей миграции |
  | 3 | проект для более нового движка (как при открытии) |
  | 4 | частично: остались `unknown_type`, `newer` или `invalid`, пропущенные по `--force` |
  | 5 | откат после ошибки |
  | 6 | откат после ошибки не завершился (`rollback_failed`): нужен `--migrate-rollback <id>` |
  | -1 (255 в POSIX) | непредвиденная ошибка (исключение) или запуск, который не дошёл до команды (`--help`) |
- `--dry-run` печатает план и ничего не пишет — для CI проекта игры.
- `--migrate-rollback <id>` — откат по журналу или бэкапу (§5).
- **Как сделано (S6, #757).**
  - Флаги разбирает общий `cfg_api.cpp`; хост `game` их отвергает (код 2).
  - Без `--headless` или вместе с `--mcp-stdio`/`--game` — код 2.
  - `--migrate` открывает проект более старого движка без вопроса.
  - В режиме миграции `main` редактора не добавляет `editor_module` и не грузит editor-модули: работают core, engine и игровой модуль проекта (его типы решают `unknown_type`/`outdated`). Проект монтируется только для чтения (как у собранной игры: `user://` и `memory://` вне проекта), лог-файл в проект не пишется, наблюдение за файлами и hot reload выключены. Рабочие копии игровых модулей у такого проекта кладутся в scratch-папку запуска, а не в `.cache/modules`, и уборка копий по проекту не ходит.
  - Логика — `prj::migration::run_migrate`/`run_migrate_rollback` (`pmg_command.h`), коды — `k_exit_*`.
  - `--dry-run` вызывает только `scan_project` и `plan_migration`, которые ничего не пишут. `--report <file>` внутри корня проекта — отказ (2).
  - `--force` = `plan_options::force`: `invalid`-файлы не мигрируются и попадают в отчёт. `newer`-файлы с S6 не повод для отказа: они остаются как есть, статус `partial` (раньше apply отказывал).
  - `desc_resave` следует правилу #851, что и миграция (`desc::keep_root_guid`, `desc_json_ops.h`): корневой `__guid` остаётся, как в файле, новый не придумывается. Поэтому `desc_resave --check` на результате миграции чист.
  - Незавершённая миграция (журнал `in_progress` или `rollback_failed`) — отказ (2) с подсказкой `--migrate-rollback <id>`, и для `--dry-run` тоже.

### 4.4. MCP (агент)

- `project.migration_plan` — только чтение, план. Политика агента: allow.
- `project.migrate` — apply:
  - **только текущий проект** редактора;
  - **без `--force`** (`invalid` агенту не переписать);
  - записи только внутри корня проекта (`platform::beneath`);
  - политика: ask по умолчанию, в headless — по `--agent-policy`;
  - ответ — отчёт.
- **Как сделано (S7, #759).**
  - Команды — `Editor/code/editor_system/controller/edt_migration_commands.{h,cpp}` (`register_migration_commands`), зависимости от редактора — функции `migration_deps`, поэтому логика проверяется без всего редактора (`tests/edt_migration_commands_tests.cpp`). Редактор линкует `snk::project_migration`.
  - `project.migration_plan {}` — категория `read`, только `scan_project` + `plan_migration` с `register_project_steps` и описаниями игрового слоя, ничего не пишет. Ответ `{code, plan, text}`: `code` — код CLI `--dry-run` (0, 1, 2 при отказе плана или незавершённой миграции, 4 когда остались только файлы, которые не мигрируют), `plan` — файлы с шагами и предупреждениями, шаги проекта, состояние `project.snkproj`, что не мигрируется, `refused`/`unfinished`; `text` — `plan_text`.
  - `project.migrate {}` — новая категория `project_migrate` (по умолчанию `ask`) и `risk = confirm`: «до конца сессии» её не покрывает, человек одобряет каждый план. Аргументов нет, `force` не принимается.
  - Политика (решение лида): файл политики проекта приходит из репозитория, поэтому ни он, ни личный слой не разрешают `project_migrate`: `allow` для категории или для `project.migrate` читается как `ask` (одно место — `policy_layer::resolve`, `needs_consent_each_call`). Разрешает только ответ человека или, в headless, `--agent-policy`, заданный при старте. Реестр описывает (`describe`) и такой разрешённый без вопроса вызов команды с `risk`, поэтому план записан на любом пути; запись живёт не дольше тикета (`confirmation_lifetime`), забирается запуском и заменяется следующим вопросом.
  - Вопрос человеку (`describe`) строит план: проект и корень, число файлов и шагов, движок `<было> -> this engine`, что не мигрируется, отказ, если он будет, и что открытые документы закроются, а уровень закроется и откроется с диска. Он же запоминает отпечаток плана для вызывающего (вид + сессия; до 32 записей): FNV-1a 64 по JSON плана (шаги и предупреждения каждого файла, шаги проекта, пропущенное, манифест), `project.snkproj`, пути, классу и байтам каждого файла скана. Ссылки не читаются, читаются только обычные файлы до 64 МиБ кусками; остальное — по виду, размеру и времени (ссылка на /dev/zero или FIFO не вешают редактор). Вызов агента без отпечатка — `denied`.
  - Проверки при вызове: нет проекта — `no_project`; Play, загрузка уровня или ассета, стартовый уровень, сборка, ожидающая перезагрузка модуля, импорт модели, другая миграция — `busy`; незакоммиченная правка в инспекторе или перетаскивание гизмо и несохранённый документ — `needs_input`; ещё `busy` — git-операция записи (`running_writes`) и открытый диалог экспорта ассета.
  - Миграция идёт на месте и на главном потоке (ей нужны desc_system, resource_system и документы); job на `io` только ждёт promise. Кадр 1 — модальное окно «Migrating project...». Кадр 2 — проверки ещё раз и отпечаток ещё раз: проект изменился после вопроса — `error.code = denied`, ничего не записано. Отказ плана или незавершённая миграция — `{code: 2, refused}`, ничего не закрывается. Иначе закрываются все документы, кроме сцены (редактор префаба, data-документы через их хост, документы модулей и расширений через `document_manager::close`), уровень отпускается (`detach_from_game_layer`), `apply_migration` (наблюдение за уровнем на паузе), `signal_changed` для каждого записанного и созданного файла, пересборка базы ассетов, уровень подключается и грузится с диска заново.
  - Ответ job — `{code, status, id, report, text, level{tag, reopened, reason?}}`: код и `report.json` те же, что у CLI (`exit_code_of`, `report_to_json` стали публичными в `pmg_command.h`/`pmg_apply.h`). Уровень, который не загрузился заново, — `reopened: false` с причиной; уровень тогда остаётся закрытым, это принято. Пустой план ничего не пишет и уровень не трогает. Исключение из `apply_migration` — код 6 (`rollback_failed`: состояние проекта неизвестно), с подсказкой `--migrate-rollback <id>`, если журнал остался. Job, отменённый до кадра 2, ничего не пишет; редактор, закрытый раньше конца, даёт `error.code = failed`.
  - Записи вне корня: аргумента пути нет; содержимое, которое ссылкой уходит из проекта (`res` — ссылка наружу), отказывает план (`invalid`) ещё до записи.

## 5. Бэкап, журнал и откат

- **Где:** `<project>/.snk/migrations/<UTC-время>-<engine_version>/`. Не в `.cache/`: его чистят, а бэкап должен пережить очистку.
  - `.snk/` добавляется в `.gitignore` шаблона проекта (`Editor/data/templates/projects/empty/.gitignore`) — в S3.
  - Каталог, не zip (решение 4): легко сравнить и восстановить вручную.
- **Содержимое:**
  - `backup/` — копии изменяемых файлов с относительными путями, включая `project.snkproj`;
  - `report.json` — он же журнал: план, статус, хеши «до» и «после», **список созданных файлов**;
  - `report.md` — короткий текст для человека.
- **Журнал сбоя.** `report.json` со статусом `in_progress` пишется до первой записи и обновляется после каждого файла. Если процесс упал, при следующем открытии проекта (или `--migrate`) статус `in_progress` означает незавершённую миграцию — предложить откат.
- **Откат** (автоматический при ошибке apply, ручной — `--migrate-rollback <id>` или меню «Restore from migration backup…»):
  1. восстановить файлы из `backup/`;
  2. **удалить созданные файлы** (например, новые `.resource`) по списку из отчёта;
  3. перестроить базу ассетов.

  Перед ручным откатом проверяются хеши «после»: если файл изменили после миграции, откат отказывает со списком файлов.
- **Хранение:** бэкапы автоматически не удаляются. `--migrate-prune --keep N` удаляет старые, но никогда — каталог со статусом `in_progress` (S11).
- **Проект под git** (VCS-сервис #561): план предупреждает о незакоммиченных изменениях в файлах, которые будут переписаны.

## 6. Отчёт

`report.json` + `report.md` в каталоге миграции:
- `id`, время, версии движка «до» и «после», версии загруженных модулей;
- `status`: `in_progress | ok | partial | rolled_back | dry_run`;
- по файлам: путь, класс, шаги (`type v1→v4: summary`), предупреждения, хеш «до» и «после»;
- шаги проекта и созданные файлы;
- не мигрированные файлы с причиной (`unknown_type: mod.foo (модуль game не загружен)`, `newer: v5 > v4`, `invalid: …`);
- путь к бэкапу.

Редактор показывает отчёт в окне: предупреждения сверху, ссылки открывают файл.

## 7. Совместимость

### 7.1. Версии и модули

- **Старый редактор, новые файлы** — без изменений: «newer than supported» → отказ загрузки с понятным текстом. Проект новее движка не открывается (код 3).
- **Модули:** типы модуля мигрируют только при загруженном модуле. Типы незагруженного модуля — `unknown_type`, их файлы не трогаются.
- **Hot reload модуля с другой раскладкой схемы** (миграция blob'ов, DESC_SCHEMA.md «Ограничения для host API») — **вне эпика**: это рантайм, не файлы проекта.

### 7.2. Пользовательские данные и Shipping

- **Снимки мира и привязки ввода игрока** (решение S10): `older` → миграция в памяти тем же реестром; `newer` → понятный отказ.
- **Рантайм-цепочка миграций** в игре нужна только для `user://` (сохранения и настройки игрока). Команда проекта их не видит.
- **Shipping (cook):** cook **отказывает** на устаревших данных проекта и называет команду `--migrate`. Это делает данные детерминированными и заставляет мигрировать явно. Флаг `--allow-outdated` мигрирует копию в памяти в собранный пакет, источники не трогает. В собранной игре цепочка шагов для данных проекта не нужна: данные уже текущие.

### 7.3. Документы и инспектор (EPIC-56, #26)

- **Открытие документа старой версии** — миграция в памяти, как сейчас (`desc_adapter_t`).
- **Сохранение** пишет новую версию, с предупреждением (§4.2, Р26).
- **Инспектор** документа показывает бейдж «устарел: vN → vM, Project → Migrate Project». Данные для бейджа: `__version` файла и `current_version` типа.
- **Пикер ссылок EPIC-56** зависит от id ассетов (#27). Миграция `.resource` (§3.3) должна пройти до того, как пикер начнёт писать ссылки с id.
