# EPIC-62: Импорт ассетов с настройками (`.resource`: importer + settings)

**Theme:** editor
**Status:** in_progress (#1193 — импорт PNG/JPEG; дальше #1194, #1195, #1371)
**Issue:** #34
**Stories:** #1193, #1194, #1195, #1371

---

## 1. Зачем

Сейчас картинка попадает в проект только как побочный продукт
импорта модели или копированием руками, а параметры текстуры
(wrap, фильтр, мипы) правятся в `*.txm.desc` вручную. Импорт с настройками
записывает «рецепт» импорта рядом с исходником, чтобы повторный
импорт (#1194) дал тот же результат с тем же ID.

## 2. `.resource`: importer и settings

- Владелец настроек — `.resource` **исходника** (`rock.png.resource`), а не выход
  импорта. Формат `.resource` не меняется (EPIC-57, 4.2): `importer` — строка,
  `settings` — объект.
- Движок `importer`/`settings` не читает никогда: это рецепт редактора.
  Движок читает только выход (`rock.png.txm.desc`).
- `.resource` пишется первым, новым файлом (никогда поверх), в
  каноническом виде `res::write_asset_meta`; база ассетов, увидев картинку,
  берёт его guid и своего не создаёт.

## 3. `texture`, версия 1 (#1193)

Импорт `<abs>/rock.png` в папку `F` (png, jpg, jpeg) пишет в верхний слой проекта,
по порядку:

1. `res://F/rock.png.resource` — новый guid, `importer: "texture"`, `settings`, `flags: []`;
2. `res://F/rock.png.txm.desc.resource` — свой новый guid у desc текстуры, `importer: ""`,
   `settings: {}`, `flags: []`: desc — выход импорта, а не рецепт, но ID у него свой с
   самого начала (база ассетов не придумывает его сама);
3. `res://F/rock.png` — байты исходника без перекодирования;
4. `res://F/rock.png.txm.desc` — `texture_2d_desc`: `__parent` = `res://base_texture.desc`,
   `name`, `data` = `res://F/rock.png`, `header`.

Каждая запись — создание нового файла без следования по
ссылкам; при сбое уже записанное удаляется в обратном порядке.
Все четыре имени проверяются `res::name_taken` во всех слоях (при плане и в задаче).
Результат задачи: `{image, resource, texture, texture_resource, guid, texture_guid}`.
Нет открытого проекта — отказ `disabled` («no project is open»), в слой движка ничего не
пишется. Тексты ошибок, уходящие агенту, не содержат абсолютных путей машины: папка
слоя читается как `res://`, исходник — как имя файла.

| Ключ | Тип | По умолчанию | Значения |
|---|---|---|---|
| `version` | int | 1 | только 1 |
| `wrap` | string | `clamp_to_edge` | `clamp_to_edge`, `repeat`, `repeat_mirror`, `clamp_to_border` |
| `filter` | string | `nearest` | `nearest`, `linear` |
| `mips` | bool | `false` | |

Разбор строгий: неизвестный ключ, неверный тип или значение —
отказ с именем ключа; отсутствующий ключ — значение по
умолчанию (как в `base_texture.desc`).

Отображение в `header`:

- `wrap` = `wrap`; `mag` = `filter`;
- `mips: false` → `min` = `filter`, `data.mip_levels` = 1;
- `mips: true` → `min` = `linear_mipmap_nearest` (единственная строка с мипами в
  словаре `texture_desc`, загрузчик даёт GL_LINEAR_MIPMAP_LINEAR; так же и при
  `filter: nearest`), `data.mip_levels` = 32 (загрузчик ограничивает
  полной цепочкой и строит уровни);
- `type`, `usage`, `extent`, `format` не пишутся: загрузчик берёт их из картинки
  (#926).

Кто вызывает: команда `file.import_image {path, folder?, name?, settings?}` (агент —
только с подтверждением человека, `risk = confirm`, задача `{job}`) и пункт
«Import Image...» в контекстном меню папки Asset Browser (выбор файла, затем
окно с wrap / filter / mips и итоговыми именами).

### Источник агента (ревью безопасности #1193)

- **Разрешённые корни источника — только локальные несъёмные и съёмные тома.** Проверка
  `agent_source_path_problem` текстовая, к самому пути не обращается: отказ для двух
  ведущих разделителей (UNC, `\\?\`, `\\.\`), `\??\`, компонентов `.`/`..`; на Windows —
  путь без буквы диска `X:\` и диск, у которого `GetDriveTypeW("X:\")` (только таблица
  дисков, без сети) не DRIVE_FIXED/DRIVE_REMOVABLE; на POSIX — путь под `/proc` и путь,
  чья самая длинная точка монтирования из `/proc/self/mounts` (по границам компонентов)
  имеет тип вне белого списка локальных файловых систем (ext2/ext3/ext4, xfs, btrfs, zfs,
  f2fs, vfat, exfat, ntfs, ntfs3, fuseblk, tmpfs, overlay; #1380), либо таблица не
  читается. Сетевые, automount, FUSE (`fuse.sshfs`...), системные (proc, sysfs...) и
  неизвестные типы отклоняются.
- До одобрения человеком диск источника агента не трогается: вопрос (`describe`)
  строится из текста запроса (путь как дан, без размера) и проверки занятости имён в
  слоях проекта. Обращение к файлу (stat, canonical, размер, время, file id) — только в
  `start` после одобрения; правило применяется ещё раз там, к разрешённому пути и в
  задаче перед чтением.
- Вызов человека (`ui`) правилом не ограничен: в системном диалоге можно выбрать файл
  на общей папке.
- Не-человеческий вызов идёт только с планом, запомненным `describe` для этого самого
  вызова. Реестр команд отдаёт вызов с `ask` только после одобренного тикета, а при
  `allow` вызывает `describe` перед запуском (`describe_before_allowed_invoke`).
- План привязан к тикету (#1380): `describe` при `ask` получает id вопроса в
  `call.confirmation`, при `allow` — пустую строку; `start` сравнивает его с
  `confirmation` вызова. Одобренный вызов несёт тикет своего вопроса; вызов с другим
  тикетом или без него после вопроса, который человек отклонил, отказан.
- Ошибки, которые читает агент, не содержат абсолютных путей: `without_paths` заменяет
  слои на `res://`, источник — на имя файла, папку источника — на `<source folder>`.
- **Одно правило на оба импорта** (#1380): `agent_source_path_problem`, порты томов
  (`source_volume_ports`, `system_drive_type`/`system_mount_table`) и `without_paths`
  лежат в `Editor/code/editor_system/import/edt_agent_source_rule.{h,cpp}`; ими
  пользуются импорт картинки (`file.import_image`) и импорт модели агентом
  (`file.import_model`). У модели так же: `describe` агента строится из текста
  (`text_plan`), `start` требует запомненный план, правило применяется к пути как дан,
  к разрешённому пути и в задаче перед чтением; каждый побочный файл (текстуры, `.bin`,
  `.mtl` из списка сканирования) проходит то же правило в первой задаче (после
  сканирования), во втором вызове (`describe`, `start`) и в его задаче, до того как
  импорт его прочтёт.
- **Ссылки и облачные файлы (#1408, закрыто).** Для агента путь источника проходит
  `agent_source_links_problem` (общий файл правила): префиксы пути от корня вниз
  открываются как они есть (`platform::beneath::link_entry_at`, lstat / FileAttributeTagInfo
  с OPEN_REPARSE_POINT) и отказ ставится на первом, что не обычная папка или файл:
  symlink, junction, точка монтирования, любая другая reparse-точка, запись, которую
  нельзя прочесть. Ниже отказанного ничего не трогается. Проверка стоит в `resolve`
  обоих импортов сразу после текстового правила и до `symlink_status`/`canonical`, и в
  задаче перед чтением источника (`identity_problem`). На Windows по атрибутам
  (`GetFileAttributesW`, ссылка не разыменовывается, плейсхолдер не скачивается)
  отказ получает файл, открытие которого пошло бы в сеть: `RECALL_ON_DATA_ACCESS`,
  `RECALL_ON_OPEN`, `OFFLINE` («сделайте файл доступным офлайн»); файл OneDrive,
  лежащий на диске, проходит. Побочные файлы: `import_source::may_read` → конструктор
  `model_file_access` на диске; `resolve` до `path_within_dir_from` строит лексический
  путь (`папка модели / имя`, нормализованный) и спрашивает правило; импорт агента
  ставит `agent_side_file_problem` (текстовое правило + обход от папки модели вниз),
  непустой ответ — отказ по правилу (`refusal_kind::rule`): файл не stat-ится, не
  читается и не хешируется; побочный файл для ребёнка-декодера тогда «отсутствует»,
  текстура проваливает сканирование. Импорт человека правила не получает — без изменений.
- **Читается проверенный дескриптор (#1412, закрыто).** Источник и побочные файлы агента
  читает `read_agent_file` (общий файл правила): `platform::beneath::read_beneath` с
  `read_limits{same_device, refuse_recall}` от корня тома (`source_volume_ports::read_root`:
  диск `C:\` на Windows, самая длинная точка монтирования настоящей таблицы на POSIX).
  Каждая папка открывается от предыдущей без следования ссылке (POSIX `openat` +
  `O_NOFOLLOW`, Windows — цепочка хендлов, junction отказан), ни одна не на другом
  устройстве (`st_dev` / серийный номер тома: точка монтирования по пути — отказ), файл
  открывается сам (`O_NOFOLLOW` / `FILE_OPEN_REPARSE_POINT`), его атрибуты смотрятся по
  хендлу до первого байта, байты читаются из того же хендла, путь после этого не
  открывается. Штамп хендла (размер, id файла) сверяется с показанным файлом
  (`stamp_is_file`). `openat2` не нужен: обход по компонентам уже есть и работает на любом
  ядре, проверка устройства закрывает то, что дал бы `RESOLVE_NO_XDEV`. Побочные файлы:
  `import_source::read_file` → `model_file_access` читает ими вместо `read_beneath` от папки
  модели и не открывает путь заново (прежняя сверка по `file_id_of` открывала его на
  Windows). Новые поля — отдельная структура и перегрузка `read_beneath`, `read_request`
  не меняется (`docs/abi/changes/1412.md`).
- **`RECALL_ON_OPEN` до открытия (#1412).** Атрибуты записи на пути берутся из списка её
  папки (`FindFirstFileExW(FindExInfoBasic)` в `system_file_attributes`; в чтении —
  перечисление удерживаемой папки по хендлу) до того, как запись открывается: запись
  проецируемой ФС (VFS for Git) идёт к провайдеру при открытии, а не при перечислении.
- Ещё по ревью #1408: имя побочного файла агента с `..` отказано правилом (иначе
  `link/../x` шёл бы по ссылке до `..`), путь разрешается из одобренного кандидата; на
  Windows компонент, оканчивающийся пробелом или точкой, отказан; `without_paths` не
  разрешает источник и его папку на диске (только корни). Одиночная `.` (glTF
  `"./tex.png"`) — не компонент (#1412): мимо ссылки она не ведёт, `lexically_normal` её
  убирает.

## 7. Известные ограничения

- Сбой процесса между записями может оставить `.resource` (картинки или desc) без
  своего файла; такой `.resource` держит имя (`res::name_taken`, `needs_input`), пока
  человек его не удалит.
- Импорт картинки пока не берёт блокировку импорта модели / миграции (follow-up issue
  заведёт исполнитель ведущего).
- Правило источника проверяет текст: промежуточная ссылка внутри пути на сетевой том
  видна только после одобрения (повторная проверка разрешённого пути), а `stat` при
  разрешении уже идёт по ней.
- Корень чтения на POSIX (точка монтирования) открывается по пути; папки над ним — это
  таблица монтирования, подменить их может только администратор. Подтом btrfs без своей
  строки в таблице монтирования — другое `st_dev`: файл в нём агенту не читается.
- На ReFS id файла 128-битный, а штамп хендла хранит 64 бита: там с показанным файлом
  сверяются только том и размер.
- На POSIX облачные ФС (FUSE) отсекает список типов томов; отдельной проверки атрибутов
  там нет.
