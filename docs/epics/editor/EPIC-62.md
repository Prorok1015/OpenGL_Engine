# EPIC-62: Импорт ассетов с настройками (`.resource`: importer + settings)

**Theme:** editor
**Status:** in_progress (#1193 — импорт PNG/JPEG; дальше #1194, #1195, #1371)
**Issue:** #34
**Stories:** #1193, #1194, #1195, #1371

---

## 1. Зачем

Сейчас картинка попадает в проект только как побочный продукт
импорта модели или копированием руками, а параметры текстуры
(wrap, фильтр, мипы) правятся в `*.txm.desc` вручную. Импорт с настройками
записывает «рецепт» импорта рядом с исходником, чтобы повторный
импорт (#1194) дал тот же результат с тем же ID.

## 2. `.resource`: importer и settings

- Владелец настроек — `.resource` **исходника** (`rock.png.resource`), а не выход
  импорта. Формат `.resource` не меняется (EPIC-57, 4.2): `importer` — строка,
  `settings` — объект.
- Движок `importer`/`settings` не читает никогда: это рецепт редактора.
  Движок читает только выход (`rock.png.txm.desc`).
- `.resource` пишется первым, новым файлом (никогда поверх), в
  каноническом виде `res::write_asset_meta`; база ассетов, увидев картинку,
  берёт его guid и своего не создаёт.

## 3. `texture`, версия 1 (#1193)

Импорт `<abs>/rock.png` в папку `F` (png, jpg, jpeg) пишет в верхний слой проекта,
по порядку:

1. `res://F/rock.png.resource` — новый guid, `importer: "texture"`, `settings`, `flags: []`;
2. `res://F/rock.png.txm.desc.resource` — свой новый guid у desc текстуры, `importer: ""`,
   `settings: {}`, `flags: []`: desc — выход импорта, а не рецепт, но ID у него свой с
   самого начала (база ассетов не придумывает его сама);
3. `res://F/rock.png` — байты исходника без перекодирования;
4. `res://F/rock.png.txm.desc` — `texture_2d_desc`: `__parent` = `res://base_texture.desc`,
   `name`, `data` = `res://F/rock.png`, `header`.

Каждая запись — создание нового файла без следования по
ссылкам; при сбое уже записанное удаляется в обратном порядке.
Все четыре имени проверяются `res::name_taken` во всех слоях (при плане и в задаче).
Результат задачи: `{image, resource, texture, texture_resource, guid, texture_guid}`.
Нет открытого проекта — отказ `disabled` («no project is open»), в слой движка ничего не
пишется. Тексты ошибок, уходящие агенту, не содержат абсолютных путей машины: папка
слоя читается как `res://`, исходник — как имя файла.

| Ключ | Тип | По умолчанию | Значения |
|---|---|---|---|
| `version` | int | 1 | только 1 |
| `wrap` | string | `clamp_to_edge` | `clamp_to_edge`, `repeat`, `repeat_mirror`, `clamp_to_border` |
| `filter` | string | `nearest` | `nearest`, `linear` |
| `mips` | bool | `false` | |

Разбор строгий: неизвестный ключ, неверный тип или значение —
отказ с именем ключа; отсутствующий ключ — значение по
умолчанию (как в `base_texture.desc`).

Отображение в `header`:

- `wrap` = `wrap`; `mag` = `filter`;
- `mips: false` → `min` = `filter`, `data.mip_levels` = 1;
- `mips: true` → `min` = `linear_mipmap_nearest` (единственная строка с мипами в
  словаре `texture_desc`, загрузчик даёт GL_LINEAR_MIPMAP_LINEAR; так же и при
  `filter: nearest`), `data.mip_levels` = 32 (загрузчик ограничивает
  полной цепочкой и строит уровни);
- `type`, `usage`, `extent`, `format` не пишутся: загрузчик берёт их из картинки
  (#926).

Кто вызывает: команда `file.import_image {path, folder?, name?, settings?}` (агент —
только с подтверждением человека, `risk = confirm`, задача `{job}`) и пункт
«Import Image...» в контекстном меню папки Asset Browser (выбор файла, затем
окно с wrap / filter / mips и итоговыми именами).

### Источник агента (ревью безопасности #1193)

- **Разрешённые корни источника — только локальные несъёмные и съёмные тома.** Проверка
  `agent_source_path_problem` текстовая, к самому пути не обращается: отказ для двух
  ведущих разделителей (UNC, `\\?\`, `\\.\`), `\??\`, компонентов `.`/`..`; на Windows —
  путь без буквы диска `X:\` и диск, у которого `GetDriveTypeW("X:\")` (только таблица
  дисков, без сети) не DRIVE_FIXED/DRIVE_REMOVABLE; на POSIX — путь под `/proc` и путь,
  чья самая длинная точка монтирования из `/proc/self/mounts` (по границам компонентов)
  имеет тип вне белого списка локальных файловых систем (ext2/ext3/ext4, xfs, btrfs, zfs,
  f2fs, vfat, exfat, ntfs, ntfs3, fuseblk, tmpfs, overlay; #1380), либо таблица не
  читается. Сетевые, automount, FUSE (`fuse.sshfs`...), системные (proc, sysfs...) и
  неизвестные типы отклоняются.
- До одобрения человеком диск источника агента не трогается: вопрос (`describe`)
  строится из текста запроса (путь как дан, без размера) и проверки занятости имён в
  слоях проекта. Обращение к файлу (stat, canonical, размер, время, file id) — только в
  `start` после одобрения; правило применяется ещё раз там, к разрешённому пути и в
  задаче перед чтением.
- Вызов человека (`ui`) правилом не ограничен: в системном диалоге можно выбрать файл
  на общей папке.
- Не-человеческий вызов идёт только с планом, запомненным `describe` для этого самого
  вызова. Реестр команд отдаёт вызов с `ask` только после одобренного тикета, а при
  `allow` вызывает `describe` перед запуском (`describe_before_allowed_invoke`).
- План привязан к тикету (#1380): `describe` при `ask` получает id вопроса в
  `call.confirmation`, при `allow` — пустую строку; `start` сравнивает его с
  `confirmation` вызова. Одобренный вызов несёт тикет своего вопроса; вызов с другим
  тикетом или без него после вопроса, который человек отклонил, отказан.
- Ошибки, которые читает агент, не содержат абсолютных путей: `without_paths` заменяет
  слои на `res://`, источник — на имя файла, папку источника — на `<source folder>`.
- **Одно правило на оба импорта** (#1380): `agent_source_path_problem`, порты томов
  (`source_volume_ports`, `system_drive_type`/`system_mount_table`) и `without_paths`
  лежат в `Editor/code/editor_system/import/edt_agent_source_rule.{h,cpp}`; ими
  пользуются импорт картинки (`file.import_image`) и импорт модели агентом
  (`file.import_model`). У модели так же: `describe` агента строится из текста
  (`text_plan`), `start` требует запомненный план, правило применяется к пути как дан,
  к разрешённому пути и в задаче перед чтением; каждый побочный файл (текстуры, `.bin`,
  `.mtl` из списка сканирования) проходит то же правило в первой задаче (после
  сканирования), во втором вызове (`describe`, `start`) и в его задаче, до того как
  импорт его прочтёт.
- **Ссылки и облачные файлы (#1408, закрыто).** Для агента путь источника проходит
  `agent_source_links_problem` (общий файл правила): префиксы пути от корня вниз
  открываются как они есть (`platform::beneath::link_entry_at`, lstat / FileAttributeTagInfo
  с OPEN_REPARSE_POINT) и отказ ставится на первом, что не обычная папка или файл:
  symlink, junction, точка монтирования, любая другая reparse-точка, запись, которую
  нельзя прочесть. Ниже отказанного ничего не трогается. Проверка стоит в `resolve`
  обоих импортов сразу после текстового правила и до `symlink_status`/`canonical`, и в
  задаче перед чтением источника (`identity_problem`). На Windows по атрибутам
  (`GetFileAttributesW`, ссылка не разыменовывается, плейсхолдер не скачивается)
  отказ получает файл, открытие которого пошло бы в сеть: `RECALL_ON_DATA_ACCESS`,
  `RECALL_ON_OPEN`, `OFFLINE` («сделайте файл доступным офлайн»); файл OneDrive,
  лежащий на диске, проходит. Побочные файлы: `import_source::may_read` → конструктор
  `model_file_access` на диске; `resolve` до `path_within_dir_from` строит лексический
  путь (`папка модели / имя`, нормализованный) и спрашивает правило; импорт агента
  ставит `agent_side_file_problem` (текстовое правило + обход от папки модели вниз),
  непустой ответ — отказ по правилу (`refusal_kind::rule`): файл не stat-ится, не
  читается и не хешируется; побочный файл для ребёнка-декодера тогда «отсутствует»,
  текстура проваливает сканирование. Импорт человека правила не получает — без изменений.
- **Читается проверенный дескриптор (#1412, закрыто).** Источник и побочные файлы агента
  смотрит и читает `read_agent_file` (общий файл правила): `platform::beneath::read_beneath`
  с `read_limits{same_device, refuse_recall, mount_points}` по маршруту `agent_read_route_of`:
  на POSIX от `/`, каждая точка монтирования настоящей таблицы на пути названа (устройство
  меняется только на ней), на Windows от диска `C:\`. Ни одна папка пути не открывается
  по пути: каждая — от предыдущей без следования ссылке (POSIX `openat` + `O_NOFOLLOW`,
  Windows — цепочка хендлов, junction отказан), на чужом устройстве вне точки монтирования
  — отказ; файл открывается сам (`O_NOFOLLOW` / `FILE_OPEN_REPARSE_POINT`), его атрибуты
  смотрятся по хендлу до первого байта, байты читаются из того же хендла. `openat2` не
  нужен: обход по компонентам уже есть и работает на любом ядре.
- **Только штамп хендла.** После обхода ссылок агентский путь больше не смотрит на файл по
  пути (ни `canonical`, ни `file_size`/`last_write_time`, ни `file_id_of`, который на Windows
  открывает файл, ни `exists`): `resolve` обоих импортов (`resolve_for_agent`) берёт штамп
  хендла чтением `stamp_only` с теми же ограничениями и кладёт его в план (`plan.stamp`);
  задача читает файл и сравнивает штамп нового хендла с планом (`same_file_stamp`: размер,
  время записи, id файла, устройство). Подменённый файл того же размера и содержания —
  другой файл, отказ. Короткие имена 8.3 в пути агента заменяются длинными
  (`agent_source_spelled`): сначала обход ссылок пути как написан, потом `long_spelling`
  (`GetLongPathNameW` перечисляет папку каждого компонента по пути — поэтому только по уже
  проверенному пути), потом обход ещё раз по длинному написанию; чтение по хендлам
  сравнивает итоговый путь с именами, и короткое имя отказало бы. Папку модели и границу
  `model_file_access` для агента нормализует лексически, без `weakly_canonical`. Побочные файлы: `import_source::read_file` (`model_file_reader{stamp,
  read}`) → `model_file_access::resolve` берёт штамп у читателя, путь сверяется лексически,
  `read` читает им и сверяет штамп; старые сверки по пути для агента не выполняются.
  Новые поля — отдельная структура и перегрузка `read_beneath`, `read_request` не меняется
  (`docs/abi/changes/1412.md`).
- **`RECALL_ON_OPEN` до открытия (#1412).** Атрибуты каждой записи на пути берутся из списка
  её папки до того, как запись открывается: в обходе ссылок — `FindFirstFileExW
  (FindExInfoBasic)` в `system_file_attributes`, в чтении — перечисление удерживаемой
  папки по хендлу для каждой папки цепочки и для файла. Имя, которого в списке нет как
  написано (короткое 8.3) или список, который не читается, — отказ (fail closed). Запись
  проецируемой ФС (VFS for Git) идёт к провайдеру при открытии, а не при перечислении.
- Ещё по ревью #1408: имя побочного файла агента с `..` отказано правилом (иначе
  `link/../x` шёл бы по ссылке до `..`), путь разрешается из одобренного кандидата; на
  Windows компонент, оканчивающийся пробелом или точкой, отказан; `without_paths` не
  разрешает источник и его папку на диске (только корни). Одиночная `.` (glTF
  `"./tex.png"`) — не компонент (#1412): мимо ссылки она не ведёт, `lexically_normal` её
  убирает.

## 4. `model` (#1195)

Исходная модель лежит вне проекта, своего `.resource` у неё нет. Поэтому владелец
настроек здесь — `.resource` **корневого выхода** импорта:
`res://F/<имя>.prefab.desc.resource`, `importer: "model"`. Абсолютный путь исходника
не хранится никогда: только имя файла и SHA-256 его байтов.

```json
{"version": 1, "source": {"name": "rock.glb", "sha256": "<64 hex, нижний регистр>"},
 "normals": "smooth", "tangents": true}
```

| Ключ | Тип | По умолчанию | Значения |
|---|---|---|---|
| `version` | int | 1 | только 1; больше — «written by a newer editor», отказ |
| `source` | object | — | `{name, sha256}`: имя файла без папок, 64 hex-цифры в нижнем регистре |
| `normals` | string | `smooth` | `smooth` (assimp `GenSmoothNormals`), `flat` (`DropNormals` + `GenNormals`: собственные нормали модели отбрасываются) |
| `tangents` | bool | `true` | `false` убирает `CalcTangentSpace` |

Значения по умолчанию — импорт как до #1195. `Triangulate` включён всегда;
режимы материалов и текстур — как раньше, это не настройки. Масштаб, ось «вверх» и
разворот UV в v1 не входят. Разбор строгий, как у `texture`: неверный тип или
значение — отказ с именем ключа. Неизвестный ключ верхнего уровня отклоняется в
аргументах агента и в запросе декодера, а при чтении `.resource` пропускается
(`unknown_settings_keys::ignore`): его мог записать более новый редактор версии 1, и
перезапись его сохраняет, так что перезаписанный файл всегда читается. Неизвестный ключ
внутри `source` — отказ везде.

Имя исходника записывается в том виде, который принимает читатель
(`model_source_of`): `/`, `\`, `:`, управляющие символы и DEL заменяются на `_`, длина
обрезается до 255 байт по границе UTF-8, пустое имя, `.` и `..` дают `model`. Имя файла
модели (`scan:v2.glb` на Linux) поэтому экспорт не ломает.

Код: `edt::model_import_settings` (`Editor/code/model_import/edt_model_import_settings.h`,
собирается и без assimp) → `import_source::settings` → `mdl::mesh_processing` в новой
перегрузке `mdl::import_model` (`import_options` не расширяется, правило #1412;
`docs/abi/changes/1195.md`). Процессу декодера настройки идут в запросе
(`decode_request::settings`, тот же строгий разбор, `source` в запросе — отказ). Ключ кэша
декодированных моделей (`decoded_model_adapter::cache_key`) включает настройки. Адаптер
движка для `res://x.glb` всегда работает с настройками по умолчанию.

Запись (`edt_model_import_meta.h`, экспорт `asset_exporter::export_to_project`):

- `.resource` проверяется до записи любого файла экспорта, а пишется прямо перед
  префабом (база ассетов, увидев префаб, берёт его guid); не записался префаб —
  `.resource` забирается назад. Все записи — `platform::beneath`, без следования по
  ссылкам, в верхний слой проекта.
- Нового `.resource` нет — создаётся новым файлом (никогда поверх) с новым guid.
- Человек перезаписывает префаб («[overwrite]» в окне экспорта) — у существующего
  `.resource` сохраняются `guid` и `flags`, заменяются `importer` и `settings`; ключи
  `settings` версии 1, которых этот редактор не знает (записал более новый), остаются.
  Запись — temp + rename и только пока файл тот же, что был прочитан (проверка прямо
  перед rename, не атомарно с ним). Отказ до записи
  чего-либо: `.resource` не читается, не в каноническом виде `res::write_asset_meta`
  (правлен руками), более новой версии формата или `settings.version` > 1.
- Агент никогда не перезаписывает: существующий `.resource` — отказ.

Агент: `file.import_model {..., settings?: {normals?, tangents?}}` (схема с
`additionalProperties: false`). Вопрос человеку показывает настройки
(«settings: normals flat, tangents off»), они входят в то, что он одобряет; ключ
списка файлов (`files_token`) включает настройки, поэтому токен от вызова с другими
настройками отклоняется.

Человек (PR 2): File > Import Model... → выбор файла → модальное окно «Model Import
Settings» (Normals: Smooth / Flat, Tangents; Import / Cancel, Esc = Cancel; форма —
`model_import_settings_form` без ImGui, окно рисует `import_component`). Import
вызывает `file.import_model {path, settings}` от имени человека; вызов от `ui` без
`name`/`folder` идёт прежним путём диалога (задача → окно экспорта), теперь с этими
настройками, они же попадают в `.resource`. Cancel ничего не импортирует. Плохие
`settings` в таком вызове — `invalid_args` до начала импорта. Пока окно открыто,
горячие клавиши редактора молчат (как под вопросом `dialog_service`, #470).

## 5. Повторный импорт (#1194)

Настройки читаются из `.resource` исходника; выходы пересоздаются по
тем же путям; guid и settings сохраняются.

Картинка (PR 1): в контекстном меню строки картинки (`.png/.jpg/.jpeg`, у которой
есть `<name>.resource`) пункт «Re-import...» открывает выбор файла и окно Import Image
в режиме повторного импорта: «Re-import res://…», источник, Wrap/Filter/Mipmaps из
записанных настроек, список файлов, которые будут переписаны, без имени и папки.
Команда `file.reimport_image {target, path, settings?}` (`not_for_agents`) и
`image_importer::resolve_reimport/start_reimport` — только действие человека: любой
другой вызов получает `denied` («re-import is a person's action for now (#1457)»).
Цель — картинка верхнего слоя проекта (не ссылка) с `.resource` (каноничный, не новее
редактора, importer `texture`, настройки читаются `parse_image_settings`), с
`<name>.txm.desc`, чей `data` указывает на эту картинку, и с каноничным `.resource`
у desc; документ с несохранёнными правками картинки или desc — `busy`. Источник
проверяется как при импорте человека, того же формата (png для png) и не сама
картинка. Не заданные в `settings` ключи берутся из записанных. Задание пишет только
поверх прочитанных байтов: временный файл пишется целиком, затем файл перечитывается и
сравнивается (до fsync и rename; `write_request::stream` у `platform::beneath`),
никогда через ссылку. Порядок: картинка; при изменённых настройках — `.txm.desc`
(меняются только `header.wrap/mag/min` и `header.data.mip_levels`, остальное остаётся)
и последним `.resource` картинки (guid и flags остаются). `.resource` у desc не
трогается. При ошибке заменённые файлы возвращаются в обратном порядке; то, что
вернуть не удалось, называется в ошибке («… stays changed») и всё равно сообщается
кэшу и базе ассетов как изменённое. Блокировки сохранения на пути картинки нет
(`desc_binary::save_lock` — только для `.bin` геометрии).

Модель (PR 2): «Re-import...» в контекстном меню строки `.prefab.desc`, у которой есть
`.resource`, открывает выбор файла (как File > Import Model...) и окно «Model Import
Settings» в режиме повторного импорта: «Re-import <префаб>», настройки из `.resource`
префаба, заметки (записанное имя источника; другое имя у выбранного файла; «the same file
as last time», когда SHA-256 совпадает — файл до 256 МиБ хешируется io-задачей, окно
открывается сразу, заметка добавляется, когда задача кончилась; ответ задачи для закрытого
или заново открытого окна ничего не делает); ничего из этого не блокирует.
Дальше `file.import_model {path, reimport, settings?}` —
только человек (любой другой вызов получает `denied`, «re-import is a person's action for
now (#1457)»; с `name`, `folder` или `files_token` — `invalid_args`); не заданные ключи
`settings` берутся из записанных. До всего прочего проверяется (`read_model_import_record`,
`import_component::check_reimport`): префаб в верхнем слое проекта (слой ниже —
`invalid_args`), его `.resource` есть, каноничен, не новее редактора, importer `model`,
настройки читаются (`unknown_settings_keys::ignore`); префаб, открытый с несохранёнными
правками, — `busy`; так же `busy`, когда документ префаба — ссылка (EPIC-82) и любой
документ её цепочки (`chain_of`) или под ней (`descendants_of`) не сохранён
(`is_open_with_unsaved_changes(document_manager&, tag, ...)` в `edt_asset_ops.h`).
Диалог экспорта в этом режиме: имя и папка — префаба, список файлов
с «[overwrite]»; Export запрещён, пока любой перезаписываемый файл открыт с
несохранёнными правками, и пока корневой префаб новой модели ложится не на этот префаб.
Файлы перезаписываются на месте (их `.resource` и ID остаются); `.resource` префаба
сохраняет guid, flags и неизвестные ключи настроек. Порядок: новый `.resource` (обычный
импорт) пишется до префаба, чтобы база ассетов взяла его guid; существующий (повторный
импорт) уже держит guid и пишется после префаба. «Больше не создаются»: строки `res://`
старого префаба (прочитанного до перезаписи) под папкой префаба, которых нет среди файлов
нового экспорта и которые есть на диске; они не удаляются, а перечисляются в отчёте
диалога и в логе (`.bin` геометрии и `.resource` в список не попадают — на них префаб не
ссылается).

**Запись `made` и проверка перед перезаписью (#1194).** Каждый экспорт модели (человека и
агента, `asset_exporter::export_to_project`) записывает в `settings` `.resource` префаба
ключ `made`: объект «путь относительно папки префаба (через '/') → SHA-256 (64 строчные
hex) байтов на диске после записи» для каждого файла, который экспорт записал или оставил
как есть: все цели remap, сам префаб (хеш его выходных байтов) и `.bin` геометрии (desc и
`.bin` хешируются с диска после `rnd::write_geometry_files`, через `platform::beneath`, до
512 МиБ); `.resource` префаба в список не входит. Префаб пишется последним, поэтому к нему
все хеши известны (`set_made(plan, made)` в `edt_model_import_meta.*` перерисовывает текст
плана, guid/flags/неизвестные ключи остаются; больше 4096 файлов — `made` не пишется, WARN).
Разбор: в режиме `ignore` (прочитанный `.resource`) `made` проверяется (объект, ≤ 4096
записей; ключи — простые относительные пути: без ведущего '/', без сегмента '..', без '\',
без управляющих символов, ≤ 1024 байт; значения — 64 строчные hex), плохой `made` — ошибка,
как у других ключей; в режиме `refuse` (аргументы агента, запрос декодеру) — отказ «settings.made
is recorded by the editor, not given». `rewrite_model_settings` старый `made` выбрасывает.
`model_import_record::made`; старые записи без `made` остаются валидными.

Диалог экспорта в режиме повторного импорта сразу запускает io-задачу (`job_service`,
`m_lifetime` диалога): для каждой цели remap, которая есть в верхнем слое (и `.bin` геометрии),
читает файл через `platform::beneath` и считает SHA-256 (`asset_exporter::scan_reimport`);
сравнивает (а) с `made` записи — «unchanged» / «changed» / «unknown» (нет записи или пути в
ней) и (б) с байтами, которые экспорт записал бы (`asset_exporter::planned_bytes`: remap
`.desc` + pretty JSON или сырые байты; для пары геометрии (б) не делается). Файл, чьи байты
совпадают с новыми, в списке перезаписи не показывается. Изменённый — строка «changed after
import: edits will be lost», неизвестный — «may hold edits made after import: they will be
lost» (цвет warning темы). Пока проверка идёт, Export выключен («checking the files...»);
файл, который не прочитался, запрещает Export. Если перезаписывается хоть один изменённый или
неизвестный файл, Export ждёт галочку «Overwrite the files listed above, losing their edits»;
она сбрасывается при каждом открытии (одна галочка на запуск) и при повторной проверке после
неудачного экспорта. Решение — `asset_export_dialog::reimport_blocker` / `export_blocker()`
(без ImGui), `start_export()` делает то же, что кнопка. Внутри задачи экспорта каждый файл,
который увидела проверка, перед перезаписью хешируется снова (`seen` у `export_to_project`);
отличается — экспорт падает: «<tag> changed after the dialog looked at it: nothing more was
written» (байты, которых человек не видел в списке, не перезаписываются). Путь агента `seen` не
передаёт (поведение прежнее).

«Больше не создаются» берутся из `made` старой записи (`made` минус цели, как `res://` под
папкой префаба; `.bin` целей геометрии считаются целями); без `made` — прежний поиск ссылок
старого префаба под его папкой; если папка — корень `res://`, ничего не перечисляется и отчёт
говорит «the files of the earlier import are not known (old record)»; если старый префаб не
прочитался — «the earlier prefab could not be read: files it made are not listed». Сообщение
показывается в отчёте диалога и в WARN.

Повторный импорт не добавляет новый экземпляр модели в открытый уровень (`exported` не
вызывается, когда у диалога `reimport_target()`).

Отмена: в режиме повторного импорта, как только записан первый файл (`progress->done > 0`,
атомарно), Cancel выключен, Esc игнорируется, а `job.cancel` из списка задач отклоняется
(veto задачи) — `asset_export_dialog::may_cancel_export`. Если отмена всё же пришла (до первого
файла), диалог не закрывается: форма показывает «The re-import was cancelled part way» и список
записанного (`written_before_text`), проверка файлов идёт заново.

## 7. Известные ограничения

- Сбой процесса между записями может оставить `.resource` (картинки или desc) без
  своего файла; такой `.resource` держит имя (`res::name_taken`, `needs_input`), пока
  человек его не удалит.
- Импорт картинки пока не берёт блокировку импорта модели / миграции (follow-up issue
  заведёт исполнитель ведущего).
- Правило источника проверяет текст: промежуточная ссылка внутри пути на сетевой том
  видна только после одобрения (повторная проверка разрешённого пути), а `stat` при
  разрешении уже идёт по ней.
- Отказ, задуманный как fail closed: смена устройства в точке, которой нет в
  `/proc/self/mounts` (вложенные подтомы btrfs, контейнеры), и на Windows папка с правом
  обхода, но без права чтения списка (её не перечислить до открытия).
- Смена устройства разрешена на любой точке монтирования таблицы на пути, какое бы
  устройство там ни оказалось: монтирование поверх неё (FUSE пользователя) между
  проверкой и чтением не отличить. Подтом btrfs без своей строки в таблице монтирования —
  другое `st_dev`: файл в нём агенту не читается.
- На ReFS `nFileIndex` хендла (64 бита) не обязательно уникален: штамп там слабее.
- На POSIX облачные ФС (FUSE) отсекает список типов томов; отдельной проверки атрибутов
  там нет.
